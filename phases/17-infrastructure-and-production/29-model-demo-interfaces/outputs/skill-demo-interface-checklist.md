根据模型演示的说明或代码，按照以下清单进行评审。每一项标记为 PASS、FAIL 或 UNKNOWN。为每个判断提供证据：文件和行号、配置项，或说明中的引文。

如果缺少以下信息，请询问：

- 模型调用：提供方 API 还是本地模型、典型延迟，以及单次调用成本。
- 受众：仅团队成员、受邀评审者，还是任何持有链接的人。
- 输入类型，以及模型接受的最大输入。
- 演示运行方式：框架、服务器，以及链接的托管方。

检查清单：

约定

1. 输入有明确的类型、最大大小，以及控制字符处理规则。
2. 服务器会再次检查每一项限制。只有浏览器检查应判为 FAIL。
3. 每种输出类别至少有一个示例。
4. 模型调用设有超时，且超时错误附有面向用户的操作提示。

反馈

5. 请求运行期间，提交控件被禁用。
6. 页面通过已用时间或进度显示，表明模型正在工作。
7. 文本回复以流的形式到达，页面显示首 token 时间。
8. 流开始后的失败以错误事件传达给用户。无声停止应判为 FAIL。

错误

9. 每个错误响应都有稳定的错误代码、包含相关数值的消息、给出一个操作的提示，以及请求 ID。
10. 任何错误响应都不包含堆栈跟踪、文件路径或秘密信息。

公开链接

11. 存在按客户端执行的限流。被拒绝的请求收到状态码 429 和 `Retry-After` 响应头。
12. 位于代理后面时，限流键仍正确。客户端无法自行选择键。
13. 整个演示设有覆盖所有客户端总量的用量上限或支出限制。
14. 访问需要令牌、密码或登录，除非所有者希望向所有人开放演示。
15. 限流和上限也适用于框架创建的 API 端点。
16. 页面将模型输出当作文本写入，绝不当作 HTML。服务器发送 `Content-Security-Policy` 响应头。

隐私

17. 日志不保留输入文本、不保留带查询字符串的完整 URL，也不保留原始客户端地址。
18. 所有存储输入的功能，例如标记、历史或分析，都已关闭，或已在页面上告知用户。
19. 页面告诉用户服务器会保留什么。

产品化信号

20. 报告已经出现的每一种信号：
    - 团队之外的人每周都会使用演示。
    - 有人提出可用性目标。
    - 用户要求账户、保存结果或历史功能。
    - 模型成本成为预算中的一个项目。
    - 输入包含受到合同或法律约束的数据。

输出：

1. 一张包含项目编号、判断和证据的表格。
2. 为每个 FAIL 列出修复方案，按风险排序。优先公开链接和隐私项，其次是错误，再其次是约定，最后是反馈。每项修复都应指明文件、配置项或代码改动。
3. 列出已经出现的产品化信号。如果存在一个或多个信号，建议迁移到生产技术栈。该技术栈应具备真正的身份验证、链路跟踪和每用户成本追踪。
4. 一行结论：可以分享、完成所列修复后可以分享，或应先迁移到生产技术栈。

硬性否决条件。存在以下任何一种情况时，不得将演示标记为可以分享：

- 服务器不检查输入大小。
- 任何人都能打开的链接没有限流或没有用量上限。
- 日志或框架功能存储了输入文本，但页面没有告知用户。

拒绝规则：

- 如果受众未知，按任何人都能访问处理。
- 如果单次模型调用的成本未知，公开链接前必须设置用量上限。
- 如果演示运行在框架上，检查它在标记功能、分享链接和自动创建 API 端点方面的默认值。不要假设这些默认值适合公开链接。
