# 在选择输出之前先定义成效

> 飞速的代码实现能力反而放大了选错问题所付出的代价。唯有先厘清所追求的实质成效（Outcome），高速前进才能指向正确的方向。

**Type:** Learn + Build
**Languages:** Python (stdlib)
**Prerequisites:** None
**Time:** ~60 分钟

## 学习目标

- 在不预设具体解决方案的前提下，撰写成效框架（Outcome Frame）。
- 明确目标用户、发生情境、当前现状及预期改善的指标。
- 显式声明硬性约束（Constraints）与非目标（Non-goals）。
- 识别“解决方案泄漏”（Solution Leakage），防止其过早固化为开发范围。

## 交付产物不等于实质成效

“构建一个故障应急助手”指明的仅仅是某种产物（Output）。它完全没有说明究竟谁需要它、什么指标会得到改善，以及哪些关键防线必须保持安全。

相比之下，成效框架（Outcome Frame）是这样表述的：

> 当生产环境发生告警时，值班工程师能在两分钟内定位故障服务并确认下一步安全操作，同时整个排查过程保持只读并具备完整的审计追踪。

这句话所定义的成效，既可以通过一套软件来实现，也可以通过优化运维手册（Runbook）、修复数据，或者做一次更轻量级的界面改造来达成。它让团队始终紧盯最终要解决的问题，而不是过早死磕在某人凭空设想出的第一套具体产物上。

## 成效框架的六大要素

| 构成要素 | 核心问题 |
|---|---|
| 用户（User） | 谁在直接面对并承受该问题？ |
| 情境（Situation） | 该问题何时、何地发生？ |
| 当前现状（Current behavior） | 现状如何运作，包括现有的各种临时变通手段（Workarounds）？ |
| 期望成效（Desired outcome） | 哪些可观测的状态应当得到实质改善？ |
| 约束条件（Constraints） | 哪些安全、策略、成本或兼容性底线是固定的？ |
| 非目标（Non-goals） | 哪些极具诱惑但相关的邻近工作被明确排除在外？ |

```mermaid
flowchart LR
  U[用户与情境] --> C[当前现状]
  C --> O[期望成效]
  O --> K[约束条件]
  K --> N[非目标]
  N --> E[证据探究问题]
```

## 识别解决方案泄漏

当成效表述中夹带了未经证据充分论证的产品形式、界面形态、模型选型、技术框架或底层架构时，就发生了“解决方案泄漏”（Solution Leakage）：

- “用户每周收到一份 AI 摘要”：泄漏了“摘要”这一形式以及“每周”这一频次。
- “用户在审批前能够准确理解账户变更”：表述的是真正的成效。
- “部署向量数据库”：泄漏了基础设施选型。
- “审核期间能够便捷获取相关的合规政策依据”：表述的是真正的能力提升。

当既有的系统兼容性真正锁定了某项技术时，约束条件中可以指名该技术，但必须明确记录其被锁定的客观理由。

## 约束条件守护成效底线

约束条件绝非单纯的实现细节，它们是真实世界目标不可分割的组成部分：

- 故障诊断期间严禁对生产环境执行任何写入操作；
- 响应耗时必须控制在事故处置时间预算之内；
- 现有的审计事件记录必须继续保持唯一权威性；
- 不允许引入新的运行时依赖库；
- 无障碍访问（Accessibility）支持必须保持完好。

如果一个系统虽然表面上达成了预期目标，却违反了任何一项刚性约束，那么该系统就是彻底失败的。

## 依靠非目标划清边界

非目标能够有效防止一个本应小巧实用的功能切片膨胀成庞大臃肿的平台。好的非目标必须足够具体，足以理直气壮地拒绝无关需求：

- 不做自动化故障修复；
- 不做全新的告警路由系统；
- 不取代现场事故指挥官（Incident Commander）；
- 本切片中不涉及历史数据分析功能。

## 构建它

本课的实验程序将校验一个 `OutcomeFrame` 的有效性，并将结果写入 `outputs/outcome-frame.json`。

运行命令：

```bash
python3 code/main.py
python3 -m unittest discover code/tests -v
```

尝试将期望成效修改为“使用故障应急助手”。校验器应当敏锐地指出：所提议的产物已经泄漏到了成效定义之中。

## 练习

1. 将你项目待办列表（Backlog）中的一个功能需求重写为标准的成效框架。
2. 添加一条会从根本上改变可行解决方案空间的刚性约束。
3. 添加两条能够确保首个开发切片保持精简的非目标。
4. 找出能够证伪该期望成效的最早观测指标。
5. 构想三种完全不同、但都能满足同一成效定义的产物形式。

## 延伸阅读

- [Nuseibeh and Easterbrook, Requirements Engineering: A Roadmap](https://www.cs.toronto.edu/~sme/papers/2000/ICSE2000.pdf)：探讨将现实世界目标作为软件工程锚点的核心思想。
- [Dardenne, van Lamsweerde, and Fickas, Goal-Directed Requirements Acquisition](https://doi.org/10.1016/0167-6423(93)90021-G)：阐述如何将高阶目标逐步细化为操作性约束与具体规约。
