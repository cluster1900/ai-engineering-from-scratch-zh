# MCP 可靠性、取消与流控

> 请求 ID 只能关联消息。它不能让副作用变得安全，不能让后台工作进程停下来，也不能保护数据流免受慢消费者的拖垮。

**Type:** Build
**Languages:** Python
**Prerequisites:** Phase 13, Lessons 09 and 13
**Time:** ~120 minutes

## 学习目标

- 为 stdio 和 Streamable HTTP 分别实现正确的请求取消信号。
- 解决完成（completion）与取消（cancellation）之间的竞态，避免在取消后发送多余消息。
- 严格区分瞬时请求取消与持久化 `tasks/cancel` 的语义差异。
- 根据副作用属性与显式幂等键（idempotency keys）制定重试策略。
- 在对进度队列设置容量上限的同时，确保最终响应不被丢弃。
- 通过重新连接、权威重拉（refetch）以及带抖动的退避机制实现流的恢复。

## 核心问题

最昂贵的分布式系统缺陷往往潜伏在顺利执行的“正常路径”之外。

客户端调用了一个工具。服务端开始执行。进度通知源源不断发出。反向代理在中间缓冲了事件流。客户端触发超时并断开连接。服务端恰好在 1 毫秒之后完成了业务处理。客户端使用新的 JSON-RPC id 发起重试。于是，这项写操作（mutation）被重复执行了两次。

链路上的每一个组件从自身局部来看都没有报错，但整个系统却从全局上崩溃了。

MCP 规范定义了消息格式与传输层行为，但你的应用程序仍然必须亲自负责：

- 时间预算（Time budgets）；
- 业务幂等性（Business idempotency）；
- 有界队列（Bounded queues）；
- 重试分类（Retry classification）；
- 持久化任务状态（Durable task state）；
- 重连与重新拉取策略（Reconnect and refetch policy）。

本课程将这些决策构建在一个确定性的模拟器中。这里没有引入 sleep、真实网络 socket 或随机故障。你将直接掌控取消事件的先后次序。一个同步线程测试还会强制两个账本客户端对同一个幂等键展开竞态争夺。

## 请求取消因传输层而异

无论使用何种传输协议，客户端的意图都是一致的：不再需要当前正在执行的结果。然而，在线路（wire）上传递的具体信号却截然不同。

### stdio

stdio 采用单条共享的双向通道。客户端发送一个 notification：

```json
{
  "jsonrpc": "2.0",
  "method": "notifications/cancelled",
  "params": {
    "requestId": 41,
    "reason": "User closed the operation"
  }
}
```

该通知属于“即发即弃”（fire-and-forget）。服务端不需要且绝不能对其返回任何 JSON-RPC 响应。

服务端应当停止工作、释放资源，并不再为已被取消的请求发送响应。如果请求未知、已经执行完毕，或者无法安全中断，服务端可以安全地忽略该取消通知。

格式错误、指向未知请求或针对已完成请求的取消通知都会被服务端静默忽略。如果将这些并发竞态转化为新的错误报文，只会引发更多竞态问题。

### Streamable HTTP

现代 Streamable HTTP 为每个请求分配独立的 HTTP 响应或 SSE 响应流。客户端通过**直接关闭该请求的响应流**来发出取消信号。

不要为普通的 HTTP 请求 POST 发送 `notifications/cancelled`。断开流本身就是取消信号。

一旦服务端检测到连接断开，就应当停止工作，并且绝不能再为该请求发送任何后续消息。

### 服务端发起的取消范围极其有限

服务端绝不能使用 `notifications/cancelled` 来随意取消客户端的普通调用。在 stdio 传输上，服务端发起的取消仅限于终止 `subscriptions/listen` 监听请求。必须将这一极窄的路径与客户端发起的常规请求取消严格区分开。

## 取消是一场竞态

两种事件发生的顺序都是完全合法的。

### 取消获胜

```text
request starts（请求启动）
client sends cancellation signal（客户端发送取消信号）
server marks request cancelled（服务端将请求标记为已取消）
worker reaches completion（工作线程执行完成）
server suppresses the response（服务端抑制并不发送响应）
```

### 完成获胜

```text
request starts（请求启动）
worker commits the result（工作线程提交业务结果）
server sends the response（服务端发送响应）
cancellation arrives late（取消信号迟到）
server ignores the late notification（服务端忽略迟到的通知）
```

客户端也必须主动忽略针对其已经放弃的请求所迟到的响应。由于网络延迟的存在，任何一方都无法向另一方绝对证明是谁先观察到了状态变更。

```figure
mcp-reliability-race
```

本课的 `RequestCoordinator` 会记录单一的终态记录。一旦取消，`complete()` 将不再返回任何响应；而迟到的取消通知也绝不能篡改已完成的记录。

## 超时机制需要两个时钟

单一的无活动（inactivity）计时器是远远不够的。

必须同时引入两套时间上限：

1. **空闲超时（Idle timeout）**：请求在多长时间内未产生任何有用活动即视为超时。
2. **最大超时（Maximum timeout）**：从请求最初发起时刻算起的绝对物理时钟预算（wall-clock budget）。

持续产生的进度事件（Progress）可以重置空闲时钟，但**绝不能**推迟或消除最大截止时间。

```text
start: 0 ms
progress: 400 ms
progress: 800 ms
progress: 1200 ms
idle timeout: 500 ms
maximum timeout: 2000 ms
```

在 1500 ms 时，请求依然处于活跃状态，因为距离上一次进度事件仅过去了 300 ms。但在 2000 ms 时，最大截止时间将强制取消该请求，即便在 1999 ms 时刚刚产生了一个新的进度事件。

进度通知是可选的。服务端完全可以接受一个进度令牌（progress token）但在执行期间不发送任何更新。绝不要因为存在进度令牌就赋予其无限的超时宽限。

MCP 的进度数值必须单调递增。在完成或取消之后，所有通知必须立即停止。对进度通知进行速率限制（rate-limit），防止高速运转的 worker 冲垮网络传输。

## 请求取消不等于 `tasks/cancel`

这两种机制解决的是完全不同生命周期层面的问题。

| 机制 | 作用目标 | 线路信号 | 成功意味着什么 |
|-----------|--------|--------|--------------------|
| stdio 上的请求取消 | 单次在途 RPC | `notifications/cancelled` | 客户端放弃了该请求；若可行服务端应当停止执行 |
| HTTP 上的请求取消 | 单个在途响应流 | 关闭该流 | 客户端放弃了该请求；若可行服务端应当停止执行 |
| `tasks/cancel` | 单个持久化 Task | 普通 MCP 请求 | 服务端已确认收到取消意图 |

`tasks/cancel` 的调用成功并不证明后台 worker 已经停止运行。Task 可能依然保持 `working` 状态，直到 worker 在某个检查点（checkpoint）感知到取消标记；工作也可能在感知到该标记之前就已经成功执行完毕。

当 HTTP 连接断开时，**绝不要**清除持久化 Task 的状态。创建 Task 的初衷正是为了让其生命周期能够超越单次请求与单条连接的限制。

## 新的 JSON-RPC ID 绝不等于幂等性

JSON-RPC id 仅用于关联单次请求与响应，它们绝不代表业务操作本身。

假设客户端提交了一笔账单扣款（id 为 `41`），中途丢失了服务端的响应，随后客户端使用 id `42` 发起重试。服务端看到的是两条截然不同的消息。如果没有应用层的唯一标识，服务端根本无法得知它们代表同一次结账请求。

幂等键（idempotency key）明确代表了业务意图：

```json
{
  "name": "charge_account",
  "arguments": {
    "account": "acct-7",
    "cents": 1200,
    "idempotencyKey": "checkout-7"
  }
}
```

服务端会持久化记录：

- 幂等键；
- 操作参数的哈希指纹（argument fingerprint）；
- 已提交的执行结果。

相同的键与相同的参数将直接返回之前存储的结果。相同的键若携带了不同的参数，则会被坚决拒绝。这能防止因为误复用幂等键而篡改了另一项不同的业务操作。

### 账本边界必须具备原子性与持久性

以下执行时序是极度危险且不安全的：

```text
check key（检查键是否存在）
run mutation（执行写操作）
store result（存储执行结果）
```

两个并发 worker 可能会同时发现该键不存在，进而同时执行这项有副作用的写操作。更糟糕的是，如果程序在执行完副作用后、存储结果前发生崩溃，重试时同样会造成重复执行。

本课程使用基于文件的 SQLite 账本。利用 `BEGIN IMMEDIATE` 将键的检查、模拟的业务副作用、执行计数器以及结果存储全部序列化在同一个事务中。即便两个独立的账本连接使用相同的键展开竞态并发，也只会产生一次真正的业务执行并记录一份已提交的结果。关闭并重新打开账本文件，该历史记录依然完整保留。

所有返回值均通过存储的 JSON 重新反序列化生成。调用者绝不会直接拿到账本内部持有的可变对象引用，从而杜绝了调用方修改返回字典而污染后续重放结果的隐患。

模拟器中的业务副作用是包含在同一个 SQLite 事务内的收据与计数器。在生产环境中，真实的付款、容器部署或外部第三方 API 调用，绝不是靠向本地数据表写一条记录就能自动获得原子性的。生产架构需要依赖分布式共享数据库事务、事务性发件箱（Transactional Outbox），或者要求上游提供方本身支持相同的幂等键。仅靠进程内互斥锁（Process lock）既无法协调多个服务副本，也无法在进程重启后幸存。

### 重试决策矩阵

在实现重试逻辑之前，必须对重试进行清晰分类。

| 类别 | 示例 | 重试规则 |
|------|---------|------------|
| 安全（Safe） | 无副作用的确定性读操作 | 在明确故障边界后，可使用新的 JSON-RPC id 直接重试 |
| 有条件（Conditional） | 具备持久化幂等键的写操作（Mutation） | 必须使用完全相同的幂等键和完全相同的参数发起重试 |
| 不安全（Unsafe） | 未提供业务去重机制的写操作 | 严禁自动重试；必须先进入人工或系统对账调和流程 |

工具描述符中附带的 `readOnlyHint` 和 `idempotentHint` 仅仅是不可盲信的外部提示。真正的重试安全性完全取决于应用层契约与服务端的底层实现。

## 背压是正确性的一部分

SSE 生产者生成进度事件的速度，可能远远超过客户端、代理或网络链路的消费能力。一个无上限的无限队列会将网络拥堵转化为内存耗尽（OOM）。

必须采用有界队列（Bounded queue），并明确定义在过载时可以牺牲什么。

进度通知是可以被替代的。对于同一个进度令牌，后到的进度数值自然取代先前的旧值。然而，最终的 JSON-RPC 响应是绝对不可替代的。

本课实现的缓冲区执行如下流控策略：

1. 合并（Coalesce）同一令牌相邻的进度更新；
2. 当队列达到容量上限时，丢弃最旧的进度数据；
3. 将事件流标记为“需要权威数据重拉（needs authoritative refetch）”；
4. 始终完整保留最终响应；
5. 如果保留最终响应需要以丢弃另一个最终响应为代价，则拒绝该状态。

这是具备明确恢复机制的“有界丢弃”。静默丢失绝不是合规的策略。

### 代理缓冲问题

服务端可能在完美流式输出，而中间的反向代理却在私自积攒事件缓冲。

对于 SSE 响应，必须下发以下响应标头：

```http
Content-Type: text/event-stream
Cache-Control: no-cache
X-Accel-Buffering: no
```

2026 年的 Streamable HTTP 规范强烈建议配置 `X-Accel-Buffering: no`，以便兼容的代理服务器（如 Nginx）能够即时向客户端推送事件。

对于长期处于静默状态的长连接，需定期发送 SSE 注释行（保活心跳）：

```text
:
```

客户端会自动忽略注释行。中间代理设备则能看到网络活动，从而避免切断看似空闲的连接。

传输保活不等于业务进度。绝不能因为收到了传输层的保活注释就顺带重置了业务操作的语义空闲超时计时器。

## 重连意味着重新拉取

现代 Streamable HTTP 协议**不支持**通过 `Last-Event-ID` 进行断点续传。

当 `subscriptions/listen` 事件流意外中断后：

1. 使用全新的 JSON-RPC id 发起新的监听请求；
2. 重新注册所需的订阅过滤器；
3. 调用权威接口全量拉取可能受影响的 tools、resources、prompts 或 Tasks；
4. 依据稳定的全局唯一标识对应用层状态进行去重；
5. 绝不要仅仅因为先前响应丢失就盲目重放未受保护的危险写操作。

示例中的恢复方案显式将 `sendLastEventId` 设置为 false，并列出了需要全量重拉的资源清单。

### 防止重连风暴（Herd Effect）

如果 10,000 个客户端在连接断开后恰好都在整整 1 秒时同时重连，刚刚恢复的服务端将瞬间再次被打垮。

必须采用带有随机抖动（Jitter）与上限保护的指数退避机制。本课根据客户端 ID 和重试次数计算出确定性的抖动偏移，使得单元测试完全可复现：

```text
attempt 0: up to 250 ms
attempt 1: up to 500 ms
attempt 2: up to 1000 ms
...
cap: 8000 ms
```

生产环境可以采用密码学安全随机数或运行时随机数。不变的核心在于时间分布的离散化，而非特定数学公式本身。

## 手写实现

`code/main.py` 构建了五个精炼的可靠性核心组件：

### `RequestCoordinator`

- 启动在途请求并维护空闲与最大双重截止时间；
- 发送单调递增的进度通知；
- 为 stdio 与 HTTP 分别生成规范的取消信号；
- 忽略非法的取消通知；
- 显式裁决取消与完成之间的终态竞态；
- 确保服务端发起的取消仅用于 stdio 订阅。

### `MutationLedger`

- 演示在缺乏业务键的情况下，两次使用不同的 JSON-RPC id 会导致两次重复执行；
- 使用基于文件的 SQLite 事务串行化键检查、模拟业务效果、执行计数器与结果提交；
- 支持跨多个独立账本连接，对相同幂等键和完全一致的参数进行全局去重；
- 拒绝使用相同幂等键但篡改参数的请求；
- 返回防御性深拷贝，在重新打开账本文件后依然完整保留已提交数据。

### `DurableTaskService`

- 对取消请求进行确认回执（Acknowledge）；
- 保持 Task 处于 `working` 状态，直到工作线程主动检查到标记；
- 直观展示为什么“确认收到取消”绝不等于“任务已终止”。

### `BoundedSseBuffer`

- 在高压背压下合并或淘汰旧进度；
- 明确记录当前流已需要进行权威数据全量重拉；
- 绝不丢弃最终响应。

### 恢复辅助工具

- 输出适用于代理环境的 SSE 标头与保活心跳注释；
- 生成完整的重连与全量重拉执行方案；
- 采用确定性带抖动的指数退避算法打散重试压力。

## 交互式实验

在不添加任何 sleep 延时的前提下，运行四种特定的事件先后顺序：

1. 启动请求 `A`，将其取消，随后调用 `complete()`。
2. 启动请求 `B`，将其完成，随后送达迟到的取消信号。
3. 启动请求 `C`，在每次空闲超时之前均发送进度事件，但最终突破最大绝对超时阈值。
4. 在 Streamable HTTP 上启动请求 `D`，并直接关闭其响应流。

针对每种场景，记录：

- 请求最终所处的终态；
- 是否生成了最终响应；
- 在通信线路上发出的取消信号具体形式；
- 客户端应当主动忽略哪个事件。

然后将场景 `D` 改为 stdio 传输。业务操作完全一致，但在通信线路上产生的取消信号必须发生变化。

## 动手实践

为 `MutationLedger` 扩展一个 `reserve_inventory`（库存预留）写操作。

需求规范：

1. 幂等键需绑定 SKU、数量、租户以及操作名称。
2. 使用相同的键和完全相同的参数重试时，必须直接返回第一次生成的预留结果。
3. 使用相同的键但修改了预留数量发起重试时，必须报错拒绝，且不得产生二次预留。
4. 当写操作已在服务端提交但响应在回传途中丢失时，支持凭借幂等键发起对账核验。
5. 结果中绝不能记录机密凭证或支付敏感信息。
6. 若客户端在调用时未提供幂等键，则直接禁用自动重试机制。
7. 模拟订阅流意外断开的情景，在决定后续动作前，先对该库存记录执行权威全量重拉。
8. 启动两个位于同步屏障（Barrier）前的账本连接，并发提交同一个幂等键。断言全局仅有一次预留成功提交。
9. 篡改第一次返回的预留对象。重新传入该键进行重放，证明底层存储的真实结果未受任何污染。
10. 关闭并重新打开账本文件，通过键核验预留数据完好无损。

请保持工程诚信：如果库存数据实际上存在于另一个独立微服务中，请明确说明该微服务是否支持同一个幂等键，或者是否必须引入事务性发件箱（Transactional Outbox）来桥接本地提交与远程副作用。

当以下各项全部达成时，本节课目标即告完成：

- stdio 取消操作发送 `notifications/cancelled` 且不接收任何响应。
- Streamable HTTP 取消操作直接关闭响应流，绝不发送多余的取消 POST 请求。
- “先取消后完成”能正确抑制并抹除最终响应。
- “先完成手取消”能保留合法响应并静默忽略迟到的取消信号。
- 进度通知可以重置空闲超时，但绝不能推迟绝对最大超时。
- 仅更换新的 JSON-RPC id 会导致无保护的写操作被二次执行。
- 在双连接并发竞态下，相同的幂等键与一致参数保证只执行一次。
- 已提交记录在关闭并重新打开后完好保存，且重放返回的是防御性副本。
- 篡改返回的对象无法破坏底层持久化存储的数据。
- 有界缓冲区在压力下严格控制在容量上限内，且绝不丢失最终响应。
- 重连机制发起新请求，不携带 `Last-Event-ID`，并全量重拉受影响状态。
- `tasks/cancel` 的确认回执使任务在 worker 检查点发现前保持非终态。

## 生产环境故障模式

| 故障现象 | 观察到的表象 | 正确处理方案 |
|---------|--------------------|------------------|
| HTTP 客户端 POST 发送取消通知 | 服务端与客户端对请求的生命周期产生分歧 | 直接关闭该请求专有的 SSE 响应流 |
| 服务端在接受取消后依然回传响应 | 客户端收到一份已无法使用的陈旧无用结果 | 当取消获胜时停止业务计算并抑制所有后续消息 |
| 进度通知无限重置所有超时时钟 | 挂起卡死的任务永久占用资源无法退出 | 维持一个独立的全局绝对最大超时硬上限 |
| 将新的 RPC id 当成请求去重依据 | 扣款、发布或删除操作被多次重复执行 | 在应用层引入并强制校验持久化幂等键 |
| 键检查与业务副作用彼此分离 | 并发执行的多个 worker 同时判定键不存在 | 将键占位、副作用记录与结果提交放入单次原子事务 |
| 在多副本集群中使用内存级账本 | 节点重启或换到另一台机器后遗忘了先前的提交 | 使用持久化共享存储或依赖上游系统的幂等支持 |
| 直接返回底层存储的可变对象引用 | 调用方的内存修改意外污染了后续重放结果 | 将提交结果序列化存储，返回时构造深拷贝副本 |
| 相同的键被复用于篡改后的参数 | 单个幂等键混淆了两种不同的业务意图 | 持久化记录并校验调用参数的哈希指纹 |
| 进度通知队列无界增长 | 遇到慢消费者时服务内存持续飙升直至 OOM | 在容量限制内对可替代的进度通知进行合并与淘汰 |
| 在高压下误丢弃了最终响应 | 客户端永远无法获知该请求的最终成败 | 预留专用容量或只淘汰进度通知，绝不丢弃最终响应 |
| 反向代理缓冲了 SSE 事件 | 进度事件呈突发性到达，或在全部执行完后才下发 | 禁用代理缓冲（`X-Accel-Buffering: no`）并调整代理超时 |
| 盲目假定支持 `Last-Event-ID` | 客户端尝试从服务端根本不支持的位点续传 | 使用新请求重连并向权威数据源全量拉取 |
| 所有客户端在断开后同一瞬间重连 | 系统恢复的瞬间引发严重的次生雪崩风暴 | 采用带上限保护、结合随机抖动的指数退避重连机制 |
| 将 Task 的确认回执当成已完成取消 | 前端界面显示已停止，而后台 worker 仍在计费运行 | 持续轮询 Task 状态直到其真正进入终态 |

## Capstone 串联

工具生态 Capstone 项目应当把系统可靠性视为可执行的代码凭据，而不是系统架构图里的两行文字。

Capstone 必须提供以下交付凭证：

- 针对每种传输协议的取消竞态执行日志；
- 针对所有暴露写操作的重试决策矩阵；
- 幂等键持久化记录以及参数不匹配时的拦截测试；
- 并发同键争夺记录、重启后持久性核验以及可变对象隔离测试；
- 有界缓冲区过载状态下的流控处理日志；
- 反向代理 SSE 标头配置与空闲保活策略说明；
- 标明了权威数据拉取接口的断线重连与全量恢复方案；
- 在引入 Tasks 扩展时，完整的持久化 Task 取消追踪链路。

在单个本地进程中的成功调用只能证明跑通了基本功能。只有当丢失响应、迟到取消、慢消费者以及重连风暴都能产生确定性、可预期的处理结果时，你的 Capstone 才真正具备生产就绪水平。

## 关键术语

| 术语 | 含义 |
|------|---------|
| 请求取消（Request cancellation） | 放弃单次处于在途状态的 MCP RPC 请求 |
| 取消竞态（Cancellation race） | 终态执行完成与取消信号抵达之间的时序争夺 |
| 空闲超时（Idle timeout） | 距离上一次产生有效请求活动的最大允许时间 |
| 最大超时（Maximum timeout） | 从请求开始时刻算起、不受进度通知影响的全局绝对时间上限 |
| 幂等键（Idempotency key） | 唯一标识单次特定业务意图的应用层去重标识符 |
| 原子账本（Atomic ledger） | 将键校验、副作用记录与结果提交绑定为不可分割单元的持久化存储 |
| 背压（Backpressure） | 在生产者生成速度超过消费者处理能力时施加的流量控制机制 |
| 进度合并（Progress coalescing） | 用更新的权威进度数值替换掉旧的进度更新 |
| 权威重拉（Refetch） | 在数据流中断或出现断层后，向权威接口重新读取当前全量状态 |
| 抖动（Jitter） | 在重试退避间隔中引入的随机偏移，用于在时间轴上打散瞬时并发高峰 |
