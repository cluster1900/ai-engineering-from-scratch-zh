# MCP Registry 供应链：准入、漂移与回滚

> Registry 条目只能说明发布者声明了什么。生产级准入控制则必须证明你拉取了什么、观察到了什么、批准了什么，以及你能安全恢复什么。

**Type:** Build
**Languages:** Python
**Prerequisites:** Phase 13 · 17 (gateways and registries), Phase 13 · 18 (production authentication)
**Time:** ~90 minutes

## 学习目标

- 明确切分 Registry 发布、软件包出处（provenance）、运行时发现与本地审批等不同边界。
- 在不信任 MCP 服务端记录自身声明的前提下，独立验证其命名空间。
- 对不可变发布记录、执行源、软件包出处以及实时工具描述符固定证据指纹（Pinning）。
- 在准入之后，实时检测 Registry 状态变更与运行时行为漂移。
- 在不重写历史记录的前提下，将路由安全回滚到先前已准入的版本。
- 维护一个防篡改的准入账本（Admission ledger），为每一项决策提供审计解释。

## 核心问题

你在 Registry 中找到了 `com.example/inventory`。它的描述看起来完全符合需求。它的软件包真实存在。该服务端也能正常响应 `server/discover`。

这并不是单一孤立的事实，而是一条由不同权威机构背书的事实链条：

1. 一位通过了该命名空间身份验证的发布者提交了一条记录。
2. 某个包注册中心分发了一个具备特定标识与哈希摘要的工件。
3. 一个实际运行的端点上报了协议版本、支持的能力、可用工具以及诊断服务端信息。
4. 你的组织判定这套确切的组合在策略上是合规且被允许运行的。

如果将这些层次混为一谈，简单认为“既然它在 Registry 里，就可以直接信任”，就会在供应链安全上留下巨大盲区。一个合法的发布版本随时可能被废弃（deprecated）。如果你没有固定工件摘要，软件包的 tag 可能在未来被替换为未预期的二进制内容。服务端可能在通过安全审查后擅自添加具有破坏性的工具。自动回滚时，系统可能会静默切到一个根本未经准入验证的未知版本。

解决之道是建立一个准入控制器（Admission Controller），在每一个边界处均强制采集并校验凭证。

## Registry 是索引，而不是你的审批系统

官方 MCP Registry 用于存储服务端元数据。其 `server.json` 记录声明了一个服务版本，并列出一个或多个软件包或远程端点。发布规则包含了命名空间认证、软件包所有权检查、受限注册源规则以及严格限定的发布者元数据存储位置。

这些控制措施回答的是**发布层面**的问题。但你的生产环境安全策略依然必须回答**部署层面**的问题：

| 边界 | 核心问题 | 证据所有者 |
|---|---|---|
| 命名空间 | 该发布者是否有权使用此名称？ | Registry 认证凭证 + 本地验证过的命名空间输入 |
| 发布记录 | 发布者针对该版本具体声明了什么？ | 不可变的 `server.json` 内容摘要 |
| 执行源 | 最终执行的是哪个软件包或远程端点？ | 已声明的源字段、已验证的所有权结果、传输协议以及可信内容摘要 |
| 运行时 | 该端点当前实际暴露了什么能力？ | 实时 `server/discover` 结果与工具描述符 |
| 准入决策 | 本地安全策略是否批准了这套确切的组合？ | 本地固定的指纹（Pin）与账本记录项 |
| 运维治理 | 当前服务是否依然安全？故障时何者可替代？ | 漂移检测、状态同步、健康检查与备用回滚路由 |

Registry Schema 版本与 MCP 协议版本是彼此独立的。一条记录可能采用已发布的 `2025-12-11` 服务端规范，而实际运行的服务端却支持 MCP `2026-07-28`。绝不能从其中一个版本去臆断另一个。

## 单次准入决策中的七重控制

### 1. 命名空间验证

官方 Registry 的命名采用经过身份认证的命名空间。一个经过验证的域名可以映射为反向域名格式的前缀。例如，拥有 `example.com` 的控制权可以确立 `com.example/*` 的合法性。

绝对不能使用简单的字符串前缀检查：

```python
server_name.startswith("com.example")
```

因为这种判断也会错误放行恶意仿冒的 `com.exampleevil/tool`！必须以 `/` 切分名称，要求包含非空的 slug 片段，并精确比对命名空间这一段。更重要的是，准入控制器接收的已验证命名空间必须来自于可信的鉴权结果输入，绝不能直接从不可信的发布记录本身提取信任。

基于 GitHub 组织的命名空间与基于域名的命名空间拥有不同的认证路径。准入控制器应当将这两种路径统一规范化为同一个输入参数：完全匹配且已验证的命名空间字符串。

### 2. 出处关联（Provenance Join）

对于软件包类型的记录，声明的数据必须与实际拉取的工件在以下显式字段上严格关联：

- 软件包注册中心类型（如 PyPI、npm）
- 软件包标识符
- 软件包版本号
- 已验证的所有权检查结果
- 实际下载工件的内容哈希摘要

同时还要校验声明的传输协议。如果某条记录仅声明了远程端点（remote endpoint），这也是完全合规的，绝不能因为缺少软件包就将其错误拒绝。对于远程源，需将声明的 URL 和传输类型与经过独立验证的端点所有权，以及可信连接或部署证据的哈希摘要进行关联。

本课示例代码同时支持这两种源类型，并将所选源与 Registry 源、服务端名称、Registry 版本、记录摘要以及凭证摘要共同计算出一个哈希。生成的出处摘要（provenance digest）是对完整证据链的紧凑指针，但它绝不能替代对完整原始证据的持久化留存。

绝不能直接接受由待验证工件自身所单方面提供的摘要。必须在可信的下载边界处重新计算摘要，或者从你已验证其校验结果的受信任包管理服务处接收。

### 3. 固定决策，而非仅固定版本

Registry 版本是唯一的发布标识符。已发布的元数据是不可变的。任何记录的修改都必须发布为一个全新的版本。虽然官方推荐使用语义化版本（SemVer），但 Registry 本身并不强制要求，也不接受类似版本范围的通配符。

这意味着类似 `^1.4` 的表达式并不是合法的准入 Pin，所谓的“latest”更不是。一个有效的准入固定指纹（Pin）应当包含：

```json
{
  "server": "com.example/inventory",
  "version": "1.0.0",
  "recordDigest": "...",
  "source": {"kind": "package", "registryType": "pypi"},
  "sourceDigest": "...",
  "toolsetDigest": "...",
  "provenanceDigest": "...",
  "registryStatus": "active"
}
```

对多个不同层次同时进行指纹固定，能让你在出现异常时迅速定位是哪个边界发生了突变：在同一个 Registry 版本下记录摘要改变，属于 Registry 数据完整性损坏；在同一个软件包坐标或远程部署下源摘要改变，属于执行源篡改；而工具集摘要（toolset digest）改变，则属于运行时行为漂移。

### 4. 实时运行时漂移检测

准入流程必须主动观测实际接收业务流量的服务端实例。通过受信任通道调用 `server/discover`，列出或获取其暴露的工具描述符，并验证：

- `supportedVersions` 中包含 `2026-07-28`；
- 本地策略要求的所有必要能力均已就绪；
- 每一个工具描述符都具备规范的身份标识与 Schema 定义表面；
- 规范化之后的描述符摘要在后续复检时与已准入的固定指纹完全一致。

结果中可选的 `_meta["io.modelcontextprotocol/serverInfo"]` 仅属于自述性质的展示、日志与排错上下文。可以将其作为诊断信息记录下来，但**绝不能**以此作为判断命名空间、软件包所有权、端点归属、准入许可或任何安全决策的依据。位于 `_meta` 外部的直接 `serverInfo` 别名更不属于官方契约字段，绝不可将其升级为合法的诊断证据。

只对那些顺序本身没有语义的字段进行规范化排序。本课示例在计算哈希前按照稳定的工具名称对工具列表进行排序，因此纯粹的返回顺序变化不会被误报为漂移。但它绝不会丢弃描述符内的任何字段。新增工具、修改 Schema、改动描述文本或引入新的注解，都会立即改变工具集摘要。

示例代码将任何格式错误的描述符或描述符摘要的变动均视作行为漂移，立即对该指纹进行隔离（quarantine）、撤销其活跃路由，并封锁将其作为回滚目标的资格。在生产环境中，哪怕是“微不足道”的描述改动也必须走全新的审批流程，因为大模型正是根据工具描述来决定是否调用该工具的——“表面上的文本修饰”足以从根本上改变 Agent 的执行行为。

### 5. Registry 状态是实时动态状态

Registry API 会在每个服务端记录旁边附加一个响应级别的 `_meta` 对象。由 Registry 官方托管的字段存放在 `_meta["io.modelcontextprotocol.registry/official"]` 路径下。准入控制器需解析该响应并读取 `_meta["io.modelcontextprotocol.registry/official"].status`。直接位于根节点的 `_meta.status` 并不符合官方线上传输格式。不要把外层响应元数据与记录内部自带的发布元数据混为一谈。状态可能包括：

- `active`：默认返回，具备本地准入候选资格；
- `deprecated`：已废弃，虽仍可被检索到但会附带告警，不再适合作为自动推荐选项；
- `deleted`：已删除，在默认列表中隐藏，但可通过针对已删除或增量视角的接口查看其历史档案。

准入完成后必须持续同步状态。一旦原本活跃的版本被标记为废弃或删除，应立即对其指纹进行隔离并停止将新流量路由给它。同时必须保留全部历史凭证——在上游默认列表中被删除，绝不意味着你可以在本地抹除审计追踪记录。

发布者自行提供的自定义元数据在发布记录中只能存放于 `_meta.io.modelcontextprotocol.registry/publisher-provided`。Registry 托管的响应元数据是完全独立的。绝不能允许发布者自行篡改其官方状态。

### 6. 回滚意味着路由恢复

不可变发布记录在回滚过程中绝不会被修改。所谓回滚，是在先前已经通过准入且当前依然符合条件的固定指纹中进行挑选，并切换活跃路由的目标。

一个安全的回滚目标必须同时满足：

1. 拥有完整且合法的准入记录；
2. 在当前本地策略下，其 Registry 状态依然保持为 active；
3. 未被任何运行时告警或安全凭证标记为隔离状态；
4. 依然能精确解析到已固定的软件包和线上描述符集合；
5. 通过当前最新的健康检查。

本课示例重点验证前三项条件。在真实的生产对账控制器中，在正式切流激活前，还应对软件包执行重新拉取校验并重新探活线上端点。

### 7. 追加准入账本

准入数据库只能说明“当前活跃的是什么”，而准入账本（Admission ledger）则记录了“为什么是它”。

本课账本中的每条记录项均包含序号、时间戳、事件类型、服务端标识、版本号、裁决结果、原因说明、证据集、前一项哈希以及本项哈希。篡改任何一条历史记录的判定结果，都会导致该记录及其后续所有链条的哈希校验彻底失效。

这是具备防篡改检测能力（tamper-evident）的机制，但并非魔法般不可破坏。应定期将账本最新哈希头（ledger heads）锚定到独立的信任域中，例如经过数字签名的发布元数据系统或单写多读（WORM）存储。对账本的追加权限实施严格访问控制。鉴权 Token、包管理私钥凭据、工具实际业务参数以及私有端点数据，都严禁写入审计证据中。

## 手写实现

可直接运行的控制器代码位于 `code/main.py` 中，全部基于 Python 标准库实现。

首先运行有限状态演示：

```bash
cd phases/13-tools-and-protocols/30-mcp-registry-supply-chain-and-drift
python3 code/main.py
```

该演示依次执行五项核心操作：

1. 准入 `1.0.0`，核验匹配的命名空间、包出处、协议版本、能力及工具集；
2. 准入 `1.1.0` 并将其切换为活跃路由；
3. 在运行时观测到一个未预期的删除工具；
4. 观测到 `1.1.0` 在 Registry 中的官方状态变为 `deprecated`；
5. 将路由平滑恢复到先前依然合规的 `1.0.0` 固定指纹。

预期输出结构：

```json
{
  "admitted": [true, true],
  "driftAllowed": false,
  "rollbackAllowed": true,
  "activeVersion": "1.0.0",
  "ledgerValid": true
}
```

建议按以下顺序研读实现代码：

1. `namespace_for_domain()` 与 `namespace_matches()`：建立精确的命名空间鉴权边界；
2. `digest()` 与 `normalized_tools()`：生成确定性的凭据摘要；
3. `RegistryAdmissionController.admit()`：聚合发布记录、出处凭据、运行时观测与本地策略；
4. `check_live()`：对比最新观测数据与已固定的指纹；
5. `observe_registry_status()`：对 Registry 状态发生变更的版本执行隔离；
6. `rollback()`：仅激活先前已准入且符合条件的合法回滚目标；
7. `AdmissionLedger.verify()`：精准检测对历史记录的任何篡改。

## 运行与使用

将准入控制器置于发现与路由之间：

```text
Registry sync -> artifact verifier -> live discovery -> admission controller -> route table
                                                |                 |
                                                v                 v
                                           evidence store    admission ledger
```

为上述各项任务分配互相隔离的最小权限身份：Registry 同步任务只需要元数据的只读权限；工件校验任务需要访问软件包的拉取权限；路由调和控制器则需要激活获批指纹的权限。没有任何一个组件需要掌握全部凭据。

明确划分版本的状态模型：“Approved”（已批准）意味着凭证通过了策略审查；“Active”（活跃）代表当前路由正在选用它；“Quarantined”（已隔离）表示禁止接收新业务请求；“Superseded”（已更替）说明另一个已准入的版本当前处于活跃状态。绝不能用单一的布尔值来混淆这四种截然不同的状态。

必须在向 `tools/list` 暴露某个服务端之前执行准入校验，否则客户端很可能在发布与安全策略评估的时间窗口缝隙中，意外发现并调用未受信任的工具。

## 交互式实验

你将亲手观察各个边界逐一失败的现场。

### 实验 A：命名空间冲突

进入代码目录并打开 Python 交互环境：

```bash
cd phases/13-tools-and-protocols/30-mcp-registry-supply-chain-and-drift/code
python3 -q
```

执行如下命令：

```python
from main import namespace_matches
namespace_matches("com.example/inventory", "com.example")
namespace_matches("com.exampleevil/inventory", "com.example")
```

第一个结果是 `True`；第二个结果是 `False`。在本地临时把精确片段比对换成 `startswith`，观察为什么第二个恶意名称会突破边界。在继续前，恢复精确比对逻辑。

### 实验 B：描述符漂移

```python
from main import *
times = iter(f"2026-08-21T12:00:{n:02d}+00:00" for n in range(10))
c = RegistryAdmissionController(clock=lambda: next(times))
meta = {OFFICIAL_META_KEY: {"status": "active"}}
c.admit(sample_record("1.0.0"), meta, "com.example", evidence_for("1.0.0"), sample_live("1.0.0"))
c.check_live("com.example/inventory", "1.0.0", sample_live("1.0.0", True))
```

检查返回的原因与路由状态。软件包与 Registry 记录丝毫未变，但由于运行时的工具表面发生了变化，控制器立即隔离并停用了该固定指纹。这正是为什么供应链安全管控必须贯穿到安装后的整个生命周期。

### 实验 C：状态与回滚

准入 `1.1.0`，将其标记为已废弃，并尝试分别回滚到这两个目标：

```python
c.admit(sample_record("1.1.0"), meta, "com.example", evidence_for("1.1.0"), sample_live("1.1.0"))
c.observe_registry_status("com.example/inventory", "1.1.0", "deprecated")
c.rollback("com.example/inventory", "1.1.0", "unsafe retry")
c.rollback("com.example/inventory", "1.0.0", "restore known release")
c.ledger.verify()
```

被隔离的目标会被明确拒绝，而先前合规的 `1.0.0` 指纹则顺利激活，账本哈希链始终保持有效。

## 动手实践

为控制器扩展双人审批门禁（Two-person approval gate）。

需求规范：

- 审批信息需作为经过数字签名的证据引用进行存储，不得作为可变字符串保存在指纹中；
- 当工具集中包含声明了 `destructiveHint: true` 的高危工具时，必须要求两个不同的审查员身份签名；
- 拒绝包含重复身份的审批；
- 当审批未凑齐时，依然在账本中完整记录本次准入尝试；
- 编写测试，分别覆盖 0 人、1 人、重复身份以及 2 个不同合法身份的审批场景；
- 日志中绝不得打印数字签名、凭证密钥或完整的私有工具参数。

验收标准：只要缺少两名独立审查员针对完全一致的记录摘要、软件包摘要与工具集摘要所签署的批准，破坏性工具就绝对无法进入活跃路由状态。


测试套件应当严格证明：

- 精确的命名空间边界能成功拦截形似前缀的恶意名称；
- 只有官方命名空间所附带的 Registry 状态才能决定版本是否具备候选资格；
- 未经校验或内容不匹配的软件包与远程端点凭据会被坚决拒绝；
- 发布者自述元数据绝无法冒充 Registry 官方托管元数据；
- 工具列表的排序进行了规范化，同时不会掩盖描述符的实质变动；
- 结构畸变的软件包与工具定义会触发安全失败；
- `serverInfo` 仅保留在诊断凭证中，绝不赋予其准入权威；
- 描述符发生漂移时，系统会立即执行隔离、撤销路由，并封锁对该指纹的回滚；
- 上游状态变更能驱动对活跃指纹的隔离；
- 回滚绝无法选定被隔离或未知的版本；
- 对账本历史记录的任何篡改都能被即刻检出。

## 生产环境故障模式

| 故障现象 | 发生原因 | 必须采取的应对措施 |
|---|---|---|
| 名称看似合法但命名空间从未经验证 | 准入策略轻信了记录内部的自述文本 | 严格拒绝，直到可信命名空间验证方提供精确前缀 |
| 相同软件包坐标拉取到了全新的二进制内容 | 上游版本被覆盖或分发源遭受投毒篡改 | 立即终止激活，保留两份摘要，调查拉取网络边界 |
| “latest”版本在未经人工审查的情况下发生漂移 | 浮动版本选择绕过了固定指纹机制 | 始终只解析和激活完全精确的已准入版本与摘要 |
| 安全审查通过后线上悄然出现新工具 | 发生了运行时行为漂移，或部署了不同镜像 | 隔离该路由，重新采集最新的实时描述符快照 |
| 已废弃的版本依然在线上持续运行 | 状态同步机制缺失或同步存在严重延迟 | 建立定时状态调和机制，并在每次路由激活前复核 |
| 已删除记录在默认同步中彻底消失 | 客户端只向 Registry 增量请求活跃记录 | 采用增量式或感知删除事件的调和机制，并在本地归档历史 |
| 回滚的目标版本根本从未通过准入审查 | 路由切换与准入审批状态彼此脱节 | 坚决拒绝回滚，强制对该目标走全新的准入流程 |
| 攻击者重写全部账本后本地依然校验通过 | 哈希链缺乏外部信任根的约束锚定 | 定期将带签名的账本头发布到独立的外部信任域 |
| 留存的凭据中泄露了 Bearer Token 或参数 | 日志和证据记录盲目复制了完整请求 | 在采集入口处执行脱敏，仅持久化留存最小必要凭据 |

## 运维守则

发布流程回答的是“该身份是否有权发布此名称？”而准入流程回答的是“我们是否确信要执行这个具体的工件，并向大模型暴露这一具体的行为？”务必将这两项裁决严格分开，对每一个关联点进行指纹固定，让回滚成为依据可验证证据做出的工程动作，而非依赖人脑记忆的侥幸尝试。
