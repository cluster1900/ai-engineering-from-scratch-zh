# MCP 一致性工程：版本控制、证据与运维

> 服务端不能因为正常路径在某个 SDK 中碰巧跑通就自称一致合规。真正的一致性体现在原始线路上、版本边界间、穿透中间代理时，以及面临回滚的时刻。

**Type:** Build
**Languages:** Python
**Prerequisites:** Phase 13 · 09 (transports), Phase 13 · 17 (gateways), Phase 13 · 30 (registry admission)
**Time:** ~100 minutes

## 学习目标

- 将规范性的 MCP 协议规则转化为黄金记录（golden）与负面拒绝（negative）交互语料库。
- 将严格的 `2026-07-28` 行为与受约束的旧版回退（legacy fallback）机制清晰隔离。
- 精确区分附加性未知字段与非法的未知 `resultType`。
- 将原始 JSON-RPC 证据与经过 SDK 规范化后的视图进行差异比对。
- 在真实的代理层边界上，检验 HTTP 标头与请求体的一致性及完整性。
- 通过脱敏后的交互记录、健康指标与回滚凭据来构建发布门禁。

## 核心问题

你的客户端通过 SDK 成功调用了 `tools/list` 并拿到了工具列表。集成测试通过了。

但这留下了很多关键问题未能得到解答：

- 请求报文中是否真正携带了现代按请求隔离的协议元数据？
- `MCP-Protocol-Version`、`Mcp-Method` 和 `Mcp-Name` 是否与 JSON-RPC 请求体完全一致？
- 响应报文在线路上是否包含合法的 `resultType`，还是由 SDK 私自推断补全的？
- 客户端能否无损保留未来的前向附加字段？
- 收到已识别的现代协议错误代码时，会不会误触发对旧版握手流程的降级？
- 中间代理是否完整透传了源站的 HTTP 状态码与 JSON-RPC 错误详情？
- 针对单向 Notification 的序列化器是否违规发出了响应报文？
- 运维团队能否在不泄露凭证密钥的前提下，证明某个版本为何被放行晋级或为何被执行回滚？

协议一致性是一组可被客观观测的不变量。必须在生产环境真实流量踩坑之前，构建一套能够捕获这些不变量的自动化测试工具链。

```figure
mcp-conformance-operations
```

## 从版本纪元（Version Eras）开始

MCP `2026-07-28` 规范采用了完全自包含的“按请求元数据”（per-request metadata）。一个现代请求会携带 `params._meta.io.modelcontextprotocol/protocolVersion` 和 `params._meta.io.modelcontextprotocol/clientCapabilities`。这里的精确命名空间键名至关重要；简写的 `protocolVersion` 或 `clientCapabilities` 裸键均属于格式畸变。当 HTTP 边界存在镜像路由标头时，其数值必须与 JSON-RPC 请求体严格一致。现代规范下所有成功的响应结果都必须携带 `resultType`。

而截至 `2025-11-25` 的旧版本则采用早期的连接初始化纪元（Initialization era）。在此纪元下，缺少 `resultType` 的旧版结果只有在客户端明确协商并选定了该旧版纪元后，才会被解释为 complete。

绝不要编写一个同时宽容接受两种格式的“万能宽松校验器”。必须严格划分为两个独立分支：

| 分支 | 准入凭证 | 缺少 `resultType` 的处理 | 初始化握手 |
|---|---|---|---|
| 现代纪元（Modern） | 成功的 `server/discover` 或已识别的现代响应 | 判定为非法（Invalid） | 不再作为默认建立连接路径 |
| 旧版纪元（Legacy） | 现代探测无果后，目标命中白名单且返回合法的旧版 `initialize` 响应 | 解释为 complete | 该纪元所必需的强制步骤 |

这种严格隔离杜绝了格式错误的现代节点因校验宽松而侥幸通过测试的隐患。

### 严格模式

严格模式（Strict mode）要求对端必须展现出现代协议行为的直接证据。一次成功的 `server/discover` 即可确立现代分支。收到一个已识别的现代 JSON-RPC 错误（如 `-32020`、`-32021` 或 `-32022`）同样能确立现代分支——此时应当修正请求或终止流程，**绝不能**降级回退到旧版协议。

### 回退模式

回退模式（Fallback mode）允许执行一次有边界约束的现代探测。如果遇到超时、空响应、连接中断或无法识别的响应，这些均属于“无结论”（Inconclusive），它们不能直接证明对端就是旧版节点。只有那些在配置中显式允许或位于白名单内的端点，才可以随后接收一次受限的旧版探测；且客户端只有在该旧版探测的 `initialize` 结果及协商版本通过验证后，才能正式切换到旧版分支。

回退绝不等于“一旦报错就尝试旧版”。一个已识别的现代错误本身包含了极具价值的纠错上下文。在收到此类错误后盲目降级，只会掩盖标头不匹配、缺少能力声明或协议版本不兼容等真正的配置缺陷。

这种设计能防止攻击者、网络故障或过滤代理通过故意丢弃现代响应来强迫系统降级。请务必将端点策略、无结论的现代观测、确凿的旧版正向凭据以及最终选定的版本纪元一并记录存档。

在每份交互记录旁边必须明确标注所选定的纪元。若脱离了纪元上下文，某个缺失的字段在一轮测试中看似合法，在另一轮测试中就会被判定为致命违规。

## 构建交互记录语料库（Transcript Corpus）

一份规范的交互记录夹具（fixture）记录的是实际穿透边界的真实报文，而不仅是 SDK 层的调用：

```json
{
  "name": "golden-modern-list",
  "era": "modern",
  "headers": {
    "MCP-Protocol-Version": "2026-07-28",
    "Mcp-Method": "tools/list"
  },
  "request": {
    "jsonrpc": "2.0",
    "id": 1,
    "method": "tools/list",
    "params": {
      "_meta": {
        "io.modelcontextprotocol/protocolVersion": "2026-07-28",
        "io.modelcontextprotocol/clientCapabilities": {}
      }
    }
  },
  "responseStatus": 200,
  "responseBody": {
    "jsonrpc": "2.0",
    "id": 1,
    "result": {
      "resultType": "complete",
      "tools": []
    }
  }
}
```

测试语料库应当维护两大类记录：

### 黄金记录（Golden Transcripts）

黄金记录用于证明合规行为被正确接受：

- 携带匹配元数据与标头的现代发现或方法请求；
- 携带必需字段的完整结果（`complete`）；
- 当方法需要进一步交互时的 `input_required` 结果；
- 只有在事先声明了对应能力后才允许返回的扩展结果；
- 在明确选定的旧版纪元中，省略 `resultType` 的旧版结果；
- 不返回任何 JSON-RPC 响应的 Notification 处理过程。

黄金记录必须精准且紧凑。对易变的 ID 和时间戳采用确定性生成策略，或在比对前进行规范化剥离。

### 负面记录（Negative Transcripts）

负面记录用于证明违规行为被坚决拒绝：

- 标头与请求体不一致；
- 缺少针对每次请求的能力声明；
- 协商版本不受支持；
- 现代请求下缺失 `resultType`；
- 未知或未经通告的 `resultType`；
- 响应中的 `jsonrpc` 不为 `2.0`，或返回的 ID 在数值或 JSON 类型上不一致；
- 同时包含 `result` 和 `error`，或两者皆缺失的畸变响应；
- 缺少整数 `code` 或字符串 `message` 的错误对象；
- 将已知协议错误映射为错误的 HTTP 状态码；
- 为 Notification 错误发送了响应；
- 畸变的 JSON-RPC 信封格式；
- 中间代理对协议错误发生的“崩塌吞没”（Collapse）。

针对每一个负面用例，必须断言其拒绝的精确边界与稳定的错误代码。“调用失败了”是远远不够的。代理自作主张生成的 500 与源站规范返回的 `-32020`，在表象上都可以叫做失败，但它们传递给运维人员的信息完全不可同日而语。

标头不匹配的测试夹具必须强制断言服务端实际返回了 HTTP 400，并带有匹配的请求 ID 与错误码 `-32020`。每当本地校验器观察到 `HeaderMismatch` 时，必须强制执行该断言，而不能将其作为可选标记。如果因为返回了无请求体的 HTTP 500 而终止，即便本地判定的拒绝码正确，也是测试失败。一个在自身请求校验报错后就戛然而止的测试套件，测出的只是它自己，根本没有触及服务端真实的线上通信行为。

官方 MCP 一致性测试套件是一份宝贵的外部标准与版本参照。但务必在本地维护属于你自己的交互记录集，因为通用的公共测试集无法覆盖你的特定代理、特定 SDK、特定鉴权流水线以及生产发布路径。

## 标头值必须与 RPC 请求体匹配

在现代 Streamable HTTP 协议下，中间代理可以借助镜像标头实施路由或执行安全策略。但 JSON-RPC 请求体始终是协议层唯一的“真理之源”。标头与请求体不一致属于严重的数据完整性损坏，绝不能被当作“在两者中二选一”的宽松提示。

必须按照如下严格顺序执行校验：

1. 解析并校验 JSON-RPC 信封及元数据字段的类型；
2. 比对 `MCP-Protocol-Version` 与 `params._meta.io.modelcontextprotocol/protocolVersion`；
3. 比对 `Mcp-Method` 与 `method`；
4. 当该方法具备特定路由名称时，比对 `Mcp-Name` 与请求体中的对应字段；
5. 在确立完全一致之后，再判定匹配的协议版本与能力集是否受支持。

这个先后顺序将标头不匹配错误 `-32020` 与协议版本不支持错误 `-32022` 清晰区分开来。它也能从根本上防止“网关校验并批准了标头中的安全工具，而源站实际执行了请求体中恶意工具”的欺骗攻击。

HTTP 字段名不区分大小写，但其字段值严格区分大小写。在查找前规范化标头名称，并拒绝存在冲突的重复标头。对于包含不安全字符、非 ASCII 或带有首尾空白的 `Mcp-Name`，必须先精确还原其 `=?base64?{Base64EncodedValue}?=` UTF-8 哨兵编码，再与请求体比对。未完成的哨兵、无效 Base64、非法 UTF-8 或未编码的不安全字符，一律以 `-32020` 拒绝。未编码的原始首尾空白即便是与请求体字符完全相同也属于非法，因为传输规范强制要求此类取值在传输前必须经过哨兵编码。

中间代理可能在请求抵达 MCP 服务端之前就直接拒绝畸变的 HTTP 报文，因此其报错可能是不包含 JSON-RPC 的纯 HTTP 错误。必须如实记录该拒绝究竟来自中间代理还是源站。源站 MCP 服务端在处理有效的 JSON-RPC 请求时，应当严格遵循协议错误契约。

## 未知字段不等于未知结果

实现向后兼容需要遵循两条截然不同的准则：

### 附加未知字段

结果对象（Result objects）与 `_meta` 映射表中随时可能增加新的字段。校验器应当根据自身的职责定位，选择无损透传保留或安全忽略这些附加字段，除非该字段直接违背了保留关键字的契约。在示例代码中，测试套件会在证据中保留完整的原始响应，并在已知结果旁边宽容接受类似 `futureHint` 的附加字段。

如果你是一个透明代理，保留未知字段通常远比盲目剔除它更为安全；如果你是终端应用客户端，忽略它则是合法的。但无论如何，差异测试套件都应当精准揭示出 SDK 是否在反序列化时丢弃了该字段，确保这一行为是深思熟虑的工程决策，而非意外疏漏。

### 未知 `resultType`

`resultType` 属于核心生命周期判别器（Discriminator）。现代核心协议定义的结果类型仅有 `complete` 与 `input_required`。扩展协议只有在其对应能力预先声明并协商成功后，才允许引入新的取值（例如 Tasks 扩展在协商对应能力后可以返回 `task`）。

对于未知的、或未经声明宣告的结果判别器，绝不能自作主张将其当成 `complete` 来宽容处理。因为客户端根本无法理解自己所盲目丢弃的究竟是何种生命周期状态！必须坚决报错拒绝。

同一份原始响应报文中，完全可能同时包含“合法的未知扩展字段”与“致命的非法未知结果类型”。测试用例必须对这两种场景分别进行严格覆盖。

判别器只是校验的第一道门槛，之后还必须根据具体方法校验其专属载荷。`tools/list` 的 complete 结果必须包含 `tools` 数组，且其描述符具备非空的唯一名称、明确描述以及 object 根节点的 `inputSchema`；`task` 结果仅在具备 Tasks 能力的合法 `tools/call` 中有效，且强制要求包含 `taskId`、已知状态、创建与更新时间戳、`ttlMs` 以及合法的轮询间隔；`completion/complete` 的 complete 结果必须包含不超过 100 个字符串的 `completion` 对象，以及可选的非负整数 `total` 和可选布尔值 `hasMore`。拼写正确的 `resultType` 绝不能为格式残缺的载荷提供豁免。

## Notification 的单向性不变量

JSON-RPC Notification 消息没有 `id`。接收方**绝不能**向外发送任何 JSON-RPC success 或 error 响应报文。

对于在 HTTP 上成功接收的 Notification，测试套件预期服务端返回一个带有空请求体的 HTTP `202 Accepted`。MCP `2026-07-28` 规范并未在 Streamable HTTP 上定义核心的客户端到服务端 Notification。本课示例仅使用了一个带有命名空间的课程扩展通知，专门用于验证传输层序列化器是否满足“绝不返回任何 JSON-RPC 报文”的不变量。请勿将其误当成新的核心协议方法。

测试时必须覆盖最外层的序列化器，而不能仅测试处理函数本身。因为很可能处理函数内部返回了 `None`，但外层中间件却自动将其包装成了包含 `{result: null}` 的 JSON 成功响应。必须直接抓取并检验最终流出网络边界的原始字节。

## 引入 SDK 差异对比（SDK Differential）

各类 SDK 通常会将底层的线路对象包装转换为高级语言内置的便捷数据类型。这提升了开发体验，但也导致规范化之后的对象无法还原网络线路上真实收发了什么。

针对每个高风险测试用例，必须同时捕获四层视图：

1. SDK 解码前的原始 HTTP 状态码、响应标头与响应体；
2. SDK 规范化转换后输出的返回值对象或异常实例；
3. 针对当前选定版本纪元的预期语义映射投影；
4. 被 SDK 提升、无中生有合成、强行剥离或篡改的字段清单。

示例代码允许 SDK 仅剥离已知的线路协议记账字段（如 `resultType`、`_meta`、`ttlMs` 和 `cacheScope`），同时对比底层的业务载荷。但如果 SDK 擅自丢弃了未知的语义字段 `futureHint`，测试套件会将其作为差异告警明确上报。

不要简单假设每一处差异都是 SDK 的 Bug。核心目标在于让这类隐式转换完全显形。明确你的组件定位究竟是一个允许忽略附加字段的应用端点，还是一个必须忠实保留字段的透明代理。

在发布前，针对你所维护的每一个 SDK 及其目标版本均需运行差异测试。如果两个不同的 SDK 对完全相同的交互记录产生了不同的规范化输出，发布策略必须明确裁决哪种行为是规范合法的，绝不能事后和稀泥。

## 捕获代理层证据

生产环境中绝大多数 MCP 故障都发生在跨进程或穿透代理的网络边界上。必须同时记录三重视角：

| 视角 | 最小必要凭据 |
|---|---|
| 入口（Ingress） | 客户端原始请求头、JSON-RPC 请求体、Content-Type、已认证路由、接收时间戳 |
| 源站（Origin） | 代理转发出的标头与请求体哈希、源站 HTTP 状态、源站响应头与响应体 |
| 出口（Egress） | 客户端最终可见的 HTTP 状态、响应头、最终响应体、发送时间戳 |

示例代码专门针对两种最常见的代理篡改行为建立了检测能力：

- 源站原本规范返回的 HTTP 400 或 404 JSON-RPC 协议错误，被中间代理简单粗暴地转换成了通用的 HTTP 500；
- 最终送达客户端的出口 JSON-RPC 请求体与源站返回的内容存在实质性变异。

根据实际部署架构，还可扩充针对 Content-Type、`Accept`、传输压缩、针对单请求的 SSE、缓存标头以及分布式链路追踪追踪上下文的断言。在合规允许的前提下，捕获 TLS 终结前后的两重视角。但请谨记：绝不能为了证明链路完整而打印鉴权密钥凭证。

## 证据离开内存前进行脱敏

脱敏属于一致性运维体系的内建核心步骤，而不是事后打补丁的扫尾工作。在将凭据序列化、计算哈希、写入日志、归档测试工件或上传排错报告之前，必须在内存中完成脱敏。

示例代码在执行匹配前先将键名统一转为小写并剔除所有连接符，然后递归清除诸如 `Authorization`、`Cookie`、`Set-Cookie`、`X-Api-Key`、`accessToken`、`clientSecret`、`registrationAccessToken`、`token`、`password`、`secret` 以及 `api_key` 等敏感字段的取值。规范化比对逻辑与黑名单字典必须统一，防止小驼峰、中划线、下划线及点号等不同命名风格互相绕过。在生产环境中还应补充针对特定方法参数的脱敏策略，因为即使像 `query` 这样看似无害的键名，也可能包含个人隐私或合规监管数据。

计算哈希时基于已脱敏的证据捆绑包进行计算。原始未脱敏的抓包数据只有在特定事故调查中，由获批人员在生命周期极短的受限系统中临时调阅。证据摘要能够确凿证明是由哪一份经过脱敏的凭据支撑了本次发布裁决，同时绝不会泄露被抹除的敏感明文。

## 将健康检查与回滚纳入发布门禁

协议层的一致合规是发布的必要条件，但绝非充分条件。一个完全符合协议规范的候选版本，在线上依然可能发生超时、内存泄漏或压垮下游依赖。

在正式放行流量前，必须定义清晰的健康观察窗口：

- 最小请求样本容量；
- 最大允许错误率阈值；
- 延迟分位数（P95/P99）上限；
- 资源饱和度与算力限制；
- 持续观测的时间跨度；
- 与基线基准指标的横向对比。

同样，回滚凭证也必须在上线前预先就绪：

- 精确的前序版本标识；
- 先前的准入凭据哈希摘要；
- 对应的 SHA-256 工件与描述符固定指纹；
- 当前最新的 Registry 官方状态；
- 当前最新的健康检查评估报告；
- 经过演练的路由恢复标准作业程序；
- 由可信发布控制器身份针对上述全量字段签署的认证凭证（Attestation）。

强制要求该回滚目标在候选版本被批准前就必须处于健康且已验证的状态，而不是等到候选版本在线上炸锅后才临时手忙脚乱地寻找出路。一个没有可靠后退之路的成功上线，在工程上是不合格的。

若候选版本发生故障，而当前指定的回滚目标又缺乏完整的准入凭据支持，系统应果断选择拦截停常（Hold），绝不能靠“凭感觉回滚到看起来正常的版本”来碰运气。

绝不要将就绪检查降级为非空字符串判断、`healthy: "yes"` 或随意的状态标记。示例代码严格要求匹配确切的类型、活跃的状态、三个关键 SHA-256 摘要、可信的签名主体，以及基于完整载荷计算出的合法 HMAC-SHA-256 签名。示例中确定性的密钥属于非机密的测试夹具；在生产环境中，应在发布边界处注入受严格保护的密钥、KMS 验签结果或非对称公钥认证服务。

发布门禁还会坚决拒绝内容为空的交互记录、SDK 差异凭证或代理层证据。每个证据源都必须提供有效的摘要指针。一段看似全绿的健康曲线，绝不能用来掩盖某个从未真正被测试过的系统边界。

## 手写实现

运行基于标准库实现的一致性工程框架：

```bash
cd phases/13-tools-and-protocols/31-mcp-conformance-versioning-and-operations
python3 code/main.py
```

演示程序会运行整整 15 组黄金与负面交互记录（包括合规与畸变的自动补全用例）、比对原始数据与 SDK 视图的差异、检查一个篡改了源站错误码的中间代理、评估健康窗口指标、验证回滚凭证的数字签名，并最终选择安全的回滚目标。

预期输出结构：

```json
{
  "transcriptsPassed": 15,
  "transcriptsTotal": 15,
  "sdkDroppedFields": ["futureHint"],
  "proxyIssues": [
    "proxy collapsed a protocol error into HTTP 500",
    "proxy changed the origin JSON-RPC body"
  ],
  "releaseAction": "rollback",
  "evidenceDigest": "..."
}
```

建议按以下顺序阅读 `code/main.py` 的源码实现：

1. `validate_request()`：强制执行特定版本纪元的请求与标头一致性规则；
2. `validate_result()`：精确切分旧版缺失判别器、现代合法取值、扩展类型及未知类型；
3. `select_era()`：实现严格模式与受约束的回退策略；
4. `run_transcript()`：评估黄金记录与负面拒绝夹具；
5. `compare_sdk_view()`：揭示 SDK 规范化过程中的字段差异；
6. `inspect_proxy()`：全链路对比入口、源站与出口三重視角凭据；
7. `redact()`：在生成证据摘要前彻底清除明显的敏感机密；
8. `rollback_evidence_ready()`：校验回滚指纹的精确字段与可信发布签名；
9. `ReleaseGate.evaluate()`：聚合一致性、SDK、代理、健康与回滚等全部非空凭据做出终审裁决。

## 运行与使用

在软件研发交付的四个关键节点运行该一致性测试流水线：

1. 每次代码改动时，通过进程内测试适配器快速运行；
2. 针对构建出的客户端与服务端二进制产物，在真实物理传输层上运行；
3. 在预发布（Staging）环境中，穿透实际部署的反向代理或网关运行；
4. 在金丝雀灰度（Canary）发布期间，结合实时健康指标与回滚凭据动态运行。

在所有测试层级中保持全局一致的用例标识名。`negative-header-body-mismatch` 在单元测试、端到端测试、代理测试及金丝雀报告中必须严格代表同一个不变量。虽然各层边界不同会导致证据摘要改变，但底层的不变量约束标准绝不漂移。

将测试夹具 Schema 纳入版本控制（Git）。将脱敏后的运行凭证保存在发布管理系统中。未经脱敏的短期原始抓包，仅限在发生故障且获得专门审批时方可临时调阅。

## 交互式实验

### 实验 A：验证版本纪元边界

进入 `code` 目录并启动 Python：

```bash
cd phases/13-tools-and-protocols/31-mcp-conformance-versioning-and-operations/code
python3 -q
```

运行如下代码：

```python
from main import *
validate_result({"tools": []}, "legacy")
validate_result({"tools": []}, "modern")
```

旧版纪元会将其正确推断为 `complete`，而现代纪元则会直接抛出 `ProtocolViolation` 异常。接下来测试回退逻辑：

```python
select_era({"kind": "timeout"}, "fallback")
select_era(
    {"kind": "timeout"},
    "fallback",
    legacy_allowed=True,
    legacy_evidence={"kind": "initialize_success", "protocolVersion": LEGACY_VERSION},
)
select_era({"kind": "jsonrpc_error", "code": -32021}, "fallback")
```

第一次超时会安全失败，因为对端的沉默绝不构成旧版协议的合法证据。第二次调用成功选定旧版，是因为配置显式开放了权限且观测到了合法的旧版握手凭据。而第三次收到的缺失能力错误，则直接将系统锁定在现代分支。

### 实验 B：附加字段与判别器对比

```python
validate_result({"resultType": "complete", "tools": [], "futureHint": True}, "modern")
validate_result({"resultType": "future_mode", "tools": []}, "modern")
```

第一条结果完整保留了 `futureHint` 扩展字段；第二条结果则被坚决拦截，因为其生命周期判别器完全未知。

### 实验 C：检查 SDK 转换

```python
compare_sdk_view(
    {"resultType": "complete", "tools": [], "futureHint": {"mode": "new"}},
    {"tools": []},
)
```

结合你的组件定位评估：当前系统是否允许丢弃 `futureHint`，还是必须强制向外透传？将这一工程决策明确写入团队的发布规范中，绝不可听任差异被静默抹杀。

### 实验 D：修复代理层问题

调整演示程序中的交互报文，使得出口处能够忠实透传源站的原生状态与请求体。重新执行 `python3 main.py`。代理告警随即消除，但由于 SDK 依然丢弃了字段，放行依然被拦截。随后在 SDK 视图中补齐对 `futureHint` 的保留，当所有维度的证据全部校验通过后，观察发布动作平滑切换为 `promote`（放行）。

## 动手实践

为测试工具链扩充针对请求级 SSE 流的交互测试用例。

需求规范：

- 捕获 HTTP 响应状态码、Content-Type、有序的 SSE 事件序列以及连接终止信号；
- 证明每个通过 SSE 发出的 JSON-RPC 事件均具备与其版本纪元相符的结果或错误信封；
- 编写负面测试用例：模拟某个中间代理在完整缓冲了全部事件流后才一次性转发的违规行为；
- 编写负面测试用例：捕获某个 SSE 事件中的 JSON-RPC id 与最初发起的请求 id 不匹配的故障；
- 在将事件持久化为证据前执行全量脱敏；
- 将事件流持续时长、首事件到达延迟（TTFT）以及总事件数纳入健康评估观察窗口；
- 确保当事件流发生异常时，发布门禁仅选择证据完备的合法回滚目标。

验收标准：同一个用例能够直接运行并穿透代理运行，且生成的评测报告能精确定位是哪一跳网络边界引发了行为异变。

## 验证标准

运行演示程序与全套确定性测试套件：

```bash
cd phases/13-tools-and-protocols/31-mcp-conformance-versioning-and-operations
python3 code/main.py
python3 -m unittest discover -s code/tests -v
```

测试应当严格证明：

- 所包含的全部 15 组黄金与负面记录均达到预期判定结果；
- 现代请求强制要求使用带精确命名空间的元数据键；
- HTTP 标头名称比对不区分大小写，且编码后的 `Mcp-Name` 值被无损精准还原；
- 标头与请求体不一致时准确返回现代错误码 `-32020`；
- 响应版本、ID 一致性、结果与错误的互斥性、错误对象结构以及 HTTP 映射均通过严格校验；
- 强制执行针对 `tools/list`、Tasks 扩展以及补全方法的专属载荷规范；
- 只要出现 `HeaderMismatch`，就必须实际捕获到 HTTP 400 与 JSON-RPC `-32020` 响应；
- 未编码的原始 `Mcp-Name` 首尾空白被拒绝，而使用哨兵编码的空白字符能精准往返还原；
- 缺失 `resultType` 仅在明确选定的旧版纪元中被视作合法；
- 附加未知字段能够安全保留，而未知的生命周期结果类型则会被坚决拒绝；
- 扩展结果类型必须在预先通告对应能力的前提下才被允许；
- 收到已识别的现代协议错误绝不触发向旧版协议的降级回退；
- Notification 绝不产生任何形式的 JSON-RPC 响应；
- 清晰辨识出 SDK 对协议记账字段的正常剔除与对业务语义字段的意外丢失；
- 精准检出代理层对错误码的吞没篡改，且在小驼峰与带连接符等多种风格变体下均能递归脱敏凭据；
- 晋级放行必须同时具备非空的交互记录、SDK 差异、代理审计以及处于健康区间的运维凭据；
- 无论是放行还是回滚，均强制要求存在一个经过签名认证、指纹固定、处于活跃状态且指标健康的回滚目标。

## 生产环境故障模式

| 故障现象 | 浅层粗糙测试的假象报告 | 测试工具链必须证明的实质 |
|---|---|---|
| SDK 擅自补全了缺失的判别器 | “tools/list 运行通过” | 原始线路上缺失现代 `resultType`，属于非法响应 |
| 收到 `-32021` 后客户端自行降级 | “旧版重试成功” | 收到已识别的现代错误绝不允许降级回退 |
| 未知结果类型被当成 complete | “响应成功解析” | 未经能力通告的生命周期判别器必须被坚决拒绝 |
| 代理批准了 A 工具而源站执行了 B 工具 | “请求成功抵达服务端” | 确保每一跳的 `Mcp-Name` 均与请求体中的路由名称严格一致 |
| 测试在读取服务端响应前自行报错终止 | “标头不匹配测试通过” | 必须真实捕获并验证 HTTP 400 及 JSON-RPC `-32020` 响应体 |
| 代理将源站 400 转换为通用的 500 | “上游服务端报错” | 源站与出口两端的 HTTP 状态及错误体必须原样保留 |
| Notification 中间件强行输出 `{result: null}` | “处理函数正常返回了 None” | 最终网络出口的请求体必须为空，且不存在任何 JSON-RPC 报文 |
| SDK 擅自剥离了前向附加字段 | “强类型对象转换一致” | 原始视图与规范化视图清晰指出具体哪一个字段被丢弃 |
| 事故排查工件泄露了 Bearer Token | “已成功上传调试数据包” | 在计算哈希、写入日志或上传网络之前已彻底完成脱敏 |
| 命名风格变体绕过了脱敏拦截 | “黑名单中已包含 api_key” | 小驼峰、中划线等所有变体在脱敏前均统一规范化为规范形式 |
| 金丝雀发布在毫无流量时显示指标全绿 | “零错误率” | 强制校验最小请求样本容量门槛 |
| 故障回滚切到了一个未经测试的未知构建 | “已恢复先前部署” | 回滚目标、准入摘要、固定指纹、状态与健康凭据必须全部完备 |

## 运维守则

去测试你发出的每一个真实字节，测试每一台中间代理所转发的真实字节，测试每个 SDK 所对外呈现的具体语义，以及运维团队在紧急高压下所必须依赖的诊断证据。协议兼容性必须是一条经过深思熟虑的显式分支，而版本回滚更是一项由严密证据支撑的工程发布决策。两者都绝不能成为某个宽松解析器所带来的偶然副作用。
