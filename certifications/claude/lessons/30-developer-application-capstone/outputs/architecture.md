# 订单状态 Assistant 架构记录

## 决策

使用一个有界的 Claude 辅助工作流，其中包含一个只读的进程内 Tool、确定性策略、严格的输出验证和明确的升级处理。

## Context

用户需要根据准确的公开订单 ID 获取经过验证的订单状态。路径是已知的，而虚构操作的代价很高。目前由一个 Application 拥有该能力。

## 组件

1. 输入 validator 提取公开 ID 格式。
2. 信任边界将用户内容和检索内容标记为不可信。
3. Claude 可以通过类型化 Tool 契约提议调用 `lookup_order`。
4. 策略门禁仅允许包含一个参数的只读调用。
5. 可信集成代码绑定经过身份验证的用户和 tenant 身份。
6. 订单服务返回最小化的已验证状态。
7. Claude 生成结构化最终响应。
8. Application 验证 schema、证据、路由状态和 trace。

## 决策与权衡

### 选择工作流而不是自主 Agent

执行顺序是已知的。通用 Agent 会增加 Tool 选择和循环风险，却无法改善核心用户结果。

### 选择直接 Tool 而不是 MCP

一个 Host 使用一种能力。直接的类型化 handler 具有更少的运维边界。当两个或更多经过批准的 Host 需要共享发现和治理时，再迁移到 MCP。

### 只读自动能力

通过 schema 和策略检查后，可以自动执行查询。退款、取消、地址变更和外部消息需要独立 Tools、外部审批、幂等性和新的 eval。

### Structured output 加本地验证

Provider 约束生成可以减少语法错误。本地 schema、语义和授权检查仍然是强制要求。

### 默认不使用 extended thinking

该工作流是直接查询。采用额外思考预算之前，必须证明它能带来可衡量的质量提升。

## 被拒绝的替代方案

- 自由格式的 shell 或数据库 Tool：权限过大且难以验证。
- 一个宽泛的 `manage_order` Tool：混合了读取和修改权限。
- 将对话文本作为审批依据：未经过身份验证，并且容易受到注入攻击。
- 无限重试：会造成成本和副作用状态不明确。
- 在首个版本中使用 MCP：互操作性收益尚不足以证明 Server 运维的合理性。

## 安全边界

- 凭据保留在可信集成代码中。
- Model 参数绝不用于确立身份或 tenant。
- 不可信内容不能授予能力。
- 未知 Tools 和参数字段应按失败关闭原则处理。
- Tool 结果在进入 Model Context 前会被最小化。
- Trace 包含类型化摘要、版本和 fingerprint，而不是机密信息。

## 验证

- 单元测试覆盖验证、策略、Tool 行为、契约结构和升级处理。
- 行为 eval 覆盖已知订单、未知订单、缺少输入和注入用例。
- 生产部署必须增加 live API 序列化测试、经过身份验证的所有权检查、速率限制处理和 canary Evaluation。

## 产品细节说明

在实现和升级期间，必须根据当前官方文档检查 Model ID、SDK 方法、structured-output 字段、stop reason 和配置界面。
