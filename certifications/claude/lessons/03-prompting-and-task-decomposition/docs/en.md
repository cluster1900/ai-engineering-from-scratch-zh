# 将请求转化为可测试的契约

> 强大的 prompt 不只是描述要写什么，还会在生成开始前让成功标准变得可观察。

**Type:** Learn
**Languages:** Python
**Prerequisites:** [研究决策，而非词汇](../../00-certification-strategy/), [Prompt Engineering](../../../../../phases/11-llm-engineering/01-prompt-engineering/)
**Time:** ~100 分钟

## 学习目标

- 将模糊请求转化为结果、证据标准、约束和验收检查。
- 将复杂工作拆解为可以独立检查和纠正的阶段。
- 在直接 prompting、示例、结构化章节、迭代和工作流重新设计之间进行选择。
- 诊断 prompt 故障，而不把每个不良输出都视为模型故障。
- 为高价值 Claude 工作流构建可复用的 prompt packet。

## 问题

一位运营经理要求 Claude“研究我们的客户投诉，并创建一份具有说服力且包含建议的高管报告”。结果行文流畅，其中包含四项建议、两个趋势和一张整洁的表格。

但它无法使用。其中一项建议与政策冲突。表格合并了两个日期范围。某项区域例外被遗漏。没有人能判断哪项投诉支持哪项主张。

团队尝试了三种修复方式。他们添加了“确保准确”。他们要求 Claude“更努力地思考”。然后，他们把相同的请求粘贴到能力更强的模型中。文笔有所改善，但证据问题仍然存在。

该请求从未定义要支持的决策、允许使用的来源、必需的覆盖范围、受众或有证据支持的建议所需通过的测试。Claude 针对一份看似合理的报告进行了优化，因为合理性是唯一可见的目标。

## 概念

### Prompting 是接口设计

Prompt 是人类意图与模型行为之间的接口。良好的接口会公开输入、约束、输出和故障状态。薄弱的 prompt 则会把这四项都隐藏在“出色”“全面”或“专业”等形容词中。

使用以下契约：

1. **结果：** 此输出将支持什么决策或行动？
2. **上下文：** 哪些背景是必要的，哪些内容无关？
3. **任务：** Claude 应执行什么转换？
4. **证据：** 哪些来源可以支持主张，应如何处理证据缺口？
5. **约束：** 哪些事情绝不能发生？
6. **格式：** 结果应采用什么确切结构？
7. **验收检查：** 人员或程序将如何判定它是否通过？

各部分是否齐全比排列顺序更重要。你可以使用 Markdown 标题、XML 风格标签或其他一致的分隔符来标记各部分。结构可以帮助模型区分数据与指令，也能帮助审核人员定位假设。

```text
<outcome>
准备每周支持工作评审，以便主管选择两项流程修复措施。
</outcome>

<sources>
仅使用随附的工单和政策手册。将该手册视为权威来源。
</sources>

<task>
按根本原因对投诉进行分组，量化每组投诉，并提出不超过三项修复措施。
</task>

<constraints>
不要推断客户意图。将缺失的日期标记为未知。不要包含姓名。
</constraints>

<output>
返回：高管摘要、证据表、建议、不确定事项。
</output>

<checks>
每项建议必须引用至少两个工单 ID 和一个政策章节。
</checks>
```

### 标准先于措辞

没有目标，就无法优化 prompt。首先定义标准，然后使用有代表性的案例改进 prompt。

对于投诉报告，标准可能包括：

- 每项投诉只分配一次，或明确标记为未分类。
- 统计数量与输入总数一致。
- 政策相关主张引用已提供的章节。
- 建议不超出团队的权限。
- 不包含个人身份识别信息。
- 明确显示不确定性，而不是将其转化为猜测。

“让它更好”无法提供诊断信号。“统计数量必须一致”则能说明哪里失败以及需要修改什么。

### 按验证边界进行拆解

如果每个阶段都能产出可供检查的产物，长任务会更加可靠。一种实用的拆解方式如下：

```mermaid
flowchart LR
    A["澄清决策"] --> B["盘点来源并分类"]
    B --> C["提取主张和证据"]
    C --> D["分析模式"]
    D --> E["针对受众起草内容"]
    E --> F["验证主张和约束"]
    F --> G["批准或修订"]
```

这与按任意页数拆分任务并不相同。每个边界都应回答一个问题：

- 能否在分析前验证来源集合？
- 能否在解释前验证提取出的事实？
- 能否在发布前验证建议？

只有在任务彼此不依赖时，才并行运行这些任务。对投诉类别进行分类和提取政策约束可以并行进行。撰写建议则必须等待两者完成。

顺序执行的阶段可以减少隐藏耦合，也能建立恢复点。如果提取有误，你只需修复提取阶段，而不必重新生成整份报告。

### 示例用于教授边界

当规则难以表述或格式必须完全准确时，Few-shot 示例非常有用。好的示例会展示决策边界，而不只是展示简单而典型的情况。

对于情感标签，不要提供三个明显正面的示例。应包含一条含义模糊的投诉、一条混合陈述和一个“未知”案例，并解释每个标签适用的原因。模型由此学习类别之间的区别。

示例也可能意外创造规则。如果每个演示都提到零售客户，模型可能会把零售相关语言视为任务的一部分。应确保示例多样、精简，并与书面标准保持一致。

### 谨慎分配角色

角色 prompt 可以提供视角，例如“作为合规审核人员行事”。它们不会赋予知识、权限或访问能力。角色不能替代政策文本、来源证据或人员审批步骤。

优先使用具体视角：

```text
从隐私负责人的角度审核草稿。
找出每个暴露个人数据的句子，引用适用的已提供政策，
并提出符合规定的最小修改方案。
```

这是可以测试的。“你是世界上最优秀的隐私专家”则无法测试。

### 迭代需要假设

有效的迭代每次只改变一个有意义的变量，并在一小组评估案例中测量效果。例如：

- 假设：要求提供主张与证据对应表，可以减少缺乏支持的建议。
- 假设：将政策放在工单之前，可以改善对例外条款的处理。
- 假设：一个反例可以改善对混合案例的分类。

比较不同 prompt 变体时，应保持评估案例不变。否则，你无法区分是 prompt 得到了改善，还是输入变得更简单。

如果反复修改仍然失败，就停止润色句子。问题可能在于证据缺失、要求冲突、上下文过多、模型能力不足或工作流不安全。

## 动手构建

### 第 1 步：编写验收卡

选择一项重复性工作任务。在编写 prompt 之前，先写一张简短的验收卡：

```text
支持的决策：
主要读者：
权威来源：
必需事实：
禁止的内容或操作：
输出结构：
通过条件：
升级处理条件：
```

让每项通过条件都可观察。“专业”并不可观察。“不使用任何未经解释的缩写，并以三句话的摘要开头”则可以观察。

### 第 2 步：创建来源层级

来源冲突很常见。告诉 Claude 哪个来源优先。

```text
权威顺序：
1. 日期为 2026-07-01 的已批准政策手册
2. 当前操作规程
3. 工单备注

如果来源发生冲突，请报告冲突。不要默认选择更新或更长的文本。
```

时效性与权威性并不相同。最近的聊天消息不会自动取代已批准的政策。

### 第 3 步：设计阶段

为每个阶段定义输入、输出和门槛：

| 阶段 | 输入 | 输出 | 门槛 |
|---|---|---|---|
| 接收 | 请求和来源清单 | 范围卡 | 负责人确认决策和截止日期 |
| 提取 | 已批准的来源 | 主张与证据对应行 | 必填字段完整 |
| 分析 | 已验证的对应行 | 模式和例外 | 统计数量一致 |
| 起草 | 已批准的分析 | 面向受众的报告 | 格式和范围检查通过 |
| 验证 | 草稿及来源 | 发现的问题和修正 | 高风险问题已解决 |

此表是一份工作流规范。每个阶段的 prompt 可以保持简短、精确，不必使用一个巨大的 prompt。

### 第 4 步：添加不确定性处理行为

告诉 Claude 在证据缺失时应如何处理：

```text
如果无法获得必需事实，请写明“无法根据所提供的来源确定”。
列出缺失的来源，并说明因此无法得出哪项结论。
除非任务明确允许估算，否则不要估算数值。
```

Abstention 是经过设计的输出，而不是模型缺陷。

### 第 5 步：测试对抗性案例

创建至少五个案例：

- 一项证据完整的正常请求。
- 一项缺少一个必需来源的请求。
- 两个相互冲突的来源。
- 隐藏在来源内容中的指令。
- 一项超出用户权限的请求。

根据验收卡记录通过或失败。不要依赖一次令人印象深刻的演示。

## 实践实验

运行 contract scorer，并删除一项验收检查、来源等级、阶段门槛或对抗性案例。修复确切的故障，而不是添加模糊的 prompt 措辞。

## 实际应用

### 考试决策模式

对于场景题，请按以下顺序处理：

1. 识别请求的结果。
2. 找出缺失的要求或证据。
3. 优先选择能让故障变得可观察的修复措施。
4. 在后果严重时，保留明确的人员或政策边界。
5. 仅在解决 prompt、上下文和工作流层面的原因后，才提升模型能力。

最可靠的答案通常会改进契约或工作流，很少只是添加一个模糊的形容词。

### 常见陷阱

- **对整个项目只使用一个 prompt：** 复杂工作没有检查点。
- **增加细节但不设置层级：** 更长的 prompt 可能包含更多矛盾。
- **把角色当作权威：** persona 不会创造可靠的事实或权限。
- **示例缺少边界案例：** 模型学会了简单模式，却无法识别边界。
- **依赖 Chain-of-thought：** 要求输出隐藏的推理文本，不能替代可验证的中间产物。
- **首先升级模型：** 更强的能力无法恢复缺失的政策。
- **无休止地通过对话纠正：** 可复用任务需要版本化指令和评估案例。

### 练习

1. 将“为管理层总结此内容”改写为由七部分组成的 prompt contract。
2. 选择一项包含五个步骤的任务，识别哪些步骤可以并行运行，并解释每项依赖关系。
3. 为一个分类标签创建三个示例：一个明确案例、一个边界案例和一个 Abstention 案例。
4. 为你的 prompt 设计五个评估案例，其中包括证据冲突和未授权请求。
5. 审查最近一次较差的输出，并将故障归类为要求、来源、上下文、prompt、模型或工作流故障。

## 关键术语

- **验收标准：** 输出必须满足的可观察条件。
- **任务拆解：** 将工作拆分为具有明确依赖关系和输出的多个阶段。
- **Few-shot prompting：** 提供用于展示目标任务或边界的示例。
- **Prompt contract：** 对结果、上下文、任务、证据、约束、格式和检查进行结构化陈述。
- **来源层级：** 在来源冲突时确定哪项证据具有权威性的规则。
- **Abstention：** 在证据或权限不足时明确拒绝进行推断。
- **验证边界：** 在工作继续之前可以测试中间产物的节点。
