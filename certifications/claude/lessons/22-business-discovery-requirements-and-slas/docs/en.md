# 业务调研、需求与 SLA

> 第一个架构决策，是确定你真正负责解决的问题。

**Type:** Reference
**Languages:** Python
**Prerequisites:** Phase 11, Lesson 13; Phase 14, Lesson 12; Phase 17, Lesson 08
**Time:** ~120 分钟

## Learning Objectives

- 将宽泛的 AI 请求转化为可度量的问题陈述
- 区分功能、质量、基础设施、安全和生命周期需求
- 定义成功指标、服务级别目标和升级边界
- 识别架构设计开始前需要证据验证的假设
- 产出一份可由技术和业务利益相关者批准的调研简报

## 问题

一位客服主管要求构建一个能够自动解决所有工单的 Agent。
这个请求听起来很具体，其实并非如此。

你不知道哪些工单类别在范围内、解决意味着什么、Agent 可以更改哪些
系统、它拥有多大的财务权限、用户能容忍多长的延迟，以及哪些操作需要人员介入。
你也不知道真正的问题是响应时间、政策应用不一致、积压、
成本，还是客户满意度。

如果从 Model 和 Tool 列表开始，你优化的将是一个假设。即使系统在
技术上令人印象深刻，也可能因为改进了错误的指标、自动执行了被禁止的步骤，
或仅仅将工作从 Agent 转移给审查者而没有减少总工作量，最终仍然失败。

专业的架构设计始于调研。考试会检验你能否将业务意图转化为解决方案，
并为其中的权衡进行论证。在实践中，这项 Skill 可以避免数月的返工。

## 概念

### 从决策开始，而不是从 Feature 开始

将请求重写为一项具有负责人、证据和后果的决策。

薄弱的问题陈述：

```text
构建一个 Claude 客服 Agent。
```

决策型陈述：

```text
将账单问题获得符合政策的首次响应所需的中位时间
从 11 分钟缩短到 3 分钟以内，同时将缺乏依据的退款操作保持为
零，并保留由人员审批超过团队阈值的退款。
```

第二种陈述明确了需要度量的内容，也明确了不应自动化的内容。

在第一次调研会议中使用以下五个问题：

1. 哪个可观测结果应该发生变化？
2. 谁对该结果负责？
3. 输出之后会执行什么操作？
4. 错误、迟到或缺失答案的成本是多少？
5. 哪些约束不能被舍弃？

### 在确定优先级之前对需求进行分类

当每个请求都变成“需求”下的一条通用项目时，架构师就会丢失信息。
应使用明确的类别。

| 类别 | 问题 | 客服示例 |
|-------|----------|-----------------|
| 功能 | 系统必须做什么？ | 读取工单、查找政策、起草回复 |
| 质量 | 必须达到怎样的质量？ | 在 98% 的 Evaluation 草稿中引用当前有效的政策版本 |
| 性能 | 需要多快，并支持多大规模？ | 在每秒 40 个请求时，P95 草稿延迟低于 8 秒 |
| 安全 | 谁可以查看或更改什么？ | 只有被指派的 Agent 可以查看账户 Context |
| 安全防护 | 哪些结果需要预防或审批？ | 未经有效的权限决策，绝不执行退款 |
| 可运维性 | 如何检测故障并恢复？ | 对检索新鲜度和 Tool 错误率发出警报 |
| 生命周期 | 谁负责更新、批准和停用它？ | 政策团队负责来源新鲜度；平台团队负责 runtime |

这种分类会暴露矛盾。“立即回答”与“执行三来源合规审查”相冲突。
“自动处理所有退款”与人员审批要求相冲突。调研会在代码将这些冲突
变成事故之前，使其显现出来。

### 映射当前工作流

不要根据幻灯片中描述的理想化流程进行设计。观察真实工作。

```mermaid
flowchart LR
    I["工单到达"] --> T["Agent 对意图进行 Classification"]
    T --> P["Agent 搜索政策"]
    P --> A["Agent 检查账户权限"]
    A --> D["Agent 起草回复或升级"]
    D --> R["审查者批准高风险操作"]
    R --> O["记录回复和操作"]
    O --> F["结果成为反馈"]
```

对于每个步骤，记录：

- 输入和输出
- 记录系统
- 负责角色
- 决策规则
- 常见例外
- 延迟和返工
- 数据分类
- 保留的证据

价值最高的干预方式可能是为政策步骤提供检索、在接入环节使用一个窄范围
classifier，或改进审批界面。自主 Agent 只是其中一种可能的模式。

### 将价值与能力分开

Claude 可能具备起草回复的能力。业务价值取决于草稿是否能减少审查后的
总处理时间、提高一致性，或实现新的服务级别。

使用一个简单的价值假设：

```text
对于 [user or team]，使用 [bounded capability] 改变 [workflow step] 将把
[business measure] 从 [baseline] 提升到 [target]，且不违反
[guardrail]。我们将在 [evaluation window] 后确认结果。
```

每个字段都必须用证据填写，或明确标记为假设。不要把不确定性
隐藏在一张显得笃定的架构图中。

### 将风险转化为审查边界

人工审查并不是通用的安全答案。它必须具备触发条件、审查者、
证据包、时间预算和回退方案。

对于每项操作，估算：

- 出错时的影响
- 可逆性
- 证据可提供的置信度
- 监管或政策义务
- 被滥用的可能性
- 审查成本

低影响、可逆的草稿可以自动继续。高影响或不可逆的操作需要
确定性检查和明确权限。中等风险通常需要抽样审查、基于阈值的审查，
或操作后的审计。

### 正确定义 SLI、SLO 和 SLA

服务级别指标是实际测得的信号。服务级别目标是内部目标。
服务级别协议是具有业务或合同后果的承诺。

| 层级 | 示例 |
|-------|---------|
| SLI | 带有当前有效政策引用的草稿百分比 |
| SLO | 在滚动七天窗口内至少达到 98% |
| SLA | 在合同约定的客服时间窗口内向客户提供首次响应 |

在没有定义总体范围、Label、测量方法，以及未达到目标时如何响应之前，
不要承诺 Model 准确率 SLA。“Model 准确率为 95%”在运维层面没有意义。

对于 AI 系统，应包含多个类别的指标：

- 任务质量：事实性、完整性、政策遵循情况
- 系统性能：延迟、可用性、吞吐量
- 经济性：每个成功任务的成本、cache 命中率、审查工作量
- 安全防护：被阻止的不安全操作、错误阻止、升级精确度
- 运维：检索新鲜度、Tool 故障、回滚时间

### 明确非目标

非目标可以防止系统范围悄然扩张。

示例：

- 第一个版本起草回复，但不发送回复。
- 它处理账单 FAQ，但不处理账户关闭。
- 它可以建议退款金额，但不能执行退款。
- 试点期间仅支持英文工单。

如果利益相关者不同意，说明调研发现了一项需要明确归属的决策。
这就是进展。

### 按错误成本确定优先级

为每个候选用例使用以下决策表：

| 维度 | 低 | 中 | 高 |
|-----------|-----|--------|------|
| 错误输出的影响 | 轻微编辑 | 客户阻力 | 财务、法律或安全伤害 |
| 可逆性 | 一键撤销 | 手动修正 | 不可逆或难以修正 |
| 数据敏感度 | 公开 | 内部 | 受监管或机密 |
| 操作权限 | 仅起草 | 有界写入 | 破坏性或财务写入 |
| 证据质量 | 直接来源 | 部分来源 | 模糊或缺失 |

高分并不意味着自动禁止使用 AI。它会推动架构采用更窄的范围、
确定性关卡、更有力的证据、人员审批和更保守的发布方式。

## Use It

将简报应用于三个候选架构：

1. 采用人员审批的检索辅助草稿生成。
2. 仅调用 Claude 进行 Classification 和起草的确定性工作流。
3. 配备工单、政策、账户和退款 Tool 的自适应 Agent。

根据需求为每个方案评分。能力最强的选项不一定是最佳选择。
如果工作流稳定且已知，确定性编排通常可以减少延迟、成本和失败面。
当执行路径取决于执行期间发现的证据，且额外的灵活性值得承担控制负担时，
再使用 Agent。

将选择记录在架构决策记录中：

```markdown
# ADR：客服解决模式

## 状态
提议中

## Context
决策、约束、证据和未解决的假设。

## 选项
1. 检索辅助草稿工作流
2. 确定性多步骤工作流
3. 使用 Tool 的自适应 Agent

## 决策
选定的选项，以及它最能满足的需求。

## 被拒绝的替代方案
说明每个替代方案为何在当前约束下落选。

## 后果
新增的运维工作、剩余风险和回退计划。

## 验证
离线 Evaluation、试点防护措施、SLO 和审查日期。
```

## 考试决策模式

当场景以宽泛的业务请求开始时，最有力的第一步通常是在选择技术之前
减少歧义。

优先选择符合以下特征的答案：

- 确立业务结果和当前基线
- 识别用户、记录系统和下游操作
- 将硬性约束与偏好分开
- 定义质量和运维度量
- 明确审查和生命周期负责人
- 通过有界试点验证风险最高的假设

对于立即选择最大 Model、添加 Agent，或在没有澄清权限和错误成本的情况下
承诺自动化的答案，应保持警惕。

## 常见陷阱

### 将每个请求都变成 Agent

Agent 式灵活性是有成本的：更多 Tool 调用、更大的攻击面、
更困难的测试，以及更不可预测的延迟。仅当自适应规划是一项需求时才选择它。

### 将人工审查视为免费

审查队列可能成为新的瓶颈。应度量审查时间、一致程度和升级质量。

### 使用没有分母的准确率

明确 Dataset、总体范围、Label、Evaluator 和时间窗口。
否则这个数字无法指导运维决策。

### 忽略上线后的归属

每个 Prompt、来源、Tool、控制项、指标和升级路径都需要负责人。
无人负责的控制项会悄然失效。

## 练习

1. 将“构建一个 AI 分析师”重写为决策型问题陈述，其中包含
   基线、目标、防护措施和负责人。
2. 映射一个真实工作流，并识别其中一个确定性规则优于
   Model 调用的步骤。
3. 为检索辅助的合规工作流定义五个 SLI。至少包含一个
   质量、安全防护、经济性和可运维性信号。
4. 编写一份 ADR，拒绝采用 Agent 架构，即使 Model
   有能力完成这项工作。
5. 设计一个试点，在不给予系统生产写入权限的情况下，
   验证风险最高的假设。

## 关键术语

| 术语 | 人们通常怎么说 | 它真正的含义 |
|------|-----------------|------------------------|
| Requirement | 一项被请求的 Feature | 解决方案必须满足的可测试条件 |
| Constraint | 某件不方便的事情 | 架构不能舍弃的边界 |
| SLI | 一个 SLA 目标 | 用于判断服务行为的测量信号 |
| SLO | 供应商承诺 | 针对某项指标的内部目标 |
| SLA | 任何性能目标 | 具有明确后果的服务承诺 |
| Non-goal | 被悄然推迟的工作 | 防止范围漂移的明确边界 |
| ADR | 一张图 | 对 Context、选项、决策和后果的持久记录 |
