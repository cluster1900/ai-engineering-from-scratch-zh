# एजेंट निर्देश के रूप में निष्पादित करने योग्य बंधन

> प्रसंस्करण के लिए लिखित निर्देशों का उपयोग करना इच्छा है। प्रसंस्करण के लिए लिखित निर्देशों का उपयोग करके परीक्षण किया जाता है। कार्यस्थल प्रत्येक नियम को एजेंट में बदल देता है।

**类型：**构建
**语言：**पायथन (stdlib)
**前置要求：**चरण 14 · 32 (न्यूनतम कार्यक्षेत्र)
**时间：** लगभग 50 मिनट

## 学习目标

- मार्गदर्शिका एवं संचालन नियम अलग-अलग होंगे।
- प्रारंभ करने के नियम, रोकें संचालन, पूरा करें परिभाषा, अनिश्चितता प्रसंस्करण और अनुमोदन सीमाओं को प्रदर्शित करने के लिए मशीनों की जांच योग्य सीमाओं के लिए।
-  एक नियम जांचकर्ता को लागू करना, एक नियम संग्रह का उपयोग करके एक बार के संचालन पर मूल्यांकन करना।
- ️ नियमों का संग्रह आसान हो जाए ताकि समीक्षाएँ यह पता लगा सकें कि क्या बदलाव हुआ है

## 问题

`AGENTS.md`读起来像进入职档――它告诉代理人要谨慎和充分测试,以及不确定就问──三天后,代理人交付了没有测试的变更,写入了被禁止的目录,而且从未问过,因为它根本不知道边界在哪里──

जब निर्देश कार्य करने योग्य होते हैं, तो वे बहुत मजबूत होते हैं; जब निर्देश केवल दृश्य के होते हैं, तो वे बहुत कमजोर होते हैं।

## 概念

नियम रखा जाना चाहिए`docs/agent-rules.md`मध्य, दूर से संक्षिप्त की जड़ मार्गदर्शक. प्रत्येक नियम तथा प्रथाओं का नामकरण.

```mermaid
flowchart LR
  Router[AGENTS.md] --> Rules[docs/agent-rules.md]
  Rules --> Checker[rule_checker.py]
  Checker --> Report[rule_report.json]
  Report --> Reviewer[Reviewer]
```

### 覆盖大多数规则的五个类别

| 类别 | 规则回答的问题 | 示例 |
|----------|---------------------------|---------|
| Startup | 工作开始前必须满足什么？ | “state file exists and is fresh” |
| Forbidden | 什么事情绝对不能发生？ | “do not edit `scripts/release.sh`” |
| Definition of done | 什么能证明任务已完成？ | “pytest exits 0 and acceptance line passes” |
| Uncertainty | Agent 不确定时该做什么？ | “open a question note instead of guessing” |
| Approval | 什么需要人工审批？ | “any new dependency, any prod write” |

 इन पांचों में से एक नियम में शामिल नहीं हो सकता, आमतौर पर दो नियमों में विभक्त होना चाहिए

### नियम यंत्र पठनीय है

प्रत्येक नियम में एक शॉट होता है, एक श्रेणी, एक रेखा, और एक`check`字段,指向 `rule_checker.py`मध्य में एक प्रकार का कार्य---जोड़े नियम का अर्थ है अतिरिक्त जांच; जांचकर्ता कार्ययोजना के साथ बढ़ेगा---

### 规则便于不同

规则在一个Markdown文件中,每条规则占据一个标题──重命名在不同中可见──新规则放在其类别的顶部──过时规则应删除,而不是注释掉,因为工作台才是真相来源,不是团队上个季度感受如何的聊天记录──

### 规则与框架 पहरा

框架 guardrails(OpenAI Agents SDK guardrails、LangGraph interrupts) in运行时层面执行规则──本课中的规则集是这些 guardrails 所实现的人类可读、可评审的契约──两者都需要:运行时会在一轮中捕获违规,而规则集会证明运行时正在做正确的事──

### प्रगतिशील प्रकटीकरण: 図書, बजाय百科全书

`AGENTS.md`यह लगातार बदलता रहता है, क्योंकि हर घटना में एक नियम नया होता है, लेकिन बहुत कम घटनाएं होती हैं एक नियम को हटा दिया जाएगा। एक वर्ष बाद, इस फ़ाइल में दो हजार पंक्तियां हो सकती हैं; एजेंट  पढ़कर पहले स्क्रीन पर अपना पूरा ध्यान देने वाला बजट खर्च कर सकता है, केवल एक छोटा सा हिस्सा निष्पादित कर सकता है।

修复方式 एक छोटा सा फाइल नहीं लिखना है, बल्कि एक अलग-अलग स्तर का फाइल लिखना है। 根路由器 को प्रत्येक सत्र तक छोटा करना है ताकि वह पढ़ सके और केवल निर्देशिकाएँ सहेजें।  गहन सामग्री विषय फ़ाइलों में रखी जाती है, केवल जब कार्य संबंधित विषय को छूता है तो एजेंट 才लोड करे।

```text
AGENTS.md                  # router，少于 50 行：这个 repo 是什么、去哪里看、5 条硬规则
docs/
  agent-rules.md           # 完整规则集（本课）
  architecture.md          # 任务触及 module boundaries 时加载
  testing.md               # 任务编写或运行 tests 时加载
  deploy.md                # 只在 release 工作中加载，并受 approval rule 保护
feature_list.json          # backlog（Phase 14 · 36）
```

| Tier | 存放位置 | 读取时机 | 大小预算 |
|------|----------|----------|----------|
| Router | `AGENTS.md` | 每个 session，始终读取 | 少于约 50 行 |
| Rules | `docs/agent-rules.md` | 每个 session 启动时 | 每个 category 一屏 |
| Topic docs | `docs/<topic>.md` | 只有任务触及该主题时 | 需要多深就多深 |

两个测试能让分层保持诚实――第一是可达性测试:代理 应能从路由器出发,最多两跳到任何规则,所以路由器 必须按路径链接每个主题 doc,而不是用散文模糊描述――第二是新鲜性测试:路由器 足够短,评审员会在每个 PR 里重读它,这是防止它长回百科全书的唯一办法――指针效率失效比缺一条规则更糟,所以路由器中断链本身就是启动检查违规――

##  इसे निर्माण

`code/main.py`提供:

- `agent-rules.md`पार्सर,将规则加载到数据类 中──
- `rule_checker.py`风格的检查函数, प्रत्येक `check`引用对应一个.
- एक डेमो एजेंट  चला जाता है, यह दो नियमों का उल्लंघन करता है, तथा एक बार इन उल्लंघन की जांच को पकड़ सकता है पारित किया गया है।

运行它:

```
python3 code/main.py
```

输出:解析后的规则集、运行 追踪、 प्रत्येक条规则的通过/失败,以及保存在脚本旁边的 `rule_report.json`

## 生产中的模式

तीन प्रकार के नियम हैं जो एक तिमाही के लिए एक सप्ताह के भीतर मंदी के लिए एक नियम से भिन्न होते हैं।

**编写时标注严重性。**हर नियम के साथ है`severity`:`block``warn`या `info`◊ निरीक्षक बैठक रिपोर्ट; परिचालन समय केवल `block`ऊपर अस्वीकार करना। अधिकांश टीमों को प्रारंभिक गंभीरता का उच्च मूल्यांकन करना होगा, फिर समाप्ति तिथि के दबाव में इसे कम करना होगा; लेखन के दौरान, अंकन टीम को पूर्व-कक्षाबद्ध करना होगा।`block`规则的过渡 签入 `overrides.jsonl`लेखा परीक्षा का लॉग

**规则过期作为强制机制。**हर नियम के साथ है`expires_at`日期(默认是编写后 90 天) ⋅当某条未过期规则连续 60 天没有任何违规时,检查器发出警告;下季度评审要说明保留的理由,要么削弱为`info`, या इसे हटा दें। क्लाउडफ्लेयर के उत्पादन एआई कोड समीक्षा डेटा ((2026 वर्ष 4 月,30 天内跨 5,169  repo 运行 131,246 बार समीक्षा) दिखाता है, के साथ स्पष्ट समाप्ति तंत्र के नियम एक संयोजन प्रत्येक समाप्ति तंत्र के नियम के भीतर बनाए रखा जा सकता है; कोई समाप्ति तंत्र के नियम सभा बढ़कर 80 + तक है, और अधिकांश कभी नहीं टच है।

**Markdown 作为 source，JSON 作为 cache。** `agent-rules.md`                                                                                                                                                                                                                                                              `agent-rules.lock.json`है चेकचर में हॉट पथ 中读取的缓存──lock द्वारा पूर्व-कंपिट हुक 重新生成──Markdown diff 便于评审;JSON पार्सिंग नहीं जाएगा प्रत्येक बारी में प्रवेश──形态与 `package.json`/`package-lock.json`和 `Cargo.toml`/`Cargo.lock`समान

## इसका उपयोग करें

उत्पादन में:

- क्लाउड कोड、कोडेक्स、Cursor  सत्र शुरू होने पर नियम पढ़ें, और ऑपरेशन से इनकार करते समय उनका हवाला दें।
- OpenAI एजेंट्स SDK गार्डरेल्स 将同样检查注册为输入和输出 गार्डरेल्स──मार्कडाउन 是 डॉक्स 表面;SDK 是运行时表面──
- LangGraph interrupts 会在执行的节点 违反规则时触发──interrupt handler 读取规则,询问人类,然后恢复──

यह नियम तीनों के बीच में स्थानांतरित किया जा सकता है, क्योंकि यह केवल मार्कडाउन और फ़ंक्शन नाम है।

## 关键术语

| 术语 | 人们的说法 | 它实际意味着什么 |
|------|----------------|------------------------|
| Operational rule | “一条真正的指令” | 工作台可在运行时检查的规则 |
| Aspirational rule | “谨慎一点” | 没有检查的规则；要么删除，要么升级 |
| Definition of done | “Acceptance” | 证明任务已完成的客观、基于文件的证据 |
| Block severity | “硬规则” | 违规会中止运行；没有 operator 不能静默处理 |
| Rule expiry | “过时规则清理” | 在 N 天内没有失败的规则可以考虑退役 |
