# 生产环境中的 MCP 认证与识别权:绑定签发人注册与代币机制

> 第 16 课构建 OAuth 2.1 状态机――本课针对 MCP 2026-07-28 规范加固其生产环境边界:首选客户端 ID 元数据文档(CIMD),仅将废弃的动态客户端注册作为兼容方案,严格校验授权响应中的发发放者,根据签发者物理隔离客户端凭证,实现 JWKS 定时轮查询刷新,并精确每个无状态请求上受众绑定(观众-ピン的代币)

## 概念

### आरएफसी 8414  OAuth 授权服务器元数据

位于 `/.well-known/oauth-authorization-server`का दस्तावेज ग्राहक को आवश्यक सभी जानकारी का वर्णन करता हैः

```json
{
  "issuer": "https://auth.example.com",
  "authorization_endpoint": "https://auth.example.com/authorize",
  "token_endpoint": "https://auth.example.com/token",
  "jwks_uri": "https://auth.example.com/.well-known/jwks.json",
  "client_id_metadata_document_supported": true,
  "registration_endpoint": "https://auth.example.com/register",
  "authorization_response_iss_parameter_supported": true,
  "response_types_supported": ["code"],
  "grant_types_supported": ["authorization_code", "refresh_token"],
  "code_challenge_methods_supported": ["S256"],
  "scopes_supported": ["mcp:tools.read", "mcp:tools.invoke"],
  "token_endpoint_auth_methods_supported": ["none", "private_key_jwt"]
}
```

客户端在获取MCP 资源URL 后进行链式发现:先通过RFC 9728 `oauth-protected-resource`(资源服务器文档) प्राप्त知所信任的发发发件者, फिर आरएफसी 8414 (本规范文档) के माध्यम से प्राप्त इस发发件者 के प्रत्येक सेवा端点──客户端永远不要硬编码授权端点URL──

मार्गों में संसाधन पहचानकर्ता शामिल करने के लिए, कृपया इस मार्ग से पहले प्रसिद्ध 字段── उदाहरण के लिए,`https://mcp.example.com/team/server`प्रति应的受保护资源元数据地址应解析为`https://mcp.example.com/.well-known/oauth-protected-resource/team/server`切勿将 `/.well-known/...`错误地增加在资源路径后──

MCP पूर्व अनिवार्य अनुमोदन के अनुबंधों के लिए:

- `code_challenge_methods_supported`必須包含 `S256`(RFC 7636 के PKCE 要求 के अनुरूप)**缺失**,则表示该授权服务器不支持 PKCE,客户端**必须**                                                                                                                                                                                                                                                              
- `grant_types_supported`包含 `authorization_code`, दृढ़ता से मना कर दिया`password`和 `implicit`
- कम से कम एक पंजीकरण मोड का समर्थन करेंः`client_id_metadata_document_supported: true`(CIMD,首选) 、 पूर्व विनियोजन ग्राहक अभिलेख, या `registration_endpoint`(बंद RFC 7591 兼容模式)
- `authorization_response_iss_parameter_supported`सही है, ग्राहक अनिवार्य आवश्यकताओं को अधिकृत प्रतिक्रिया में वापस RFC 9207 `iss`,并严格将其与重定向前记录发发发人相对──
- ओएथ 2.1 规范下 में,`response_types_supported`必須精确为 `["code"]`

यदि अभाव `S256`支持,MCP सर्वर  दृढ़ता से इस IDPPKCE  कोई रियायती मोड नहीं `client_id`, इसी तरह कनेक्टिविटी को पूरा नहीं कर सका; इस समय कोडे को संशोधित करने के बजाय डिप्लॉयमेंट को साफ करने की व्यवस्था करनी चाहिए।

### आरएफसी 9728 ((回顾)  संरक्षित संसाधन

第16 课介绍了RFC 9728――在生产环境中的关键点是: इस दस्तावेज़ में ग्राहक को जानकारी प्राप्त होती है**当前**MCP सर्वर में विश्वास के लिए अधिकृत सर्वर संग्रह का एकमात्र अधिकार स्रोत। एकल MCP सर्वर एक ही समय में कई आईडीपी पर भरोसा कर सकता है जैसे एक आंतरिक कर्मचारियों के लिए, दूसरा बाहरी सहयोगियों के लिए।

```json
{
  "resource": "https://notes.example.com",
  "authorization_servers": ["https://auth.example.com", "https://partners.example.com"],
  "scopes_supported": ["mcp:tools.invoke"],
  "bearer_methods_supported": ["header"],
  "resource_documentation": "https://notes.example.com/docs"
}
```

### 客户端 ID 元数据文档(推默认方案)

客户端所托管的元数据文档结构 इस प्रकार हैः

```json
{
  "client_id": "https://app.example.com/oauth/client.json",
  "client_name": "Example MCP Client",
  "client_uri": "https://app.example.com",
  "application_type": "native",
  "redirect_uris": ["http://127.0.0.1:7333/callback", "http://localhost:7333/callback"],
  "grant_types": ["authorization_code", "refresh_token"],
  "response_types": ["code"],
  "token_endpoint_auth_method": "none"
}
```

वर्तमान में सीआईएमडी के नियमों में,`client_id``client_name`के साथ-साथ`redirect_uris`संख्याएँ आवश्यक हैं। ग्राहक पहचानकर्ता अनिवार्य रूप से एक पूर्ण HTTPS URL होना चाहिए जिसमें कोई मार्ग हो।`application_type`लेकिन यह सीआईएमडी के लिए बाध्यकारी नहीं है।`application_type`के अनिवार्य आवश्यकताएं मशीनों के लिए उपयोग किया जाता है

规范明确指出的两大核心安全事实:

- **防范 SSRF：**授权服务器拉取是攻击者提供的URL,必须严密防范服务端请求伪造(严禁访问内部私有网络及管理端点)
- **防范 localhost 冒充：** अकेले CIMD  स्थानीय हमलावरों को कानूनी ग्राहक के यूआरएल का उपयोग करने से रोकने में असमर्थ`localhost`重定向端口── इसलिए, प्राधिकरण सर्वर पर उपयोगकर्ता सहमति पृष्ठ प्रदर्शित करते समय,**必须**清晰展示重定向 URI 的主机名,并**应当**शुद्धता के लिए`localhost`सुरक्षा चेतावनी जारी करने की दिशा में पुनः निर्धारित किया गया है।

चूंकि CIMD को सेवा में पंजीकरण की स्थिति को स्थायी रूप से बनाए रखने की आवश्यकता नहीं है, इसलिए अब DCR की तरह जटिल पंजीकरण सेवा केंद्रों का रखरखाव करने की आवश्यकता नहीं है।

यदि अधिकृत सर्वर प्रबंधक ने पहले ही ग्राहक पहचानकर्ता को आवंटित कर दिया है, तो उसे पहले से ही विशिष्ट जारीकर्ता के लिए पूर्व पंजीकरण प्रमाण पत्र का उपयोग करना चाहिए, फिर स्वचालित रूप से पंजीकरण करने का प्रयास करना चाहिए। अन्यथा, केवल जारीकर्ता पहले से ही पूर्व पंजीकरण का समर्थन नहीं करता है और न ही CIMD का समर्थन करता है, तो वह केवल अप्रचलित DCR 方案 में वापस लौटता है।

### JWKS 刷新模式(AS 负责 रोटेट, संसाधन सर्वर ज़िम्मेदार Refresh)

 दो क्रियाओं को कठोरता से अलग करना आवश्यक है, उत्पादन में उन्हें मिलाकर बहुत आसानी से होने वाली वास्तविक त्रुटि हैः

- **轮换（Rotate）：**है**授权服务器（AS）**का व्यवहारः नई हस्ताक्षर निजी कुंजी उत्पन्न करना, JWKS में इसे सार्वजनिक करना, और बाद में पुरानी कुंजी को समाप्त करना। संसाधन सर्वर ने इस ऑपरेशन में भाग लेने का कोई अधिकार नहीं लिया है और यह इस ऑपरेशन को निष्पादित करने में असमर्थ है।
- **刷新（Refresh）：**है**资源服务器**का व्यवहारः HTTP GET के माध्यम से 重新拉取公开发布 के JWKS 并更新其本地缓存── यह संसाधन सर्वर का एकमात्र JWKS 操作 है जिसे निष्पादित करने की आवश्यकता है──

उत्पादन वातावरण में सबसे विशिष्ट दोषपूर्ण मॉडल है**缓存过期失效** समाधान है अपनाया**定时刷新任务 + 键值缓存**◊ संसाधन सर्वर एक समायोजन कार्य करते हैं, जो निश्चित समय के अंतराल पर संचालित होता है।`<issuer>/.well-known/jwks.json`और कवर लिखें`cache[issuer] = {keys, fetched_at}`验签器直接读取该内存缓存──若某 टोकन 的 `kid`में वर्तमान कैश में未命中,触发**单次**साथ ही, यह दो बड़े परिदृश्यों को हल करता हैः निश्चित समय चक्र ताज़ा करना, और अगले चक्र ताज़ा होने से पहले, सभी नए कुंजी जारी करने वाले टोकन का उपयोग करना।

पुनः संचालन**必须是重新拉取（Re-fetch），绝对不能是轮换（Rotate）**`kid`*अभी भी* नहीं मिल पा रहा है जो Token जारी किया गया है, परीक्षण अभी भी विफल रहा है;`kid`के टोकन, सिस्टम को नई कुंजी उत्पन्न करने के लिए मजबूर करेगा, जिससे आपदाजनक स्वयं-नकार सेवाएं उत्पन्न होंगी।`kid`अंततः केवल एक बार ही विनाशकारी निष्फलता लाया जाएगा।

缓存结构:

```json
{
  "https://auth.example.com": {
    "keys": [
      {"kid": "k_2026_03", "kty": "RSA", "n": "...", "e": "AQAB", "alg": "RS256", "use": "sig"},
      {"kid": "k_2026_04", "kty": "RSA", "n": "...", "e": "AQAB", "alg": "RS256", "use": "sig"}
    ],
    "fetched_at": 1772668800
  }
}
```

稳定运行状态下通常同时存在两个密钥.`k_2026_03`) पहले,会提前引入下一代新密钥(`k_2026_04`), ताकि यह सुनिश्चित हो सके कि पुराने कुंजी के तहत जारी किए गए भंडार टोकन अपने प्राकृतिक काल से पहले भी वैध हो।`kid`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             

### 统一的 टोकन 验证例程

MCP सर्वर में किसी भी उपकरण को निष्पादित करने से पहले एकजुट निष्पादित करने की आवश्यकता है।`code/main.py`मध्य मानक अनुशासन निम्नानुसार हैः

```python
result = server.validate(bearer_token, required_scope="mcp:tools.invoke")
if not result["valid"]:
    return {"status": result["status"], "WWW-Authenticate": result["www_authenticate"]}
```

`validate`函数负责解码 JWT, from JWKS 缓存中解析签名公钥(未命中时触发单次回退刷新),校验数字签名,然后依次检查 `iss`क्या यह सूची में है?`aud`क्या यह सर्वर के विनियमन के अनुरूप है,`exp`यदि कोई भी जांच विफल हो जाती है, तो तुरंत विशिष्ट त्रुटि विवरण के साथ वापस आएं।`WWW-Authenticate`质询头―― संसाधन सर्वर पर इस एक ही प्रक्रिया से यह सुनिश्चित होगा कि प्रत्येक प्रवाह प्रवेश (किसी भी उपकरण का उपयोग करें, या किसी भी प्रकार का संचरण) पूरी तरह से संगत सुरक्षा प्रतिबंध से गुजरता है, जिससे किसी भी अप्रत्याशित परीक्षण से व्यापारिक तर्क के किसी भी त्रुटि को दूर किया जा सकता है।

### 撤销 एक समय效性契约 (समय效性契约)

आरएफसी 7009  ग्राहक अनुरोध प्राधिकरण सर्वर किसी टोकन को वापस लेने की अनुमति देता है। लेकिन यह अनुरोध स्वचालित रूप से हटाया नहीं जाएगा जो पहले से ही विभिन्न वितरित संसाधन सर्वर पर मौजूद है।

अस्पष्ट टोकन के ढांचे का उपयोग करके उच्च जोखिम वाले लोगों के लिए एक-एक करके इनट्रॉस्पेक्शन या विनियोजन के लिए एक बहुत ही कम समय का प्रभावी कैशिंग प्राप्त करने के लिए किया जा सकता है। ️ जबकि स्वयं-समावेशित JWT ढांचे का उपयोग आमतौर पर इस प्रकार किया जाता हैः Access Token के प्रभावी जीवन चक्र को छोटा करना ️ IDP पक्ष में Refresh Token को प्राप्त करना ️ संपूर्ण सुरक्षा घटनाओं के दौरान हस्ताक्षर सार्वजनिक कुंजी का फेरबदल करना, और किसी भी व्यक्ति, सत्र या टोकन ID के स्थानीय नामों को तत्काल रोकना ️ के लिए सहायता करना। ️ हस्ताक्षरित JWT को अपने नामित स्तर की समाप्ति की अवधि तक, पासवर्ड के रूप में हमेशा प्रभावी किया जाता है, जब तक कि संसाधन सर्वर को अधिकृत बाहरी रद्द प्रमाण पत्र प्राप्त न हो।

उपयोगकर्ता पंजीकरण, खाता बंद करने, रद्द करने का अधिकार और आपातकालीन प्रतिक्रिया यद्यपि विभिन्न उत्प्रेरक स्रोतों में से हैं, लेकिन अंततः सभी को एक मात्रात्मक कठोर सूचक प्राप्त करना होगाः घोषणा के रद्द करने की खिड़की की अवधि के बाद, समूह में सभी प्रतिकृति उदाहरणों को दृढ़ता से इस प्रमाण पत्र को अस्वीकार करना होगा।

| 定时 JWKS 刷新失败，已知 `kid` 仍在尚未过期的受限缓存中 | 仅在声明的故障容忍窗口内允许降级继续运行，并向外暴露系统健康度降级告警证据 |

### 常见故障模式(अपयश मोड)

- **陈旧过期的 JWKS：**AS 轮换密钥后,验签器误将合法Token 拦截―― समाधान है उपर्युक्त 定时刷新任务 + 未命中回退拉取 模式―― किसी भी रीस्चार्ज तंत्र के बिना 板缓存 JWKS――
- **回退机制误搞成密钥轮换：**यह एक बहुत ही गंभीर तर्क बग है, यह केवल अनुरोध में गायब है, जो कि यह नहीं है।`kid`, हमलावरों को नकली का उपयोग करने के लिए भी अनुमति देगा ।`kid`                                                                                                                                                                                                                                                              
- **缺失 `aud` Claim：** कुछ पुराने संस्करण IdP 默认会省略 `aud`, जब तक ग्राहक द्वारा टोकन अनुरोध में स्पष्ट रूप से प्रदान नहीं किया जाता है `resource`◊परीक्षणकर्ता को निर्णायक रूप से अनुपस्थिति से इनकार करना चाहिए `aud`इस प्रकार, यह एक संकेत है कि यह एक संकेत है।
- **遗漏 `iss` 校验导致的 Mix-Up 攻击：**客户端若未校验 RFC 9207 授权响应中 `iss`参数, हो सकता है कि उसे धोखा दिया जाए ईमानदारी एएस का प्राधिकरण कोड ब्लैकस कंट्रोल के टोकन 端点 को प्रस्तुत किया जाए। यह एक विशिष्ट ग्राहक त्रुटि है, संसाधन सर्वर इसे ठीक नहीं कर सकता है।
- **Scope 提升并发竞争：**एक ही उपयोगकर्ता के दो बार और अधिकृत अधिकारों को बढ़ाने के लिए एक ही उपयोगकर्ता के दो बार और अधिकृत अधिकारों को बढ़ाने के लिए एक ही उपयोगकर्ता के दो बार उपयोग करने के लिए एक ही उपयोगकर्ता के दो अलग-अलग उपयोग टोकन उत्पन्न करने के लिए एक ही उपयोगकर्ता के दो बार उपयोग के लिए एक ही उपयोगकर्ता के दो चरणों में उपयोग के लिए एक ही उपयोगकर्ता के साथ एक ही उपयोगकर्ता के साथ एक ही उपयोगकर्ता के साथ एक ही उपयोगकर्ता के साथ एक ही उपयोगकर्ता के साथ एक ही उपयोगकर्ता के साथ एक ही उपयोगकर्ता के साथ एक ही उपयोगकर्ता के साथ एक ही उपयोगकर्ता के साथ एक ही उपयोगकर्ता के साथ एक ही उपयोगकर्ता के साथ एक ही उपयोगकर्ता के साथ एक ही उपयोगकर्ता के साथ एक ही उपयोगकर्ता के साथ एक ही उपयोगकर्ता के साथ एक ही उपयोगकर्ता के साथ एक ही उपयोगकर्ता के साथ एक ही उपयोगकर्ता के साथ एक ही उपयोगकर्ता के साथ एक ही उपयोगकर्ता के साथ एक ही उपयोगकर्ता के साथ एक ही उपयोगकर्ता के साथ एक ही उपयोगकर्ता के साथ एक ही उपयोगकर्ता के साथ एक ही उपयोगकर्ता के साथ एक ही उपयोगकर्ता के साथ एक ही उपयोगकर्ता के साथ एक ही उपयोगकर्ता के साथ एक ही उपयोगकर्ता के साथ एक ही उपयोगकर्ता के साथ एक ही उपयोगकर्ता के साथ एक ही उपयोगकर्ता के साथ एक ही उपयोगकर्ता के साथ एक ही उपयोगकर्ता के साथ एक ही उपयोगकर्ता के साथ एक ही उपयोगकर्ता के साथ एक और एक और उपयोगकर्ता के साथ एक और एक और उपयोगकर्ता के साथ एक और एक और उपयोगकर्ता के साथ एक और एक और एक और उपयोगकर्ता के साथ एक और एक और एक और उपयोगकर्ता के साथ एक और एक और एक और उपयोगकर्ता के साथ एक और एक और एक और एक और उपयोगकर्ता के साथ एक और एक और एक और एक और उपयोगकर्ता के साथ एक और एक और एक और एक और एक है।

## 关键术语

| 术语 | 通俗说法 | 精确工程含义 |
|------|---------|-------------|
| ASM | "OAuth 元数据文档" | RFC 8414 规范的 `/.well-known/oauth-authorization-server` JSON 文档 |
| CIMD | "客户端元数据 URL" | 客户端 ID 元数据文档（Client ID Metadata Document）：将 HTTPS URL 直接作为 `client_id`，由 AS 主动拉取 JSON。MCP 2026-07-28 首选注册方式 |
| DCR | "自助客户端动态注册" | RFC 7591 规定的 `POST /register`；在当前 MCP 规范中已废弃，仅作兼容兜底 |
| JWKS | "用于 JWT 验签的公钥集合" | JSON Web Key Set，从 `jwks_uri` 拉取，内部按 `kid` 进行哈希索引 |
| Rotate vs Refresh | "更新公钥" | **Rotate（轮换）** = 授权服务器签发/作废签名密钥；**Refresh（刷新）** = 资源服务器重新拉取发布的公钥。资源服务器仅能执行 Refresh |
| 资源指示符（Resource indicator） | "受众参数" | RFC 8707 规定的 `resource` 参数，用于将 Token 强绑定到特定 server |
| `aud` Claim | "受众标识" | JWT 中的 Claim 字段，验签器将其与自身的规范化资源 URL 进行严格字符串比对 |
| 受众重放（Audience replay） | "Token 重放攻击" | 将为 Server A 签发的 Token 拿到 Server B 去尝试调用；由受众校验防御（规范术语：访问令牌特权限制） |
| 混淆代理（Confused deputy） | "代理 Token 滥用" | 拥有静态客户端 ID 的 MCP 代理服务在未获取逐客户端同意授权的情况下盲目转发 Token；与受众重放本质不同 |
| Mix-up 混淆攻击 | "Token 端点走错门" | 客户端被恶意诱导将诚实 AS 派发的授权码拿到攻击者控制的端点去兑换；由客户端依照 RFC 9207 `iss` 校验进行防御 |
| `iss` 白名单 | "受信任的授权服务器集合" | 在受保护资源元数据的 `authorization_servers` 字段中显式声明的受信任列表 |
| `resource_metadata` | "去哪里查找 PRM 文档" | 401/403 质询头 `WWW-Authenticate` 中的标准参数，指向 RFC 9728 元数据文档的获取 URL |
| 公共客户端（Public client） | "Native 或浏览器端客户端" | 无法安全保管 `client_secret` 的客户端类型；依赖 PKCE 机制实现所有权证明 |
| `WWW-Authenticate` | "401/403 响应头" | 携带 `Bearer error=...` 等指令指导客户端如何进行凭据补全与错误恢复的标准 HTTP 响应头 |
