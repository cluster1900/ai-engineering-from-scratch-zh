## 问题

远程MCP सर्वर 可能会读取私有记录、向外部系统写入数据,或触发代价昂贵的运算──身份认证(身份认证) केवल यह स्पष्ट करना होगा कि किसने प्रमाण पत्र प्रदान किया है──而授权 (授权)  प्राधिकरण) निम्नलिखित प्रश्नों का उत्तर भी देना होगाः

- किस प्राधिकरण सर्वर ने यह प्रमाणपत्र जारी किया है?
- यह टोकन किस MCP संसाधन के लिए विशेष रूप से जारी किया गया है?
- किस ग्राहक और किस पुनर्निर्देशित यूआरआई ने इस प्राधिकरण प्रक्रिया को पूरा किया है?
-  संसाधन मालिक (स्रोत मालिक) ने किस ऑपरेशन को विशेष रूप से मंजूरी दी है?
- क्या यह पूर्व निर्धारित अनुरोध अभी भी उस समय की स्वीकृति के दायरे में है?

2026-07-28 संस्करण के अधिकृत विनियमों ने ग्राहक पंजीकरण और जारीकर्ता प्रसंस्करण तंत्र को मजबूत किया। यह ग्राहक आईडी को प्राथमिकता देता है।`application_type`, रफ़्तार 9207 签发人响应,并严禁跨签发人复用凭证──

ये सुरक्षा नियम गैर-राज्य के केंद्रीय समझौते के साथ-साथ बने हुए हैं। वे समझौते के स्तंभ के केंद्रीय हाथों को कभी भी बहाल नहीं करेंगे और न ही फिर से पेश किए जाएंगे।`Mcp-Session-Id`

## 概念

### 明确三大核心角色

- **MCP Client（客户端）：**代表 संसाधन मालिकों发起请求──
- **MCP Resource Server（资源服务器）：**验证 एक्सेस टोकन并提供 MCP 端点服务──
- **Authorization Server（授权服务器）：**认证资源所有者、收集用户同意并签发代币──

संसाधन सर्वर और अधिकृत सर्वर एक ही टीम द्वारा संचालित किए जा सकते हैं, लेकिन दोनों की पहचान और सत्यापन जिम्मेदारियों को पूरी तरह से स्वतंत्र रखना होगा।

### 授权应用于 HTTP 传输层

MCP  अधिकृत विनियम विशेष रूप से HTTP पर आधारित संचरण परतों पर लक्षित है  स्थानीय स्टूडियो आधारित सर्वर  एक ही प्रक्रिया और ऑपरेटिंग सिस्टम के विश्वास सीमा के भीतर चल रहा है, न केवल सतह के लिए  समकक्षता बल्कि स्टूडियो  पर बनावट ब्राउज़र 

 दूरस्थ स्ट्रीमेबल HTTP  ट्रांसफर के लिए, प्रत्येक अनुरोध पर होना चाहिए `Authorization`头部中携带 धारक टोकन。**绝不能**टोकन को URL में रखें

### संरक्षित संसाधनों से डेटा

 संसाधन सर्वर आरएफसी 9728 规范的元数据 के अनुसार जारी करने के लिए जिम्मेदार हैः

```json
{
  "resource": "https://notes.example.com/mcp",
  "authorization_servers": ["https://auth.example.com"],
  "scopes_supported": ["notes:delete", "notes:read", "notes:write"]
}
```

客户端 MCP 资源 URL से निकल, इस डाटा दस्तावेज़ को प्राप्त करें, इनमें से घोषित अधिकृत सर्वर का चयन करें, फिर उस अधिकृत सर्वर का OAuth या OpenID Connect 元データ पुनः प्राप्त करें।

RFC 9728 के प्रसिद्ध URL के निर्माण में, मूल संसाधन पथ को संरक्षित करना आवश्यक है।`https://notes.example.com/mcp`,本课使用的标准路径为`https://notes.example.com/.well-known/oauth-protected-resource/mcp` यदि छोड़ दिया `/mcp`, संभवतः इस डोमेन के नाम पर अन्य संरक्षित संसाधनों के लिए गलत तरीके से चयन किया गया है।

मत प्रदाता के नाम के आधार पर मत अनुमानित प्राधिकरण सर्वरों को मत मत मानना अप्रत्याशित त्रुटि प्रतिक्रियाओं के लिए प्रदाता द्वारा दी गई जानकारीों को मत मानना।

### 验证授权服务器元数据

授权服务器 के डेटा को विभिन्न बिंदुओं तथा समर्थित सुरक्षा नियंत्रण विशेषताओं के बारे में पता लगाया जाना चाहिए:

```json
{
  "issuer": "https://auth.example.com",
  "authorization_endpoint": "https://auth.example.com/authorize",
  "token_endpoint": "https://auth.example.com/token",
  "code_challenge_methods_supported": ["S256"],
  "authorization_response_iss_parameter_supported": true,
  "client_id_metadata_document_supported": true
}
```

强制要求 PKCE 采用 S256 算法──完整记录签发者(issuer)字符串── यह सटीक字符串 होगा ग्राहक के बाद पंजीकरण जानकारी और टोकन 存储 के केंद्रीय सूचक कुंजी(की)──

### पंजीकरण प्राथमिकता के नियमों का पालन करना

यदि ग्राहक और चयनित जारीकर्ता के बीच स्पष्ट पूर्व-निर्धारण संबंध पहले से ही मौजूद है, तो पूर्व-पंजीकृत ग्राहक प्रमाणपत्र का सीधा उपयोग करें। अन्यथा, जब अधिकृत सर्वर घोषणा समर्थित होती है, तो प्रथम-निर्धारित ग्राहक ID (CIMD) केवल आवश्यक समय पर ही बाद में संगत के रूप में वापस लौटने के लिए एक रिटर्न प्रोग्राम के रूप में समाप्त हो जाएगा। यदि दोनों अप्रयुक्त हैं, तो उपयोगकर्ता को फिर से सूचित करें कि वह ग्राहक प्रमाणपत्र में हाथ से प्रवेश करें।

### 优先采用客户端 ID 元数据文档(CIMD)

客户端 ID 元数据文档(CIMD) ने अधिकृत सर्वर के लिए एक HTTPS URL प्रदान किया, जो URL 既是客户端 का एकमात्र पहचानकर्ता है(`client_id`), साथ ही साथ अन्य डेटा अभिलेखागार का प्राप्ति पता भी हैः

```json
{
  "client_id": "https://client.example.com/oauth/metadata.json",
  "client_name": "Notes desktop client",
  "application_type": "native",
  "redirect_uris": ["http://127.0.0.1:8765/callback"],
  "grant_types": ["authorization_code"],
  "response_types": ["code"]
}
```

授权服务器获取并校验该文档──`client_id`⇒ मार्ग में HTTPS URL होना चाहिए, और दस्तावेज़ के आंतरिक कथन का मूल्य उस URL के साथ पूरी तरह से मेल खाना चाहिए।`client_id``client_name``redirect_uris`本例中包含的 `application_type`यद्यपि यह सीआईएमडी की बाध्यकारी आवश्यकता नहीं है, लेकिन इसे अनिवार्य तत्व के रूप में डीसीआर मार्ग में देखा गया है।

### प्रमाणपत्र जारीकर्ता के साथ बलबद्ध होना

```text
issuer_credentials[issuer] = pre_registered_or_dcr_client
tokens[(issuer, resource)] = access_token
```

CIMD  ग्राहक आईडी में अंतर हैः चूंकि यह एक स्व-निर्मित HTTPS URL है, न कि अधिकृत सर्वर द्वारा भेजे गए आंतरिक प्रमाण पत्र, इसलिए एक ही CIMD URL  के पास ट्रांसपोर्ट करने योग्य है  नए विश्वसनीय जारीकर्ता सीधे दस्तावेज़ को खींच सकते हैं और सत्यापित कर सकते हैं, और DCR को पुनः पंजीकृत करने की आवश्यकता नहीं है  लेकिन अधिकृत प्रतिक्रिया और उत्पन्न टोकन  अभी भी नए जारीकर्ता के कुंजी नाम पर संग्रहीत किए जाने से अलग होना चाहिए

### 带 PKCE 的授权码模式

交互式授权流程 में निम्नलिखित चरण शामिल हैंः

1.  生成高 के 随机数`code_verifier`
2. उपयोग SHA-256 派生出 `code_challenge`(S256 方式)
3. 发送授权请求,携带精确的 `client_id``redirect_uri``scope``code_challenge`और `resource`
4.  प्राप्ति अधिकार प्रतिक्रिया, इस प्रतिक्रिया में अधिकार कोड शामिल है `code`, और समर्थन में ले लो`iss`
5.                                                                                                                                                                                                                                                               `iss`पूर्व रिकॉर्ड के साथ पूर्णतः मेल खाता है?
6. उपयोग `code_verifier`、 पूरी तरह से समान वियोज्य URI 及 समान `resource`换代币――
7. प्राप्त टोकन भंडारण में होगा`(issuer, resource)`复合键下――

आरएफसी 8707 से `resource`参数 एक ही समय में दिखाई देता है प्राधिकरण अनुरोध और टोकन अनुरोध में, यह सटीक रूप से अधिकृत MCP सर्वर URI पहचान की है

### 严格校验 `iss`参数

आरएफसी 9207 एक जारीकर्ता से अधिकृत प्रतिक्रिया और दूसरे जारीकर्ता से प्रतिक्रिया के बीच मिश्रण को रोकने के लिए

जब प्रतिक्रिया में उभरते हैं`iss`参数时,将其与记录的发行者进行比较,禁止大小写折叠,末尾斜增删除,默认端口移除或URL 百分号编码规范化―― यदि यह मेल नहीं खाती, तो इस प्राधिकरण कोड का उपयोग करना होगा, यहां तक कि इस प्रतिक्रिया में हमलावर द्वारा नियंत्रित गलत विवरणों को भी प्रदर्शित करना होगा।

यदि अधिकृत सेवाएँ समाहित `iss`, आमतौर पर मुद्रा डेटा में घोषित किया जाता है `authorization_response_iss_parameter_supported: true` आधुनिक ग्राहक, यहां तक कि इस कथन को अनदेखा होने पर भी, एक बार प्रतिक्रिया में शामिल `iss`, भी कड़ाई से इस परीक्षा को निष्पादित करेगा।

## 关键术语

| 术语 | 含义 |
|------|------|
| 受保护资源元数据 | RFC 9728 文档，用于声明资源地址、授权服务器列表及支持的 scopes |
| CIMD | 客户端 ID 元数据文档（Client ID Metadata Document），其 HTTPS URL 即为 OAuth client_id |
| DCR | 动态客户端注册（Dynamic Client Registration），已废弃并仅作为向后兼容路径保留 |
| `application_type` | `native` 或 `web`，用于校验重定向 URI 的合法性规则 |
| PKCE | 包含 verifier 与 S256 challenge 的机制，用于防止授权码拦截攻击 |
| `iss` | RFC 9207 授权响应中的签发者标识符，用于防范 Mix-up 混淆攻击 |
| 资源指示符（Resource indicator） | RFC 8707 参数，用于将 Token 申请显式绑定到目标 MCP 资源 |
| 受众（Audience） | Token 允许被使用的合法资源范围 |
| 权限提升（Step-Up） | 针对当前操作需要的新 scope，发起用户再次同意并获取新 token 的机制 |
| 签发者绑定凭据 | 将客户端注册凭据与 Token 严格按授权服务器签发者物理隔离的存储机制 |
