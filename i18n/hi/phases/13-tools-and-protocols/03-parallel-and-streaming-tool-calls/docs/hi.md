# समानांतर उपकरण कॉल और उपकरण का स्ट्रीमिंग

> तीन स्वतंत्र मौसम पूछताछ यदि क्रमबद्ध निष्पादन,就是三次往返──并行运行后, कुल खपत समय सबसे धीमी एकल调用 तक कम हो जाएगी── अब प्रत्येक सीमा प्रदाता एक ही बारी में कई उपकरण कॉल जारी कर सकता है──收益是真实的;管道细节很微妙──本课会讲解两部分:并行风扇和流媒体论点重组,重点关注 id-相关陷──

**类型：**निर्माण
**语言：**Python(stdlib,थ्रेड पूल + स्ट्रीमिंग हर्न)
**前置要求：**चरण 13 · 02 (गहरे गोता लगाने का कार्य)
**时间：** 75 मिनट

## 学习目标

-  समझाएँ क्यों अस्तित्व `parallel_tool_calls: true`, और जब यह बंद करना चाहिए.
- समानांतर फैन-आउट के दौरान, स्ट्रिम किया जाएगा तर्क टुकड़े 关联到正确的工具-कॉल आईडी──
- पहले, इसे भाग `arguments`स्ट्रिंग 重组为完整 JSON。
- 运行一个三城市天气基准, क्रमशः बनाम समानांतर विलंबता प्रदर्शित करना

## 问题

没有平行电话 时,一个代理 回答 बेंगलुरु, टोक्यो और ज़िურიख में मौसम कैसा है 会这样做:

```
user -> LLM
LLM -> call get_weather(Bengaluru)
host -> run executor, reply with result
LLM -> call get_weather(Tokyo)
host -> run executor, reply with result
LLM -> call get_weather(Zurich)
host -> run executor, reply with result
LLM -> final text answer
```

三次 LLM 往返, प्रत्येक बार फिर से भुगतान करने के लिए निष्पादक विलंबता──大约是理想壁表时间的4倍──

उपयोग समानांतर कॉलः

```
user -> LLM
LLM -> call get_weather(Bengaluru); call get_weather(Tokyo); call get_weather(Zurich)
host -> run all three executors concurrently, reply with three results
LLM -> final text answer
```

एक बार LLM 往返── निष्पादक 时间是三者的最大值,而不是总和──在OpenAI、Anthropic 和 Gemini 上的生产基准显示, फैन-आउट वर्कलोड के लिए, वॉल-क्लॉक 60% से 70% तक कम हो सकता है──

代价是相关性复杂性── जब तीन调用乱序完成, तो आपके परिणामों को संगत होना चाहिए `tool_call_id`, मॉडल  इन्हें  एक साथ  रख सकता है  जब परिणाम  स्ट्रीम  रूप में लौटता है, तो आपको पहले  के कुछ अंशों को  के अंशों को  में  को  को  को  पूर्ण JSON में  को  को  में

### आईडी सहसंबंध

मॉडल प्रकाशित प्रत्येक调用 एक है `id`◊ होस्ट  लौटने के प्रत्येक परिणाम में एक ही आईडी शामिल होनी चाहिए ◊ इस आईडी के बिना, परिणाम स्पष्ट नहीं होगा ◊

- **OpenAI。**प्रत्येक उपकरण भूमिका संदेश ऊपर `tool_call_id`
- **Anthropic。**प्रत्येक `tool_result`ब्लॉक ऊपर की `tool_use_id`
- **Gemini。**प्रत्येक `functionResponse`ऊपर की `id`(Gemini 3 及以上;Gemini 2 按名匹配,这会在同名的并行调用中出错)

### 并发运行 कॉल

मेजबान अपने स्वयं के धागे में 会在自己的 धागे、coroutine或远程工作者 上运行每个调用执行器──最简单的使用`asyncio.gather`या संरचित समवर्तीता──完成顺序不可预测,id 才是标识符──

एक सामान्य त्रुटिः कॉल-लिस्ट पर क्रमशः प्रतिक्रिया परिणाम, न कि पूरा क्रमशः प्रतिक्रिया पर। यह आमतौर पर काम कर सकता है, क्योंकि मॉडल केवल चिंता करता है।`tool_call_id`, लेकिन यदि कोई परिणाम खो गया या दोहराया गया, तो अव्यवस्थित क्रम प्रस्तुत करेगा, जिससे अनुक्रम अधिक कठिन हो जायेगा।

### स्ट्रीमिंग टूल कॉल

मॉडल से धारा  रूप में आउटपुट`arguments`会分片到达──三条平行通话的三条分流 会在线上交错──你需要为每个ID 准备一个积累器──

按供应商的结构:

- **OpenAI。**हर टुकड़ा है`choices[0].delta.tool_calls[i].function.arguments`(भागल स्ट्रिंग)  टुकड़ा 携带 `index`(कॉल लिस्ट मध्य की स्थिति) ✿ आप के अनुसार सूचकांक 累积,在 `id`首次出现时读取它, और `finish_reason = "tool_calls"`时解析 JSON。
- **Anthropic。**स्ट्रीम घटनाएँ है `message_start`, फिर प्रत्येक ब्लॉक एक `content_block_start`, प्रकार `tool_use`( id 、name 、空 input शामिल है) ⋅`content_block_delta`घटनाएँ 携带 `input_json_delta`टुकड़े-टुकड़े`content_block_stop`关闭每块.
- **Gemini。** `streamFunctionCallArguments`(जुम्मन 3 及以上)`functionCallId`इस प्रकार, कॉल को जा सकता है, एक पूर्ण कॉल पर वापस लौटें।

### आंशिक JSON और विश्लेषण-शुरुआती 陷

`arguments`完整之前不能解析──像 `{"city": "Beng`इस तरह के आंशिक JSON नहीं है वैध JSON, जाएगा छोड़ दिया गया है।`finish_reason = "tool_calls"`、 मानव के `content_block_stop`, या Gemini के स्ट्रीम-एंड घटना,, केवल तब तक कोशिश करने के लिए `json.loads`更健壮的做法是使用增量 JSON पार्सर,在结构完成时产出事件;OpenAI का स्ट्रीमिंग गाइड 推这种做法,用于实时 思考指标的 UX प्रदर्शित करनाBrace-counting 作为完整性测试并不可靠引用字符串或逃逸内容中的 braces会导致虚假积极), केवल एक अनौपचारिक डिबग हेरिस्टिक के रूप में ही उपयोग किया जा सकता है

### बेंचमार्कः अनुक्रमिक बनाम समानांतर

`code/main.py`मध्य हर्नस 模拟三个执行器,延迟 分别为 400、600 和 800 ms── क्रमशः 运行总共需要 1800 ms── समानांतर 运行需要最大(400, 600, 800) = 800 ms──差异是常量,而不是比例,所以节省会随着工具数量 增长──

वास्तविक दुनिया ध्यानः समानांतर कॉल 会给下游 एपीआई 增加压力──对利率有限服务做10路风扇-out 会失败──Phase 13 · 17 会覆盖网关级压力;retry semantics 计划放在未来阶段──

### स्ट्रीमिंग प्रशंसक बाहर की दीवार घड़ी

यदि मॉडल स्वयं स्ट्रीम के रूप में आउटपुट होता है, तो आप किसी कॉल के तर्क को पूर्ण होने के तुरंत बाद निष्पादित करना शुरू कर सकते हैं, बजाय सभी कॉल को अंतिम रूप देने के। यह एक अनुकूलन है जिसे ओपनएआई ने रिकॉर्ड किया है, लेकिन सभी एसडीके को उजागर नहीं किया गया है।

| `parallel_tool_calls` | “OpenAI 的 flag” | 启用或禁用 multi-call emission |
| `disable_parallel_tool_use` | “Anthropic 的反向开关” | Opt-out flag；默认启用 parallel |
| Tool call id | “Correlation handle” | 每次调用的标识符，result message 必须原样回显 |
| Accumulator | “Stream buffer” | 用于 partial `arguments` chunks 的 per-id string buffer |
| Out-of-order completion | “最快的先返回” | Parallel calls 以不可预测的顺序完成；ids 是粘合剂 |
| Dependency graph | “Ordering constraints” | 某些 tools 的输出会进入其他 tools 的输入；不能 parallelize |
| Parse-early trap | “JSON.parse 炸了” | 尝试解析不完整的 `arguments` string |
| `streamFunctionCallArguments` | “Gemini 3 feature” | 带有每次调用 unique id 的 streamed argument chunks |
| Completion-order reply | “不要等全部完成” | 结果一到就回复，并按 id 标记 |
