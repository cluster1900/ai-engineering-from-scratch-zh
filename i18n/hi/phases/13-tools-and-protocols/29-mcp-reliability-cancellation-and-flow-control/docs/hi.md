## 核心问题

सबसे महंगी वितरित प्रणाली की कमीएं सामान्य तरीके से निष्पादित होने के बाहर छिप जाती हैं।

客户端调用一个工具――服务端开始执行――进度通知源源不断发发出――反向代理在中间缓冲了事件流――客户端触发超时并断开连接――服务端恰好在 1毫秒后完成业务处理――客户端使用新的 JSON-RPC id 发起重试――于是, इस लेखन ऑपरेशन (((परिवर्तन) को दो बार दोहराया गया――

प्रत्येक घटक अपने स्थान से कोई त्रुटि नहीं है, लेकिन पूरी प्रणाली पूरी तरह से टूट गई है।

MCP 规范 परिभाषित संदेश प्रारूप और संचरण स्तर व्यवहार, लेकिन आपके अनुप्रयोग अभी भी व्यक्तिगत रूप से जिम्मेदार होना चाहिएः

- 时间预算(समय के बजट);
- 业务等性 (व्यवसायिक स्वतंत्रता)
- 有界队列 (सीमित कतारें)
- 重试分类(रिटायरमेंट वर्गीकरण);
- 持久化任务状态 (स्थायी कार्य स्थिति)
- 重连与重新拉取策略 (पुनर्संपर्क और पुनर्वहन नीति)

इस पाठ्यक्रम में ये निर्णय एक निश्चितता के सिम्युलेटर में बनाए जाएंगे। यहाँ नींद का कोई परिचय नहीं है। वास्तविक नेटवर्क सॉकेट या随机故障। आप घटनाओं के पूर्ववर्ती क्रम पर सीधे नियंत्रण करेंगे।

## अनुरोध हटाने के लिए ट्रांसफर लेयर के अनुसार

इस प्रकार के संचरण प्रोटोकॉल का उपयोग करने के बावजूद, ग्राहक का इरादा एक ही हैः वर्तमान में निष्पादित किए जा रहे परिणामों की आवश्यकता नहीं है।

### स्टूडियो

स्टूडियो  एकल条共享的双向通道──客户端发送一个通知:

```json
{
  "jsonrpc": "2.0",
  "method": "notifications/cancelled",
  "params": {
    "requestId": 41,
    "reason": "User closed the operation"
  }
}
```

इस सूचना का 即发即弃(आग-और-भुल)  से संबंधित है।

服务端应停止工作、释放资源,并不再发送响应已取消的请求── यदि अनुरोध अज्ञात, पूरा हो चुका है, या सुरक्षित रूप से विराम नहीं हो सकता है, तो सेवा端 सुरक्षित रूप से इस रद्द सूचना को अनदेखा कर सकता है──

形式错误、 अज्ञात अनुरोध या पूर्ण अनुरोध के लिए रद्द सूचना को सेवा में चुपचाप अनदेखा किया जाएगा। यदि ये आमंत्रित किए गए विज्ञापन को नए गलत सूचना संदेश में परिवर्तित किया जाए, तो केवल अधिक विज्ञापन समस्याएं उत्पन्न होंगी।

### स्ट्रीम करने योग्य HTTP

现代 Streamable HTTP 为每一个请求分发独立的 HTTP 响应或 SSE 响应流──客户端通过**直接关闭该请求的响应流**एक संकेत भेजने के लिए।

कृपया सामान्य HTTP अनुरोध पोस्ट भेजें`notifications/cancelled`                                                                                                                                                                                                                                                              

एक बार सेवा के अंत में कनेक्शन टूट जाने के बाद, यह काम करना बंद कर देना चाहिए और इस अनुरोध के लिए कोई भी बाद की सूचना नहीं भेज सकती है।

### 服务端发起的取消范围极其有限

服务端绝不能使用 `notifications/cancelled`स्टूडियो 传输 पर, सेवा端 के प्रारंभ के बाद से ही समाप्त हो जाता है।`subscriptions/listen`监听请求―― इस बेहद संकीर्ण मार्ग को ग्राहक द्वारा उत्पन्न नियमित अनुरोधों से कठोर भेदभाव करना होगा

## 取消 एक खेल है

दोनों घटनाओं का क्रम पूरी तरह से कानूनी है।

### 取消获胜

```text
request starts（请求启动）
client sends cancellation signal（客户端发送取消信号）
server marks request cancelled（服务端将请求标记为已取消）
worker reaches completion（工作线程执行完成）
server suppresses the response（服务端抑制并不发送响应）
```

### 完成获胜

```text
request starts（请求启动）
worker commits the result（工作线程提交业务结果）
server sends the response（服务端发送响应）
cancellation arrives late（取消信号迟到）
server ignores the late notification（服务端忽略迟到的通知）
```

客户端 को भी अपने पहले से ही त्याग दिए गए अनुरोधों के प्रति देरी से प्रतिक्रिया को सक्रिय रूप से अनदेखा करना होगा।

```figure
mcp-reliability-race
```

本课的 `RequestCoordinator`एक ही अंतिम रिकॉर्ड का रिकॉर्ड होगा।`complete()`किसी भी प्रतिक्रिया को वापस नहीं किया जाएगा; तथा देर से समाप्त होने की सूचना को भी पूर्ण रिकॉर्ड में परिवर्तन नहीं किया जा सकता है।

## 超时机需要两个小时

单一的无活动 (无活动) 计时器是远远不够的──

एक ही समय में दो समय सीमाएं लागू करनी चाहिएः

1. **空闲超时（Idle timeout）**अनुरोध: बहुत समय में कोई उपयोगी गतिविधि नहीं हुई है।
2. **最大超时（Maximum timeout）**: अनुरोध से शुरू होने पर समय की गणना करने का पूर्ण भौतिक समय बजट

持续产生的进度事件(प्रगति)**绝不能**推迟或消除最大截止时间──

```text
start: 0 ms
progress: 400 ms
progress: 800 ms
progress: 1200 ms
idle timeout: 500 ms
maximum timeout: 2000 ms
```

1500 ms में, अनुरोध अभी भी सक्रिय स्थिति में है, क्योंकि पिछली प्रगति घटना से दूरी केवल 300 ms से अधिक है। लेकिन 2000 ms में, अधिकतम समय सीमा अनुरोध को रद्द करने के लिए मजबूर करेगी, भले ही 1999 ms में एक नई प्रगति घटना उत्पन्न हो।

进度通知是可选的. सेवा端完全可以接受一个进度令牌 (进度令牌)  प्रगति टोकन)  लेकिन कार्यान्वयन के दौरान कोई अपडेट नहीं भेजता। 

एमसीपी के प्रगतिशील मूल्य को एक बार बढ़ाया जाना चाहिए। पूरा होने या समाप्त होने के बाद, सभी सूचनाएं तुरंत बंद हो जानी चाहिए।

## अनुरोध取消不等于 `tasks/cancel`

इन दोनों तंत्रों ने जीवन चक्र के स्तरों के विषय में पूरी तरह से भिन्न समाधान प्रदान किए हैं।

| 机制 | 作用目标 | 线路信号 | 成功意味着什么 |
|-----------|--------|--------|--------------------|
| stdio 上的请求取消 | 单次在途 RPC | `notifications/cancelled` | 客户端放弃了该请求；若可行服务端应当停止执行 |
| HTTP 上的请求取消 | 单个在途响应流 | 关闭该流 | 客户端放弃了该请求；若可行服务端应当停止执行 |
| `tasks/cancel` | 单个持久化 Task | 普通 MCP 请求 | 服务端已确认收到取消意图 |

`tasks/cancel`                                                                                                                                                                                                                                                              `working`状态, जब तक किसी चेक पॉइंट पर कामगार (checkpoint) ने पहचान कर ली है कि वह चिह्न हटा चुका है; काम भी हो सकता है कि वह पहचान कर ली है कि वह चिह्न समाप्त होने से पहले ही सफलतापूर्वक निष्पादित हो चुका है।

जब HTTP connect टूट जाता है,**绝不要**清除持久化任务的状态――创建任务的初衷正是让其生命周期能够超越单次请求与单条连接的限制――

## नई JSON-RPC आईडी  बिल्कुल 等性 के बराबर नहीं है

JSON-RPC id  केवल एक अनुरोध और प्रतिक्रिया से जुड़े लिए उपयोग किया जाता है, वे अपने आप में व्यवसायिक संचालन का प्रतिनिधित्व नहीं करते हैं

假设客户端 एक खाता खाता                                                                                                                                                                                                                                                           `41`), मध्यस्थता में सेवा के उत्तर खो गया, उसके बाद ग्राहक आईडी का उपयोग किया।`42`发起重试―― सेवा端 देखते हैं कि दो अलग-अलग संदेश हैं―― यदि अनुप्रयोग परत की एकमात्र पहचान नहीं है, तो सेवा端 को यह पता नहीं चल सकता कि वे एक ही खाते के अनुरोध का प्रतिनिधित्व करते हैं――

等键 (इदम् पेन् सेन्सी कुंजी) स्पष्ट रूप से व्यापारिक इरादे का प्रतिनिधित्व करता हैः

```json
{
  "name": "charge_account",
  "arguments": {
    "account": "acct-7",
    "cents": 1200,
    "idempotencyKey": "checkout-7"
  }
}
```

服务端会持久化记录:

- 等键;
- 操作参数的哈希指纹(argument fingerprint);
- 已提交的执行结果──

समान कुंजी और समान तत्व सीधे पूर्व भंडारण के परिणामों को वापस कर देंगे। यदि एक ही कुंजी में अलग-अलग तत्व होते हैं, तो इसे दृढ़ता से अस्वीकार कर दिया जाएगा।

### 账本边界必须具有原子性和持久性

निम्नलिखित कार्यान्वयन प्रक्रिया अत्यंत खतरनाक तथा असुरक्षित हैः

```text
check key（检查键是否存在）
run mutation（执行写操作）
store result（存储执行结果）
```

 दो并发工人 एक ही समय में यह पता लगाते हैं कि यह कुंजी मौजूद नहीं है, और एक ही समय में इस दुष्प्रभावों के साथ लेखन ऑपरेशन को निष्पादित करते हैं।

इस पाठ्यक्रम का उपयोग फ़ाइल आधारित SQLite 账本──利用 `BEGIN IMMEDIATE`एक ही लेनदेन में सभी क्रमबद्ध किए गए निष्पादन कैलकुलेटर तथा परिणाम भंडारण के लिए एक ही लेनदेन में एक ही कुंजी का परीक्षण करना, केवल एक ही वास्तविक व्यापार निष्पादन और प्रस्तुत किए गए परिणामों का रिकॉर्ड करना, भले ही दो स्वतंत्र खाता कनेक्शन एक ही कुंजी का उपयोग करके एक ही खाता खोलें या फिर से खोलें, यह इतिहास अभी भी पूरी तरह से संरक्षित है।

सभी रिटर्न वैल्यूज भंडारित JSON के माध्यम से पुनः पुनः पुनः क्रमबद्धता उत्पन्न होते हैं।

模拟器 में व्यवसायिक दुष्प्रभाव एक ही SQLite कार्य में प्राप्ति और गणना उपकरण शामिल हैं। उत्पादन वातावरण में, वास्तविक भुगतान, कंटेनर तैनाती या बाहरी तृतीय पक्ष एपीआई का उपयोग, कभी भी स्थानीय डेटाशीट पर निर्भर नहीं है।

### 重试决策矩阵

पुनः परीक्षण तर्क को प्राप्त करने से पहले, पुनः परीक्षण को स्पष्ट रूप से किया जाना चाहिए।

| 类别 | 示例 | 重试规则 |
|------|---------|------------|
| 安全（Safe） | 无副作用的确定性读操作 | 在明确故障边界后，可使用新的 JSON-RPC id 直接重试 |
| 有条件（Conditional） | 具备持久化幂等键的写操作（Mutation） | 必须使用完全相同的幂等键和完全相同的参数发起重试 |
| 不安全（Unsafe） | 未提供业务去重机制的写操作 | 严禁自动重试；必须先进入人工或系统对账调和流程 |

工具描述符中附带的 `readOnlyHint`和 `idempotentHint`केवल अविश्वसनीय बाहरी संकेतों पर ही भरोसा किया जा सकता है। वास्तविक पुनः परीक्षण सुरक्षा पूरी तरह से अनुप्रयोग स्तर के समझौते और सेवा के अंत के तहत कार्यान्वयन पर निर्भर करती है।

## 背压是正确性 का हिस्सा

एसएसई उत्पादक प्रगति घटनाओं के उत्पादन की गति, ग्राहक, एजेंट या नेटवर्क लिंक की खपत क्षमता से बहुत अधिक हो सकता है।

                                                                                                                                                                                                                                                              

进度通知是可替代的──同一进度令牌 के लिए, पिछली तक के进度数值 स्वाभाविक रूप से पूर्व के पुराने मूल्य को प्रतिस्थापित करते हैं──然而, अंतिम JSON-RPC 响应绝对不可替代的──

इस वर्ग को प्राप्त करने के लिए निम्नलिखित प्रवाह नियंत्रण रणनीति को लागू किया गया हैः

1. 合并(Coalesce) उसी令牌相邻的进度更新;
2. जब कक्ष क्षमता सीमा तक पहुंचता है, तो सबसे पुराने प्रगति डेटा को छोड़ दिया जाता है;
3.  घटनाक्रम को पहचानने के लिए अधिकार डेटा पुनः प्राप्त करने की आवश्यकता है
4. 始终完整保留最终响应;
5. यदि अंतिम प्रतिक्रिया को बनाए रखने के लिए किसी अन्य अंतिम प्रतिक्रिया को त्यागना आवश्यक हो तो इस स्थिति को अस्वीकार करना चाहिए।

यह स्पष्ट पुनर्स्थापना तंत्र के लिए एक रणनीति है।

### 代理缓冲问题

服务端可能在完美流式输出中,而中间的反向代理却在私积事件缓冲中.

 SSE 响应 के लिए निम्नलिखित प्रतिक्रिया के शीर्षकों को निम्न में से एक के रूप में प्रस्तुत किया जाना चाहिएः

```http
Content-Type: text/event-stream
Cache-Control: no-cache
X-Accel-Buffering: no
```

2026 वर्ष का स्ट्रीमेबल HTTP 规范强烈建议配置 `X-Accel-Buffering: no`, ताकि एक समन्वित एजेंट सर्वर (जैसे कि Nginx) तुरंत ग्राहक को घटनाओं को भेज सके।

 दीर्घकालिक स्थिरता में रहने के लिए, SSE को नियमित रूप से भेजने की आवश्यकता है 注释行(保活心跳):

```text
:
```

客户端会自动忽略注释行──中间代理设备则能看到网络活动,从而避免断断看似空的连接──

传输保活不等于业务进步――绝不能因为收到传输层的保活注释就顺带重置业务操作的语义空超时计时器――

## पुनः प्राप्त करने का अर्थ है

`subscriptions/listen`घटनाक्रमक्रम दुर्घटनाक्रम के बादः

## हस्तलिखित

### `RequestCoordinator`

-  अधिकतम दो बार के लिए अनुरोध और रखरखाव के समय के साथ प्रारंभ करना;

- स्टूडियो और HTTP के बीच विनियमन उत्पन्न करने के लिए रद्द सिग्नल;
- 忽略非法的取消通知;
-  स्पष्ट निर्णय रद्द करने और पूरा करने के बीच अंतिम स्थिति;
- 确保服务端发起的取消仅用于工作室 订阅。

### `MutationLedger`

- 演示 व्यापारिक कुंजी की कमी के मामले में, दो बार विभिन्न JSON-RPC आईडी का उपयोग करने से दो बार दोहराई गई निष्पादन होगी;
- फ़ाइल आधारित SQLite कार्य क्रमबद्ध की जाँच, व्यवसाय परिणामों का अनुकरण, निष्पादन कैलकुलेटर और परिणाम प्रस्तुत करना;
- 支持跨多个独立账本连接, समान等键和完全一致参数 पर संपूर्ण भार
-  समान कुंजी का उपयोग करने से इनकार करना लेकिन परिवर्तन करने के अनुरोध;
-  प्रतिरक्षात्मक गहराई से प्रतिलिपि, पुनः खोलने के बाद भी पूर्ण रूप से जमा किए गए डेटा को संरक्षित किया गया है

## 交互式 प्रयोग

नींद में कोई देरी नहीं होने की स्थिति में, चार विशेष घटनाओं को पहले और बाद में क्रमशः

1. 启动请求 `A`,将其取消,随后调用 `complete()`
2. 启动请求 `B`, इसे पूरा करने के बाद, देर से भेज दिया गया
3. 启动请求 `C`, प्रत्येक समय में अपूर्व समय से पहले ही प्रगत घटनाओं को भेजता है, लेकिन अंततः अधिकतम अपूर्व समय के मूल्य को तोड़ देता है।
4. स्ट्रीमेबल HTTP पर प्रारंभ अनुरोध`D`,并直接关闭其响应流──

 प्रत्येक घटना के लिए, रिकॉर्डः

- अनुरोध अंतिम स्थान के अंतिम स्थिति;
- यदि अंतिम प्रतिक्रिया उत्पन्न हुई है;
- संचार मार्ग पर प्रदत्त उपेक्षा संकेत का विशिष्ट रूप;
- 客户端 को सक्रिय रूप से किसी घटना को अनदेखा करना चाहिए।

फिर दृश्य होगा `D`改为工作传输―― व्यवसायिक संचालन पूरी तरह से संगत है, लेकिन संचार मार्ग पर उत्पन्न होने वाले उपभोग संकेतों में परिवर्तन होना अनिवार्य है―

## 生产环境故障模式

| 故障现象 | 观察到的表象 | 正确处理方案 |
|---------|--------------------|------------------|
| HTTP 客户端 POST 发送取消通知 | 服务端与客户端对请求的生命周期产生分歧 | 直接关闭该请求专有的 SSE 响应流 |
| 服务端在接受取消后依然回传响应 | 客户端收到一份已无法使用的陈旧无用结果 | 当取消获胜时停止业务计算并抑制所有后续消息 |
| 进度通知无限重置所有超时时钟 | 挂起卡死的任务永久占用资源无法退出 | 维持一个独立的全局绝对最大超时硬上限 |
| 将新的 RPC id 当成请求去重依据 | 扣款、发布或删除操作被多次重复执行 | 在应用层引入并强制校验持久化幂等键 |
| 键检查与业务副作用彼此分离 | 并发执行的多个 worker 同时判定键不存在 | 将键占位、副作用记录与结果提交放入单次原子事务 |
| 在多副本集群中使用内存级账本 | 节点重启或换到另一台机器后遗忘了先前的提交 | 使用持久化共享存储或依赖上游系统的幂等支持 |
| 直接返回底层存储的可变对象引用 | 调用方的内存修改意外污染了后续重放结果 | 将提交结果序列化存储，返回时构造深拷贝副本 |
| 相同的键被复用于篡改后的参数 | 单个幂等键混淆了两种不同的业务意图 | 持久化记录并校验调用参数的哈希指纹 |
| 进度通知队列无界增长 | 遇到慢消费者时服务内存持续飙升直至 OOM | 在容量限制内对可替代的进度通知进行合并与淘汰 |
| 在高压下误丢弃了最终响应 | 客户端永远无法获知该请求的最终成败 | 预留专用容量或只淘汰进度通知，绝不丢弃最终响应 |
| 反向代理缓冲了 SSE 事件 | 进度事件呈突发性到达，或在全部执行完后才下发 | 禁用代理缓冲（`X-Accel-Buffering: no`）并调整代理超时 |
| 盲目假定支持 `Last-Event-ID` | 客户端尝试从服务端根本不支持的位点续传 | 使用新请求重连并向权威数据源全量拉取 |
| 所有客户端在断开后同一瞬间重连 | 系统恢复的瞬间引发严重的次生雪崩风暴 | 采用带上限保护、结合随机抖动的指数退避重连机制 |
| 将 Task 的确认回执当成已完成取消 | 前端界面显示已停止，而后台 worker 仍在计费运行 | 持续轮询 Task 状态直到其真正进入终态 |

## 关键术语

| 术语 | 含义 |
|------|---------|
| 请求取消（Request cancellation） | 放弃单次处于在途状态的 MCP RPC 请求 |
| 取消竞态（Cancellation race） | 终态执行完成与取消信号抵达之间的时序争夺 |
| 空闲超时（Idle timeout） | 距离上一次产生有效请求活动的最大允许时间 |
| 最大超时（Maximum timeout） | 从请求开始时刻算起、不受进度通知影响的全局绝对时间上限 |
| 幂等键（Idempotency key） | 唯一标识单次特定业务意图的应用层去重标识符 |
| 原子账本（Atomic ledger） | 将键校验、副作用记录与结果提交绑定为不可分割单元的持久化存储 |
| 背压（Backpressure） | 在生产者生成速度超过消费者处理能力时施加的流量控制机制 |
| 进度合并（Progress coalescing） | 用更新的权威进度数值替换掉旧的进度更新 |
| 权威重拉（Refetch） | 在数据流中断或出现断层后，向权威接口重新读取当前全量状态 |
| 抖动（Jitter） | 在重试退避间隔中引入的随机偏移，用于在时间轴上打散瞬时并发高峰 |
