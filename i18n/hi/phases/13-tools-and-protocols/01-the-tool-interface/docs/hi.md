# उपकरण इंटरफ़ेस  क्यों एजेंट  संरचनात्मक I/O की आवश्यकता है

> 语言模型会生成代币――程序会执行动作―― दोनों के बीच अंतर उपकरण इंटरफ़ेस हैः एक अनुबंध,让模型能够请求某一动作,并让主机执行它――2026 वर्ष के प्रत्येक प्रकार के स्टैकOpenAI、Anthropic 和 Gemini 上的函数 calling;MCP के `tools/call`A2A के कार्य भागों में एक ही चार चरण चक्र के विभिन्न कोड होते हैं।

**Type:** Learn
**Languages:** Python (stdlib, no LLM)
**Prerequisites:** Phase 11 (LLM completion APIs)
**Time:** ~45 minutes

## 学习目标
-  व्याख्या क्यों एक केवल ग्रंथ उत्पन्न करने वाला LLM वास्तविक दुनिया पर अकेले कार्य नहीं कर सकता
- 画出四步工具-call loop (चित्रण → निर्णय → निष्पादन → अवलोकन)
- एक उपकरण विवरण 写成三部分:name、JSON Schema input,以及确定性的执行函数──
- 区分纯工具和副作用工具,并说明为什么这种分分对安全很重要──

## 问题
LLM 输出是下一个代币的概率分布──这是它的全部输出表面── यदि आप एक चैट मॉडल बेंगलुरु 现在天气如何 से पूछते हैं, तो यह एक वाक्य लिख सकता है जो समझ में आता है, लेकिन यह मौसम एपीआई में नहीं जा सकता──那句话可能只是巧合正确,也可能已经过了时间三天──

弥合 इस अंतर सही है उपकरण इंटरफ़ेस का उद्देश्य। होस्ट प्रोग्राम आपका एजेंट रनटाइम、Claude Desktop、ChatGPT、Cursor, या एक स्वनिर्धारित स्क्रिप्ट मॉडल को एक सेट समायोज्य उपकरण के लिए जारी करेगा।

इस अनुबंध का पहला संस्करण जून 2023 में ओपनएआई के फंक्शन पैरामीटर प्रारूप में जारी किया गया था।`tool_use`ब्लॉक── मिथुन  कुछ महीने बाद शामिल `functionDeclarations`◊ अब प्रत्येक प्रदाता एक ही आकार का खुलासा किया गया हैः एक JSON-Schema 标注类型 के उपकरण सूची में प्रवेश करें, एक JSON-payload उपकरण कॉल आउटपुट करें।

चार चरण चक्र इन प्रणालियों के मूल स्तर की अपरिवर्तनीयता है।

## 概念
### चरण 1: वर्णन करें

मेजबान प्रत्येक उपकरण के लिए तीन शब्द प्रयोग करता है

- **Name.**एक स्थिर, मशीन पठनीय पहचानकर्ता।`get_weather`, बजाय  मौसम की बात 🏼
- **Description.**एक段自然语言简介──जब उपयोगकर्ता किसी विशिष्ट शहर की वर्तमान मौसम स्थिति से पूछताछ करता है तो उपयोग करना── मत उपयोग करें ऐतिहासिक डेटा──
- **Input schema.**एक वर्णन उपकरण तर्क का JSON योजना ऑब्जेक्ट(ड्राफ्ट 2020-12)。

模型会收取这个列表――现代供应商会使用供应商特定的模板将这些声明序列化进系统提示,因此作为调用方,你只需要处理结构化形式――

### चरण दो: निर्णय लें

给定用户消息和可用工具,模型会选择三种行为之一──

1. **直接用文本回答**◊ उपकरण कॉल नहीं करना
2. **调用一个或多个 tools。**输出 संरचनात्मक कॉल ऑब्जेक्ट्स──在 `parallel_tool_calls: true`निम्न(OpenAI 和 Gemini 默认启用,Anthropic 需要选择), मॉडल एक मोड़ में कई कॉल आउटपुट कर सकता है
3. **拒绝。**सख्त मोड में संरचित आउटपुट एक प्रकार के उत्पन्न कर सकते हैं `refusal`ब्लॉक, बजाय कॉल.

एक उपकरण कॉल उपयोगिता लोड है तीन स्थिर खण्डः कॉल `id`、 उपकरण `name`, तथा JSON `arguments`                                                                                                                                                                                                                                                              

### चरण 3: निष्पादित करें

मेजबान  प्राप्त कॉल, के अनुसार घोषित स्कीम  सत्यापन तर्क,并运行执行器── निष्क्रिय तर्क का अर्थ है मॉडल प्यासग्रस्त 某段段或使用错类型 यह कमजोर मॉडल पर बहुत आम विफलता मोड है── उत्पादन वातावरण में मेजबान निष्क्रिय तर्क के लिए आमतौर पर तीन चीजों में से एक करते हैंः तेजी से विफल और मॉडल को त्रुटि का खुलासा; सीमित पार्सर के साथ 修复 JSON; या शीघ्र में सत्यापन त्रुटि शामिल 后重试模型──

निष्पादक स्वयं बस साधारण कोड है। पाइथन、टाइपस्क्रिप्ट、शेल कमांड、डेटाबेस क्वेरी── यह एक परिणाम उत्पन्न करेगा, आमतौर पर स्ट्रिंग, लेकिन यह किसी भी JSON मान या संरचित सामग्री ब्लॉक में भी हो सकता है।

### चौथा चरण: अवलोकन

मेजबान उपकरण परिणाम  जोड़ने के लिए बातचीत में`id``tool`भूमिका संदेश),并再次调用模型──模型现在在文本中拥有工具输出,可以生成最终答案,或请求更多电话── यह प्रक्रिया तब तक जारी रहेगी जब तक मॉडल आउटपुट कॉल बंद नहीं कर देता, या होस्ट 代次数的安全上限  तक नहीं पहुंच जाता──

### क्यों सीधे सीधे  मॉडल JSON आउटपुट नहीं?

让模型使用JSON 回复是函数调用出现前模式──它在边界模型上大约有5%到15%的时间会失败,在更小模型上失败率更高──失败模式包括缺少大括号、尾随号、幻觉字段 和错误类型──然后你就需要一次JSON维修通过、一次重试,或一个限制式解码器──

मूल फ़ंक्शन कॉल करना बेहतर है, कारण है तीन बिंदुएँ। पहला, प्रदाता मॉडल के लिए सटीक कॉल आकार का उपयोग करेगा अंत से अंत तक प्रशिक्षण करने के लिए, इसलिए सख्त मोड नीचे की मान्य-JSON दर 98% से 99% तक बढ़ जाएगी। दूसरा, कॉल का उपयोग लोड अपने प्रोटोकॉल स्लॉट में स्थित है, बजाय मुक्त-पाठ के अंदर। इसलिए उपकरण कॉल  कभी भी उपयोगकर्ता के दृश्य प्रतिक्रिया में नहीं बह जाएगा।`tool_use`、जमेनी के `responseSchema`) अनिवार्य योजना अनुपालन―输出保证能够通过验证―

## 关键术语
| Term | What people say | What it actually means |
|------|----------------|------------------------|
| Tool | “模型可以调用的东西” | name + JSON-Schema-typed input + executor function 组成的三元组 |
| Function calling | “Native tool use” | Provider-level API 支持，用于输出结构化 tool calls，而不是 prose |
| Tool call | “模型发出的行动请求” | 模型输出的一个 JSON payload，包含 `id`、`name`、`arguments` |
| Tool result | “tool 返回的内容” | executor 的输出，被包装在带有匹配 id 的 `tool` role message 中 |
| Parallel tool calls | “一次多个 calls” | 一个 model turn 中的多个 call objects，彼此独立，并可通过 id 排序 |
| Strict mode | “Guaranteed JSON” | Constrained decoding，强制模型输出通过已声明 schema 的验证 |
| Pure tool | “Read-only tool” | 无 side effects；可以安全地重新运行 |
| Consequential tool | “Action tool” | 会改变 external state；需要 gate、audit 或用户确认 |
| Four-step loop | “The tool-call cycle” | describe → decide → execute → observe |
| Host | “Agent runtime” | 持有 tool registry、调用模型并运行 executor 的程序 |
