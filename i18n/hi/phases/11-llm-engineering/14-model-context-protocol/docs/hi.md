## 问题背景

आपके अनुप्रयोगों को डेटाबेस पूछताछ, दिनचर्या संचालन और फ़ाइल पढ़ने की सुविधाओं की आवश्यकता होती है। यदि एक एकीकृत संचार प्रोटोकॉल नहीं है, तो प्रत्येक एआई होस्ट को अपने स्वयं के खोज, समायोजन, त्रुटि प्रसंस्करण, प्रसारण और पहचान चिपचिपाहट कोड को पूरी तरह से समान क्षमता के लिए लिखने की आवश्यकता होती है।

MCP ने इस विशाल N×M 集成矩阵 को ढँक दिया है। सर्वर  मानक JSON-RPC 接口 का खुलासा करता है; किसी भी अनुपालन के क्लाइंट 均可发现该接口、将其呈现给模型或用户、执行调用并解析结果,无需为具体服务器 定制适配器──

लेकिन एक महत्वपूर्ण सीमा महत्वपूर्ण हैः एमसीपी मानक संचार प्रोटोकॉल के लिए जिम्मेदार है स्वयं। यह यह तय करने के लिए जिम्मेदार नहीं है कि मॉडल को किस उपकरण को तैनात करना चाहिए, अविश्वसनीय सामग्री को स्वचालित रूप से सुरक्षित करने के लिए जिम्मेदार नहीं है, न ही बिना राज्य के अनुरोध को स्वचालित रूप से स्थायी अनुप्रयोग राज्य में परिवर्तित किया जाएगा।

### 三大 सर्वर 原语

1. **Tools（工具）**:可调用动作── प्रत्येक उपकरण में नाम, विवरण, JSON योजना 输入约束及执行函数 शामिल हैं──
2. **Resources（资源）**: नाम और यूआरआई 寻址 के अनुसार सामग्री, प्रद क्लाइंट 读取。
3. **Prompts（提示模板）**: पुनः प्रयोज्य संरचनात्मक ढाँचा, प्रवाहितकर्ता के लिए

मेजबान 指 AI 应用程序―― मेजबान के भीतर एक MCP क्लाइंट और एक सर्वर 通信―― संचरण परत दो के बीच स्थानांतरण के लिए जिम्मेदार है JSON-RPC 报文――

### 无状态请求取代传统握手

एमसीपी 2026-07-28  पूर्णतः हटा दिया गया `initialize`和 `notifications/initialized`, ने भी समझौता स्तर के सत्र को हटा दिया। प्रत्येक अनुरोध में`params._meta`इसे पूरा करने के लिए नीचे दिए गए शब्दों का विश्लेषण करेंः

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/list",
  "params": {
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {},
      "io.modelcontextprotocol/clientInfo": {
        "name": "lesson-client",
        "version": "1.0.0"
      }
    }
  }
}
```

协议版本与客户 能力为强制必填项,客户身份为推项──缺失 `_meta`、缺少必填字段或字段类型错误均属于参数形,返回 अमान्य पैरामीटर 错误码(`-32602`)― यदि संस्करण वैध है लेकिन सर्वर 无法支持, वापसी `UnsupportedProtocolVersionError`(`-32022`)― सर्वर किसी भी वैध अनुरोध को पूरी तरह से बिना किसी ऐतिहासिक चर्चा रिकॉर्ड के स्वतंत्र रूप से संभाल सकता है―

### 服务发现与版本协商

सभी आधुनिक सर्वर 均必须实现 `server/discover`△其返回结果广播支持的协议版本、能力集合与服务器身分:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "resultType": "complete",
    "supportedVersions": ["2026-07-28"],
    "capabilities": {
      "tools": {},
      "resources": {},
      "prompts": {}
    },
    "ttlMs": 3600000,
    "cacheScope": "public",
    "_meta": {
      "io.modelcontextprotocol/serverInfo": {
        "name": "demo-server",
        "version": "1.0.0"
      }
    }
  }
}
```

ग्राहक भी सीधे व्यावसायिक विधि का उपयोग कर सकता है और संस्करण त्रुटि का प्रबंधन कर सकता है, लेकिन उपयोग पता लगाने की क्षमता को प्रदर्शित करने और संस्करण पर चर्चा करने में अधिक स्पष्ट रूप से पारदर्शी कर सकता है।`UnsupportedProtocolVersionError`, गलत कोड `-32022`其数据 包含 `supported`(सर्वर 支持的修订版数组) के साथ`requested`(被拒绝的修订版)

स्टूडियो 模式下,双时代(दो युग) ग्राहक उपयोग `server/discover`发起探测──发现成功或收到 `UnsupportedProtocolVersionError`等已识别的现代错误,均证明对方为现代服务器;唯有非现代错误或超时才允许回到2025-11-25 के पुराने संस्करण तक`initialize`握手── विरासत 行为仅作为兼容补偿,绝不是现代默认──

### 显式的结果结构

2026-07-28 核心规范 में प्रत्येक सफलता परिणाम सभी ले जाते हैं `resultType`:

- `complete`:表示操作已彻底完成──
- `input_required`: यह दर्शाता है कि सर्वर को कई बार अनुरोध करने की आवश्यकता है।`tools/call``resources/read`या `prompts/get`返回此类型──

ग्राहक  अवश्य  होगा अनुपलब्ध `resultType`                                                                                                                                                                                                                                                              

सर्वर 应在每个结果的 `_meta` 中包含 `io.modelcontextprotocol/serverInfo` इस स्थिति से सर्वर स्व-प्रकाशित, केवल प्रदर्शन के लिए उपयोग किया जाता है, 日志与调试, सुरक्षा निर्णय के आधार पर नहीं किया जा सकता

列表和读取操作的结果也附带 `ttlMs`(毫秒生存时间) और `cacheScope`(缓存范围) ――确定性的 `tools/list`排序加上新鲜度提示,使客户端能够安全缓存服务发现结果,并提升模型 Prompt Cache 的稳定性──`cacheScope: public`允许跨上下文共享缓存,`private` अनुरोध के प्रवर्तन के निजी उपक्रमों पर कड़ाई से प्रतिबंध लगाएं

### 线缆格式与传输层

MCP में स्टूडियो या स्ट्रीमेबल HTTP ऊपर运行 JSON-RPC 2.0:

- अनुरोधः समाहित`jsonrpc``id``method`和 `params`
- 响应(उत्तर): समाहित相匹配的 `id`और `result`या `error`
- 通知( अधिसूचना):无 `id`, किसी भी प्रतिक्रिया की जरूरत नहीं है.

现代 Streamable HTTP 暴露单个只接受 POST 的端点──每一个 JSON-RPC 消息应应应一次独立的 POST──请求 POST 接收单个 JSON 对象,或接收到最终响应的请求作用域 SSE 流──接受通知 POST 返回无响应体的 HTTP 202──本核心修订版未定义任何通过 Streamable HTTP 客户端发送到服务器的通知──

2026-07-28 规范中**不存在**独立的 MCP GET 订阅流、DELETE 注销端点、`Mcp-Session-Id`या आधार पर`Last-Event-ID`                                                                                                                                                                                                                                                              `subscriptions/listen`POST अनुरोध, इसका जवाब रखें

### 无需 सर्वर 发起请求的客户端 输入

旧修订版允许服务器 流发送 `sampling/createMessage``roots/list`या `elicitation/create`之类的请求──当前协议改用多轮往返请求(MRTR)──符合条件的工具 调用、资源读取或快速 获取会回归 `resultType: input_required`,并至少携带 `inputRequests`या `requestState`之一──ग्राहक 收集所需输入, उपयोग नई JSON-RPC ID 和对应的 `inputResponses`重试原始方法; यदि प्रदान किया गया है `requestState`, त原样回传――若没有 `inputRequests`, पुनः प्रयास करते समय省略 `inputResponses`

जड़ें、सैंपलिंग और लॉगिंग अभी भी उपयोग में हैं लेकिन छोड़ दी गई हैं, नई कार्यान्वयन  उन्हें अपनाने योग्य नहीं है  मौजूदा जड़ें या नमूनाकरण अनुरोध MRTR के लिए `inputRequests`मध्य संचरण, निश्चित रूप से स्वतंत्र सर्वर के रूप में क्लाइंट JSON-RPC अनुरोधों में प्राथमिकता स्पष्ट फ़ाइल या कैटलॉग तत्वों, संसाधन URI, सर्वर विन्यास और मॉडल प्रदाता के साथ प्रत्यक्ष एकीकरण का उपयोग करना।

## 动手构建

### 步骤 1: पंजीकृत सर्वर 表面

यद्यपि अनुरोध अनुबंध बदल चुका है, पंजीकरण विधि अभी भी सरल हैः

```python
server = MCPServer("demo-server")

@server.tool(
    "add",
    "Add two integers.",
    {
        "type": "object",
        "properties": {
            "a": {"type": "integer"},
            "b": {"type": "integer"}
        },
        "required": ["a", "b"]
    }
)
def add(a: int, b: int) -> dict:
    return {"sum": a + b}
```

`code/main.py`मध्य पूर्ण कार्यान्वयन ने एक संसाधन और एक प्रॉम्प्ट को भी पंजीकृत किया है। यह केवल मानक पुस्तकालय का उपयोग करने के लिए है, ताकि आप प्रत्येक अनुबंध संरचना को देख सकें, न कि एसडीके को प्रोटोकॉल विवरण सौंपें।

### 步骤 2: प्रत्येक अनुरोध के लिए अतिरिक्त डेटा

```python
def request(method, params=None):
    body_params = dict(params or {})
    body_params["_meta"] = {
        "io.modelcontextprotocol/protocolVersion": "2026-07-28",
        "io.modelcontextprotocol/clientCapabilities": {},
        "io.modelcontextprotocol/clientInfo": {
            "name": "demo-client",
            "version": "1.0.0"
        }
    }
    return {
        "jsonrpc": "2.0",
        "id": 1,
        "method": method,
        "params": body_params
    }
```

इन डेटा को केवल कनेक्टेड ऑब्जेक्ट्स में ही रखें। सर्वर प्रत्येक अनुरोध पर इसका परीक्षण करेगा।

### 步骤 3: पहले पुनः सूचीबद्ध करें

调用 `server/discover`, एक समर्थित संस्करण चुनें, फिर उपयोग करें `tools/list` यदि आप पहले से ही जानते हैं संस्करण नहीं संभाल सकता `-32022`, प्रत्यक्ष调用 `tools/list`वैध भी है।

演示按名称顺序返回工具列表,并附带 `ttlMs``cacheScope``resultType`सर्वर के रूप में उपयोग करने के लिए उपकरण पूर्ण लेकिन कैश नहीं किया जा सकता है, क्योंकि इसका आउटपुट वर्तमान स्थिति पर निर्भर हो सकता है।

### 步骤 4: एक ही अनुरोध को HTTP पर मैगज़ीन करें

远程 `tools/call`POST 携带镜像 JSON-RPC अनुरोध अनुरोध का शीर्षकः

```http
POST /mcp HTTP/1.1
Content-Type: application/json
Accept: application/json, text/event-stream
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: add
```

`MCP-Protocol-Version`अनुरोध करना अनिवार्य है`_meta`मध्य संस्करण一致──`Mcp-Method`प्रत्येक JSON-RPC अनुरोध पर अनिवार्य रूप से भरे गए हैं, और साथ ही साथ`method`एक एक`Mcp-Name` केवल `tools/call``resources/read``prompts/get`时必填,且必须与工具名、资源 URI或提示名一致──缺失必填请求头或不一致时,返回 HTTP 400与 `HeaderMismatch`错误码 `-32020`

### 步骤 5: समझौता राज्य के बाहर सुरक्षा को लागू करना

1. 添加一个 `subtract`工具, पुष्टी `tools/list`仍按字母序排列──
2. 移除 प्रोटोकॉल-वर्शन 键,验证返回 अवैध पैरामीटर(`-32602`)── फिर सही प्रारूप में भेजें लेकिन समर्थित नहीं संस्करण `2025-11-25`,验证返回 `-32022`, पुष्टि `requested`इस संशोधन संस्करण को पुनः प्रकाशित किया गया है।`supported`中选择版本──

## 核心专业术语

| 术语 | 通俗说法 | 实际含义 |
|------|-----------------|------------------------|
| MCP | “LLM 的工具协议” | 用于服务发现、工具、资源、提示模板与扩展的 JSON-RPC 协议 |
| Host | “AI 应用” | 拥有大模型与用户交互界面、挂载一个或多个 MCP Client 的 AI 应用程序 |
| Client | “连接器” | 代表 Host 与单个具体 Server 执行 MCP 通信的连接器组件 |
| 无状态 MCP (Stateless MCP) | “没有 Session” | 每个请求携带版本与能力元数据，不存在与底层物理连接绑定的协议状态 |
| `server/discover` | “能力探测” | 强制实现的 Server 方法，用于公布支持版本、能力集与身份标识 |
| `resultType` | “结果状态” | 把结果标记为 `complete` 或 `input_required` |
| 显式状态句柄 (State handle) | “工作流 ID” | 由 Server 签发、作为普通业务参数传递的应用层唯一标识符 |
| Streamable HTTP | “远程传输” | 单一 POST 端点架构，返回常规 JSON 或请求作用域的 SSE 响应 |
| MRTR (多轮请求模式) | “请求输入再重试” | 嵌入在响应结果中的输入请求，完成后由客户端重新发起原始操作重试 |
