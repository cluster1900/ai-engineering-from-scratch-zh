# 面向 प्रीफिक्स- भारी कार्यभार के SGLang के साथ RadixAttention

> SGLang के लिए KV कैश 视为一等、可复用资源,并存在基层树中──vLLM 根据FCFS(पहले आने वाले, पहले सेवा) विनंती调度请求, जबकि SGLang के कैश-जाहिर शेड्यूलर के लिए अनुरोध को प्राथमिकता दी जाएगी, मूल रूप से गहराई-पहले रेडिक्स पार करने के लिए, गर्म शाखाओं को HBM में बने रहने दें। Llama 3.1 8B में GPT-जैसे 1K प्रम्प्ट के साथ GPU शेयर किए गए हैं, SGLang 约 16,200 tok/s तक पहुंच गया है, जबकि vLLM 约 12,500, लाभ लगभग 29% है। इस पूर्वावलोकन-भारी RAG कार्यभार पर, यह लाभ 6.4x तक पहुंच सकता है।

## 问题
经典服务 会将每个请求的提示 当作模糊── यहां तक कि 5,000 RAG अनुरोध भी एक ही 2,000-टोकन प्रणाली के लिए अनुरोध करें साथ ही एक पुनः प्राप्ति प्रस्तावना 开头,vLLM भी इस 2,000-टोकन पूर्वावलोकन के लिए 5,000 बार पूर्वावलोकन करेगा──GPU एक बार फिर से एक ही काम करते हैं──

观察结论是:agentic 和 RAG workloads में से प्रम्प्ट्स 几乎总是共享长长的前置列──系统提示,工具方案, कुछ शॉट्स उदाहरण, पुनर्प्राप्ती हेडर, वार्तालाप इतिहास,全都会在请求之间重复── यदि आप इस पूर्वनिर्धारित केवी कैश को 存存一次并复用,就不需要再次预填──

RadixAttention ठीक यही कर रहा है। टोकन को रेडिक्स पेड़ में सूचकांकित किया जाता है; प्रत्येक नोड के पास रूट से उस नोड तक के रास्ते पर टोकन अनुक्रम है।

挑战在于安排── यदि दो अनुरोध साझा 2,000-टोकन पूर्वावलोकन, जबकि तीसरा अनुरोध केवल साझा एक ही पूर्वावलोकन के बीच 200 टोकन, आप चाहते हैं दो लंबे साझा अनुरोध एक साथ सेवा में डाल दिया, make长 पूर्वावलोकन 留在HBM में──FCFS 做的正相反, यह सेवा सबसे पहले आगमन अनुरोध, हो सकता है अगले लंबे पूर्वावलोकन अनुरोध में पहले ही गर्म शाखा 驱逐掉──

## 概念
### 作为 KV सूचकांक का रेडिक्स पेड़

radix tree(कॉम्पैक्ट trie) भंडारण टोकन अनुक्रमों。 प्रत्येक नोड 拥有一个 टोकन रेंज,以及为该范围 计算出的 KV ब्लॉक्स。Children 会把序列 扩展一个或多个 टोकन。

```
root
 |- "You are a helpful assistant..."  (2,000 tokens, 124 KV blocks)
      |- "Context: <doc A>..."        (500 tokens, 31 blocks)
           |- "Question: Alice..."    (80 tokens, 5 blocks)
           |- "Question: Bob..."      (95 tokens, 6 blocks)
      |- "Context: <doc B>..."        (520 tokens, 33 blocks)
```

एक नया अनुरोध प्रणाली के साथ प्रम्प्ट + "सामग्रीः <doc A>" + "प्रश्नः कैरोल" 进来──调度器遍历:system prefix 匹配(复用124 ब्लॉक्स),doc-A शाखा 匹配(复用31 ब्लॉक्स), फिर केवल "प्रश्नः कैरोल" के लिए ताजा ब्लॉक्स[4][4] का वितरण करें।

### कैश-जाहिर शेड्यूलिंग

यदि कैश लगातार चूर होता है, तो रेडिक्स-ट्री पर आधारित का पुनरावृत्ति का कोई अर्थ नहीं है।

1. **Depth-first dispatch**◊ कतार से चयन करने के लिए अगली एक अनुरोध पर, प्राथमिकता चयन करें वर्तमान चल रहे सेट के साथ  जड़ें एक ही शाखा के अनुरोध पर  यह गर्म शाखा  को चिपका हुआ रखने के लिए
2. **Branch level 的 LRU，而不是 block level 的 LRU**◊ सभी शाखाओं को नष्ट करना (संक्षिप्त उपयोगित पत्तियों से शुरू), अलग-अलग ब्लॉक की बजाय, इस प्रकार कैश आकार 才与基体形 匹配──

एफसीएफएस ने इन दो बिंदुओं का उल्लंघन किया। 2,000 टोकन के अनुरोध को साझा करने के लिए 50 टोकन के अनुरोध के बाद, 2,000 टोकन शाखा को निष्कासित कर दिया गया, ताकि 50 टोकन उस अनुरोध को समायोजित किया जा सके।

### आप याद रखना चाहिए की बेंचमार्क संख्या

- Llama 3.1 8B、H100、ShareGPT 1K प्रम्प्ट्स:SGLang ~16,200 tok/s,对比 vLLM ~12,500(约 29% 优势) 
- पूर्वसर्ग-भारी RAG(समान प्रणाली + समान दस्तावेज़, परिवर्तन प्रश्न):SGLang 上最高可达 6.4x。
- आवाज क्लोनिंग कार्यभार:86.4% प्रीफिक्स-कैश हिट दर。
- एसजीएलएएन के ग्राहकों की उत्पादन हिट दरें: 50-99% के लिए शीघ्र अनुशासन पर निर्भर करती हैं।
- 2026 में 400,000+ GPUs पर तैनात किया गया है।

### आदेश 陷

6.4x यह संख्या पर निर्भर करता है संगत शीघ्र-टेम्पलेट आदेशों. यदि आपके ग्राहक कुछ अनुरोधों में प्रम्प्ट निर्माण `[system, tools, context, history, question]`, अन्य अनुरोधों में निर्मित`[system, context, tools, history, question]`,tree पर साझा पूर्वावलोकन नहीं मिल सकता है। मनुष्य के लिए यह समान है, और रेडिक्स पेड़ के लिए दो अलग-अलग अनुक्रम हैं।

## 关键术语
| Term | What people say | What it actually means |
|------|----------------|------------------------|
| RadixAttention | "SGLang 那个东西" | KV cache 以 radix tree 索引，使 shared prefixes 能复用 blocks |
| Radix tree | "compact trie" | 每个 node 拥有一个 Token range 及其 KV blocks 的 tree |
| Cache-aware scheduler | "hot-branch-first" | 优先处理共享 resident branch 的请求的调度器 |
| Prefix-cache hit rate | "你的 prompt 有多少是免费的" | 从复用 KV blocks 服务的 prompt Tokens 比例 |
| FCFS | "first-come first-served" | 会破坏 prefix locality 的默认 scheduling |
| Branch-level LRU | "驱逐 leaf" | 与 radix shape 匹配的 eviction policy |
| Prompt template ordering | "cache key" | prompt 的 component order 决定 tree 能共享什么 |
| System prompt pinning | "resident prefix" | 保持 immutable system portion pinned，以避免 eviction thrash |
