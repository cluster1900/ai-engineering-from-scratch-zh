## 从版本纪元(版本时代)开始

股`2026-07-28`规范采用了完全自含的按请求元数据(按请求元数据) ⋅一个现代请求会携带`params._meta.io.modelcontextprotocol/protocolVersion`和 `params._meta.io.modelcontextprotocol/clientCapabilities` 简写的 简写的 简写的 简写的 简写的`protocolVersion`或`clientCapabilities`裸键均属于格式变. 当 HTTP 边界存在镜像路由标标题时,其数值必须与 JSON-RPC 请求体严格一致.`resultType`,我知道.

截至`2025-11-25`旧版本则采用早期连接初始化纪元 (初始化时代) .`resultType`旧版本的结果只有在客户端明确协商并确定了旧版本的纪元后才会被解释为完整的.

绝对不需要编写一个同时宽容接受两种格式的万能宽松校验器.

| 分支 | 准入凭证 | 缺少 `resultType` 的处理 | 初始化握手 |
|---|---|---|---|
| 现代纪元（Modern） | 成功的 `server/discover` 或已识别的现代响应 | 判定为非法（Invalid） | 不再作为默认建立连接路径 |
| 旧版纪元（Legacy） | 现代探测无果后，目标命中白名单且返回合法的旧版 `initialize` 响应 | 解释为 complete | 该纪元所必需的强制步骤 |

这种严格隔离的形式是错误的,现代节点是因为校验宽松而幸运通过测试的隐患.

### 严格模式

严格模式 (严格模式) 要求端子必须表现出代协议行为的直接证据.`server/discover`即可确立现代分支──收到已识别的现代JSON-RPC 错误(如`-32020`,我知道.`-32021`或`-32022`) 同样可以建立现代分支,**绝不能**降级回归旧版协议.

### 回退模式

回退模式 (Fallback mode) 允许执行一次有边界约束的现代探测. 如果遇到超时、空响应、连接中断或无法识别的响应,这些均属于无结论 (Inconclusive),它们不能直接证明端是旧版本的节点.`initialize`结果及协商版本经验证后,才能正式转换到旧版本分支.

回退绝不等于一旦报错就尝试旧版──一个已识别的现代错误本身包含了极具价值的纠错在下文──在收到此类错误后,只会掩盖标题不匹配,缺陷能力声明或协议版本不兼容等真正配置缺陷──

这种设计可以防止攻击者,网络故障或过代理通过故意放弃现代响应来强迫系统降级.

在每次交互记录旁边必须明确标记所选的纪元. 如果脱离纪元上下文,某个缺失的段落在一轮测试中看起来合法,在另一轮测试中就会被判定为致命违规.

### 黄金记录(黄金转录)

黄金记录用于证明合规行为正确接受:

- 携带与标题相匹配的现代发现或方法请求;
- 携带必需字段的完整结果`complete`);
- 方法需要进一步的交互.`input_required`结果;

黄金记录必须精确且紧. 采用确定性生成策略,或在比较前进行规范化剥离.

### 负面记录(负面转录)

负面记录用于证明违规行为被坚决拒绝:

- 标题与请求不一致;
- 缺少对每次请求的能力声明;
- 协商版本不受支持;
- 现代请求下缺失`resultType`其他
- 没有任何消息.`resultType`其他

- 缺少整数`code`或字符串`message`的错误对象;
- 将已知协议错误映射为错误的 HTTP 状态码;
- 为通知 错误发送响应;
- 变的JSON-RPC 信封格式;
- 协议发生错误的崩吞没 (塌)

## 标题值必须与RPC要求相匹配

在现代流通 HTTP 协议下,中间代理可以借助镜像标签实施路由或执行安全策略.但是 JSON-RPC 请求体始终是协议层唯一的真理源.标题与请求体不一致属于严重的数据完整性损坏,绝不能被视为两者中二选一的宽松提示.

必须按照以下严格顺序执行校验:

1. 解析并校验 JSON-RPC 信封及元数据字段类型;
2. 比对`MCP-Protocol-Version`与`params._meta.io.modelcontextprotocol/protocolVersion`其他
3. 比对`Mcp-Method`与`method`其他
4. 当该方法具有特定的路由名称时,比较对`Mcp-Name`与请求体中的对应字段;
5. 在完全一致后,重新确定是否支持匹配协议版本和能力集.

这个前后的序列将标记不匹配错误`-32020`与协议版本不支持错误`-32022`清晰区分来来. 它也可以从根本上防止网关检验和批准标题中的安全工具,而源站实际上执行请求中恶意工具的欺诈攻击.

HTTP 字段名不区分大小写,但其字段值严格区分大小写.`Mcp-Name`必须先精确原原料`=?base64?{Base64EncodedValue}?=`无效的基地64 不合法的UTF-8或未编码的不安全字符,一律以`-32020`拒绝. 未编码的原始首尾空白即便是与请求体字符完全相同的,也属于非法,因为传输规则强制要求此类取值在传输前必须经过哨兵编码.

中间代理可能在请求到达MCP服务端之前直接拒绝变化的HTTP报文,因此该报错可能不包含JSON-RPC的纯HTTP错误.

## 未知字段不等于未知结果

实现后兼容需要遵循两条截然不同的规则:

### 附加未知字段

结果对象 (结果对象) 与`_meta`测试器应根据自己的职责定位,选择无损传递保留或安全忽略这些附加段,除非该段直接违反保留关键字的协议. 在示例代码中,测试套件会保留在证书中完整的原始响应,并对已知结果旁边宽容接受类似的.`futureHint`加入的段落

如果您是透明代理,保留未知字段通常比盲目更安全;如果您是终端应用客户端,忽略它则是合法的.

### 没有人知道`resultType`

`resultType`属于核心生命周期判别器 (分辨器) 现代核心协议定义的结果类型仅有`complete`与`input_required`扩展协议只有在经过先宣布和协商成功后才能允许引入新的取值,例如:`task`

对于未知或未经声明的宣告结果判定器,绝不能自主提出其作为结果.`complete`客户端根本无法理解自己盲目丢弃的生命周期状态是什么!

完全可能同时包含法律未知的扩张段与致命的未知的结果类型.

判别器只是校验的第一门,然后还必须根据具体方法校验其专属载荷.`tools/list`完整的结果必须包含`tools`数组,其描述符具有非空的唯一名称,明确描述以及对象的根节点.`inputSchema`其他`task`结果仅仅在具有任务能力的合法性`tools/call`中有效,且强制要求包含`taskId`已知状态 创建和更新时间`ttlMs`以及法律问题间隔;`completion/complete`完整的结果必须包含不超过100个字符.`completion`象征和可选的非负整数`total`及可选的值`hasMore`拼写正确的`resultType`绝不能免费提供形式残缺的负载.

## 通知的单向性不变量

没有 JSON-RPC 通知`id`接收方**绝不能**向外发送任何JSON-RPC成功或错误 响应报文.

对于 HTTP 上成功接收通知,测试套件预期服务端返回一个带有空请求体的 HTTP `202 Accepted`△MCP`2026-07-28`规范并未在 Streamable HTTP 上定义核心的客户端到服务端通知. 本课程的例子仅使用一个带有命名空间的课程扩展通知,专门用于验证传输层序列化器是否满足绝对不返回任何JSON-RPC 报文的不变量. 请勿误认为它是新的核心协议方法.

测试时必须覆盖外层序列化器,而不能仅仅测试处理函数本身.`None`包装的外层中部件自动被包含`{result: null}`必须直接抓取并检查最终流出网络边界的原始字节.

## 引入SDK 差异对比

各类SDK通常将底层线路对象包装转换为高级语言内置的便捷数据类型. 这提升了开发体验,但也导致规范化后的对象无法恢复网络线路的真实收发.

针对每一个高风险测试例,必须同时捕获四层视图:

1.  SDK 解码前的原始 HTTP 状态码、响应标标题与响应体;
2.  SDK 规范化转换后输出的回值对象或异常实例;
3. 针对当前选定版本纪元的预期语义映射投影;
4. 没有中生有合成,强行剥离或改的字段清单.

示例代码允许SDK 仅剥离已知的线路协议记账字段(如`resultType`,我知道.`_meta`,我知道.`ttlMs`和 `cacheScope`),同时对低层的业务负担.`futureHint`测试套件会作为分歧警报明确的报道.

不要简单地假设每个区别都是SDK的错误.核心目标是让这种隐式转换完全显而易见.

在发布前,对于你维护的每个SDK及其目标版本均需要运行差异测试.如果两个不同的SDK对完全相同的交互记录产生不同的规范输出,发布策略必须明确决定哪种行为是规范合法的,绝对不可能后后和稀泥.

## 捕获代理层证据

在产业环境中绝大多数MCP故障都发生在跨过程或穿透代理的网络边界上.

| 视角 | 最小必要凭据 |
|---|---|
| 入口（Ingress） | 客户端原始请求头、JSON-RPC 请求体、Content-Type、已认证路由、接收时间戳 |
| 源站（Origin） | 代理转发出的标头与请求体哈希、源站 HTTP 状态、源站响应头与响应体 |
| 出口（Egress） | 客户端最终可见的 HTTP 状态、响应头、最终响应体、发送时间戳 |

具体的检测能力是针对两种最常见的代理行为:

- 源站原本规范返回的HTTP 400或404JSON-RPC协议错误,被中间代理简单粗暴地转换为通用HTTP 500;
- 最终送到客户端的出口JSON-RPC 请求体和源站返回内容存在实质性变化.

根据实际部署架构,可扩充针对内容类型,`Accept`、传输压缩、针对单个请求的SSE、缓存标签以及分布式链接追踪追踪下文的断言――根据合规允许的前提,捕获TLS 终结前后的两重视角――但请注意:绝不能为了证明链接完整性而打印识别权密钥凭证――

## 证据离开内存前进行脱敏

脱敏属于一致性运维体系的内建核心步骤,而不是后面打补丁的扫尾工作. 在将证书序列化,计算哈希,写入日志,归档测试工件或上传排错报告之前,必须在内存中完成脱敏.

示例代码在执行匹配前将键名统一转为小写并除所有连接符,然后返回清除如`Authorization`,我知道.`Cookie`,我知道.`Set-Cookie`,我知道.`X-Api-Key`,我知道.`accessToken`,我知道.`clientSecret`,我知道.`registrationAccessToken`,我知道.`token`,我知道.`password`,我知道.`secret`及`api_key`等敏感字段的取值.规范化比逻辑和黑名单字典必须统一,防止小驼峰,中划线,下划线及点号等不同的命名风格相互绕过.`query`其他类型的密码也可能包含个人隐私或合规监管数据.

计算哈希时基于已过敏证据捆绑包进行计算. 原始未过敏抓包数据只有在特定事故调查中,被获批人员在生命周期极短的限制系统中临时调阅.证据摘要能够确实证明由任何经过敏证据支持本次发布裁决,同时绝不会泄露被删除的敏感明文.

## 将健康检查与回滚纳入发布门禁

协议层一致规则是发布的必要条件,但绝对不是充分的条件.

在正式放行流量之前,必须定义清晰的健康观察窗口:

- 最小要求样本容量;
- 最允许误差率值;
- 延迟分位数 ((P95/P99) 上限;
- 资源和度与计算能力限制;
- 持续观测的时间跨度;
- 与基线基准指标的横向对比

同样,回滚凭证也必须在上线前预先就绪:

- 精确的前序版本标识;
- 预先入学证书哈希摘要;
- 对应的SHA-256工件与描述符固定指纹;
- 当前最新的登记处官方状态;
- 现行最新的健康检查评估报告;
- 经过了经过的路由恢复标准作业程序;
- 由可信发布控制器身份针对上述全量字段签署的认证凭证 (证书) 〔(

强制要求这个回滚目标在候选版本批准之前必须处于健康和验证状态,而不是等候选版本在线爆发后暂时忙碌地寻找出路.

如果候选版本出现故障,而目前的回滚目标又缺乏完整的入门证据支持,系统应决定选择停机 (Hold),绝不能依赖于凭感觉回滚到看起来正常的版本来碰运气.

绝不要将就绪检查降级为非空字符串判断,`healthy: "yes"`或随意状态标记――示例代码严格要求匹配确切类型的状态――活跃状态――三个关键 SHA-256 摘要、可信的签名主体,以及基于完整负载计算的合法 HMAC-SHA-256 签名――示例中确定性的关键属于非机密的测试具;在生产环境中,应在发布边界处注入严格保护的关键、KMS 验证结果或非对称公钥认证服务――

发布门禁还将坚决拒绝空白的互动记录,SDK 差异凭证或代理层证据.每个证据来源都必须提供有效的摘要指标.

## 验证标准

运行演示程序与全套确定性测试套件:

```bash
cd phases/13-tools-and-protocols/31-mcp-conformance-versioning-and-operations
python3 code/main.py
python3 -m unittest discover -s code/tests -v
```

测试应严格证明:

- 包含的全部15组黄金和负记录均达到预期的确定结果;
- 现代请求强制要求使用带精确命名空间的元数据键;
-  HTTP标题名称比对不区分大小写,编码后的`Mcp-Name`值被无损精准回原;
- 标头与请求体不一致时准确返回现代错误码 `-32020`其他
- 响应版本、ID 一致性、结果与错误互斥性、错误对象结构以及HTTP 映射均经过严格的校验;
- 强制执行针对`tools/list`、任务扩展及补充全程专属负载规范;
- 只要出现`HeaderMismatch`需要实际捕获HTTP400与JSON-RPC`-32020`响应
- 未编码的原始`Mcp-Name`首尾空白被拒绝,而使用哨兵编码的空白字符能精准往返原;
- 缺失`resultType`仅在明确选定的旧版纪元中被视为合法;
- 附加未知字段能够安全保留,而未知生命周期结果类型则将被坚决拒绝;
- 扩展结果类型必须在应对能力的前提下先进行通知;
- 收到已识别的现代协议错误绝不触发到旧版本协议的降级回归;
- 通知绝对不会产生任何形式的JSON-RPC响应;
- 清晰识别SDK对协议账户段的正常分离与对业务语义段的意外丢失;
- 精准检查代理层对错误码的吞没,并且在小峰和带连接符等多种风格变化下均可归咎于脱敏证据;
- 晋级放行必须同时拥有空虚的交互记录,SDK差异,代理审计以及在健康区的运维证书;
- 无论是放行还是回滚,均强制要求有一个经签证认证,指纹固定,处于活跃状态,标志着健康的回滚目标.

## 生产环境故障模式

| 故障现象 | 浅层粗糙测试的假象报告 | 测试工具链必须证明的实质 |
|---|---|---|
| SDK 擅自补全了缺失的判别器 | “tools/list 运行通过” | 原始线路上缺失现代 `resultType`，属于非法响应 |
| 收到 `-32021` 后客户端自行降级 | “旧版重试成功” | 收到已识别的现代错误绝不允许降级回退 |
| 未知结果类型被当成 complete | “响应成功解析” | 未经能力通告的生命周期判别器必须被坚决拒绝 |
| 代理批准了 A 工具而源站执行了 B 工具 | “请求成功抵达服务端” | 确保每一跳的 `Mcp-Name` 均与请求体中的路由名称严格一致 |
| 测试在读取服务端响应前自行报错终止 | “标头不匹配测试通过” | 必须真实捕获并验证 HTTP 400 及 JSON-RPC `-32020` 响应体 |
| 代理将源站 400 转换为通用的 500 | “上游服务端报错” | 源站与出口两端的 HTTP 状态及错误体必须原样保留 |
| Notification 中间件强行输出 `{result: null}` | “处理函数正常返回了 None” | 最终网络出口的请求体必须为空，且不存在任何 JSON-RPC 报文 |
| SDK 擅自剥离了前向附加字段 | “强类型对象转换一致” | 原始视图与规范化视图清晰指出具体哪一个字段被丢弃 |
| 事故排查工件泄露了 Bearer Token | “已成功上传调试数据包” | 在计算哈希、写入日志或上传网络之前已彻底完成脱敏 |
| 命名风格变体绕过了脱敏拦截 | “黑名单中已包含 api_key” | 小驼峰、中划线等所有变体在脱敏前均统一规范化为规范形式 |
| 金丝雀发布在毫无流量时显示指标全绿 | “零错误率” | 强制校验最小请求样本容量门槛 |
| 故障回滚切到了一个未经测试的未知构建 | “已恢复先前部署” | 回滚目标、准入摘要、固定指纹、状态与健康凭据必须全部完备 |
