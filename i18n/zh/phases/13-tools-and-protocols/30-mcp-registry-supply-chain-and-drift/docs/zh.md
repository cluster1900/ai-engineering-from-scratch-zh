# 供应链:准入、漂移与回滚

> 登记条目只能说明发行者声明的内容. 进入生产阶段的控制必须证明你取得了什么,观察了什么,批准了什么,以及你能恢复什么.

**Type:** Build
**Languages:** Python
**Prerequisites:** Phase 13 · 17 (gateways and registries), Phase 13 · 18 (production authentication)
**Time:** ~90 minutes

## 核心问题

你在注册表中找到了`com.example/inventory`△它的描述看起来完全符合需求. 其软件包真的存在.`server/discover`,我知道.

这不是单独的事实,而是由不同权威机构背后的事实链条:

1. 一位通过该命名空间身份证的发行者提交了一篇记录.
2. 某包注册中心发出了一个具有特定标识和哈希摘要的工件.
3. 一个实际运行端点上报道协议版本,支持能力,可用工具以及诊断服务端信息.
4. 组织决定,该套件的确切组合在策略上是合规的,并且允许运行.

如果把这些层次混为一谈,简单地认为既然它在注册表里,就能直接信任,就会留下巨大的盲区在供应链安全上. 如果没有固定件摘要,软件包的标签可能在未来被替换为未预期的二进制.

解决方案是建立一个进入控制器 (Admission Controller),在每个边界均强制采集并获得证书.

## 登记是索引,而不是你的审批系统.

官方MCP注册表 用于存储服务端元数据.`server.json`记录声明一个服务版本,并列出一个或多个软件包或远端点.发布规则包含命名空间认证,软件包所有权检查,限额注册源规则以及严格限制的发行者数据存储位置.

这些控制措施是**发布层面**问题――但你的生产环境安全策略仍然必须得到答案**部署层面**的问题:

| 边界 | 核心问题 | 证据所有者 |
|---|---|---|
| 命名空间 | 该发布者是否有权使用此名称？ | Registry 认证凭证 + 本地验证过的命名空间输入 |
| 发布记录 | 发布者针对该版本具体声明了什么？ | 不可变的 `server.json` 内容摘要 |
| 执行源 | 最终执行的是哪个软件包或远程端点？ | 已声明的源字段、已验证的所有权结果、传输协议以及可信内容摘要 |
| 运行时 | 该端点当前实际暴露了什么能力？ | 实时 `server/discover` 结果与工具描述符 |
| 准入决策 | 本地安全策略是否批准了这套确切的组合？ | 本地固定的指纹（Pin）与账本记录项 |
| 运维治理 | 当前服务是否依然安全？故障时何者可替代？ | 漂移检测、状态同步、健康检查与备用回滚路由 |

登记方案版本与MCP协议版本是彼此独立的.`2025-12-11`服务端规范,而实际运行的服务端却支持MCP`2026-07-28`绝对不能从一个版本决定另一个.

## 单次进入决策中的七重控制

### 1. 命名空间验证

官方登记册的命名采用身份认证的命名空间. 一个经验证的域名可以映射为反向域名格式的前.`example.com`控制权可以建立`com.example/*`法律的合法性.

绝对不能使用简单的字符串前检查:

```python
server_name.startswith("com.example")
```

因为这种判断也会错误地让恶意仿冒.`com.exampleevil/tool`必须要`/`切分名称,要求包含非空的片段,并精确比对命名空间这一段. 更重要的是,进入控制器接收的已验证命名空间必须来自可信的识别权输入结果,绝不能直接从不可信的发布记录本身提取信任.

基于 GitHub 组织命名空间与基于域名命名空间具有不同的认证路径.

### 2. 出处关联(来自加入)

对于软件包类型的记录,声明的数据必须严格与实际采集的工件相关,在以下明显的字段:

- 软件包注册中心类型(如PYPI、npm)
- 软件包标识符
- 软件包版本号
- 已验证所有权检查结果
- 实际下载工件的内容哈希摘要

同时还需要校验声明的传输协议. 如果某条记录只声明远程端点 (远程端点),这也是完全合规的,绝不能因为缺乏软件包就拒绝错误.

本课例代码同时支持这两种源类型,并将选取源与注册表源,服务端名称,注册表版本,记录摘要以及凭证摘要共同计算出一个哈希.

绝不能直接接受由受证件本身单方面提供的摘要.必须在可信的下载边界重新计算摘要,或者从你已经验证的受信托包管理服务处接收.

### 3. 固定决策,而不是仅固定版本

登记版是唯一的发布标识符.已发布的元数据是不可变的.任何记录的修改都必须发布为全新的版本.

这意味着类似的.`^1.4`的表达式不是合法的准入Pin,所谓的lastest更不是――一个有效的准入固定指纹) 应该包含:

```json
{
  "server": "com.example/inventory",
  "version": "1.0.0",
  "recordDigest": "...",
  "source": {"kind": "package", "registryType": "pypi"},
  "sourceDigest": "...",
  "toolsetDigest": "...",
  "provenanceDigest": "...",
  "registryStatus": "active"
}
```

在多个不同层次同时进行指纹固定,可以让你在出现异常时快速定位是发生突变的边界:在同一登录版下记录摘要变化,属于登录数据完整性损坏;在同一软件包坐标或远程部署下源摘要变化,属于执行源变化;而工具集摘要 (工具集) 消化变化,则属于运行时行为漂移.

### 4. 实时运行时漂移检测

准入流程必须主动观测实际接收业务流量的服务端实例.`server/discover`列出或获取其暴露的工具描述符,并验证:

- `supportedVersions`中包含`2026-07-28`其他
- 现场策略要求的所有必要能力已已满足;
- 每个工具描述符都具有规范的身份识别和方案定义表面;
- 规范化后的描述符摘要在后续复查时完全与已准备的固定指纹一致.

结果中可选的`_meta["io.modelcontextprotocol/serverInfo"]`仅属于自述性质的展示,日志与排错上下文.**绝不能**作为判断命名空间"",软件包所有权"",归属端点"",进入许可或任何安全决策的依据.`_meta`直接的外部`serverInfo`别名更不属于官方契约字段,绝不可将其升级为合法的诊断证据.

仅对那些顺序本身没有语义的字段进行规范排序.本课例在计算哈希前按照稳定的工具名称对工具列表进行排序,因此纯粹的返回顺序变化不会被误报为漂移.但它绝不会丢弃描述符中的任何字段. 新增工具,修改方案,修改描述文本或引入新的注释,都会立即改变工具集摘要.

示范代码将任何形式错误描述符或描述符摘要的变化均视为行为漂移,立即将指纹隔离 (隔离) 撤销其活跃路径,并封锁它作为回滚目标的资格. 在生产环境中,即使是微不足道的描述变化也必须走进全新的审批流程,因为大模型是否根据工具描述决定调用该工具的表面文本修改足以从根本上改变代理执行行为.

### 5. 登记状态是实时动态状态

登记API将在每个服务端记录旁边添加一个响应级别.`_meta`对象──由登记处官方托管的字段存储`_meta["io.modelcontextprotocol.registry/official"]`路径下――准入控制器需要解析该响应并读取 `_meta["io.modelcontextprotocol.registry/official"].status`直处根节点`_meta.status`不符合官方线上传输格式. 不要混为一谈外部响应数据和记录内部自带的发布数据.

- `active`默认返回,具有本地准入候选资格;
- `deprecated`已废弃,虽然仍可检查,但会带警报,不再适合自动推选项合作;
- `deleted`已删除,隐藏在默认列表中,但可通过针对已删除或增量视角的接口查看其历史档案.

准入完成后必须持续同步状态. 一旦原始活跃版本被标记为废弃或删除,应立即对其指纹进行隔离并停止将新流量路由给它.同时必须保留所有历史证书在上游默认列表中被删除,绝对并不意味着你可以在本地删除审计追踪记录.

发布者自行提供的自定义数据只能存储在发布记录中`_meta.io.modelcontextprotocol.registry/publisher-provided`登录管理的响应元数据是完全独立的.

### 6. 回滚意味着路由恢复

无可变的发行记录在回滚过程中绝不会被修改.

一个安全的回滚目标必须同时满足:

1. 拥有完整且合法的准入记录;
2. 在当前本地策略下,其登记处仍然保持活跃;
3. 没有任何运行时警报或安全证书标记为隔离状态;
4. 仍能精确解析到已确定的软件包和线上描述符集合;
5. 通过当前最新的健康检查.

在实际生产对账控制器中,在正式切流激活前,还应对软件包执行重新拉取校验并重新探寻活线上端点.

### 7. 额外准入账本

准入数据库只能说明目前活跃的内容,而准入账本 (Admission ledger)则记录为什么它是.

本课本中的每条记录条目包含序号,时间,事件类型,服务端标识,版本号,裁决结果,原因说明,证据集,前一项哈希以及本项哈希.

这是一个具有防改检测能力的机制,但并非不可破坏的. 应定期将账本在独立的信任域中,例如通过数字签名发布元数据系统或单写多读WORM存储. 执行对账本的额外权限严格访问控制.

## 手写实现

可直接运行的控制器代码位于`code/main.py`中,全部基于Python 标准库实现.

首先运行有限状态演示:

```bash
cd phases/13-tools-and-protocols/30-mcp-registry-supply-chain-and-drift
python3 code/main.py
```

演示将执行五项核心操作:

1. 准入`1.0.0`核验匹配的命名空间、包出处、协议版本、能力及工具集;
2. 准入`1.1.0`并将其转换为活跃路由;
3. 在运行时观测到一个未预期的删除工具;
4. 观测到`1.1.0`在注册中官方状态变为`deprecated`其他
5. 路由平滑恢复到之前仍然符合规则`1.0.0`固定指纹.

预期输出结构:

```json
{
  "admitted": [true, true],
  "driftAllowed": false,
  "rollbackAllowed": true,
  "activeVersion": "1.0.0",
  "ledgerValid": true
}
```

建议按以下顺序研读实现代码:

1. `namespace_for_domain()`与`namespace_matches()`建立精确的命名空间鉴定权边界;
2. `digest()`与`normalized_tools()`产生确定性证据摘要;
3. `RegistryAdmissionController.admit()`聚合发布记录,出处证书,运行时观测与本地策略;
4. `check_live()`对于最新观测数据和已确定指纹;
5. `observe_registry_status()`: 对注册表 状态发生变更的版本执行隔离;
6. `rollback()`仅仅激活前已准备,符合合法的回滚目标;
7. `AdmissionLedger.verify()`精准检测历史记录的任何变化.

## 交互式实验

你会亲眼观察每一个失败的现场.

### 实验 A:命名空间冲突

进入代码目录并打开Python交互环境:

```bash
cd phases/13-tools-and-protocols/30-mcp-registry-supply-chain-and-drift/code
python3 -q
```

执行如下命令:

```python
from main import namespace_matches
namespace_matches("com.example/inventory", "com.example")
namespace_matches("com.exampleevil/inventory", "com.example")
```

第一个结果是`True`第二个结果是`False` 在本地临时把精确段落比换成`startswith`继续恢复精确比对逻辑.

### 实验B:描述符漂移

```python
from main import *
times = iter(f"2026-08-21T12:00:{n:02d}+00:00" for n in range(10))
c = RegistryAdmissionController(clock=lambda: next(times))
meta = {OFFICIAL_META_KEY: {"status": "active"}}
c.admit(sample_record("1.0.0"), meta, "com.example", evidence_for("1.0.0"), sample_live("1.0.0"))
c.check_live("com.example/inventory", "1.0.0", sample_live("1.0.0", True))
```

检查返回的原因和路由状态.软件包和登记记录没有任何变化,但由于运行过程中的工具表面发生了变化,控制器立即隔离并停止使用固定指纹.

### 实验C:状态与回滚

准入`1.1.0`为了实现这一目标,

```python
c.admit(sample_record("1.1.0"), meta, "com.example", evidence_for("1.1.0"), sample_live("1.1.0"))
c.observe_registry_status("com.example/inventory", "1.1.0", "deprecated")
c.rollback("com.example/inventory", "1.1.0", "unsafe retry")
c.rollback("com.example/inventory", "1.0.0", "restore known release")
c.ledger.verify()
```

隔离目标将被明确拒绝,而前合规的`1.0.0`印纹则顺利激活,账本哈希链始终保持有效.

## 动手实践

为控制器扩展双人审批门禁 (双人审批门)

需求规范:

- 审批信息需要作为通过数字签名证据引用进行存储,必须作为可变字符串保存在指纹中;
- 当工具集中包含声明`destructiveHint: true`在高危工具时,必须要求两种不同的审查员身份签名;
- 拒绝包含重复身份的审批;
- 审批未完成时,仍在账本中记录了第一次入境尝试;
- 编写测试,分别覆盖0人,1人重复身份以及两种不同合法身份的审批场景;
- 日志中绝对不得打印数字签名,凭证密钥或完整的私人工具参数.

验收标准:只要缺少两名独立审查员, 针对完全一致的记录摘要,软件包摘要和工具集摘要的签署批准, 破坏性工具绝对无法进入活跃路由状态.

- 精确的命名空间边界能成功拦截形似前的恶意名称;
- 只有官方命名空间所附的登记处才能决定版本是否有资格竞选;
- 经验不丰富或内容不匹配的软件包与远端点证书将被断然拒绝;
- 发行者自述元数据绝不能冒充登记册官方托管元数据;
- 工具列表的排序进行规范化,同时不会掩盖描述符的实质变化;
- 结构变化的软件包与工具定义会导致安全失败;
- `serverInfo`仅保留在诊断证书中,绝不会授予其进入权力;
- 描述符发生漂移时,系统会立即执行隔离"",撤销路径",并封锁该指纹的回滚;
- 动态变更能驱动动动动动动动动动动动动动动的分离;
- 回滚绝不能选择被隔离或未知版本;
- 任何关于本书历史记录的变化都可立即检查.

## 生产环境故障模式

| 故障现象 | 发生原因 | 必须采取的应对措施 |
|---|---|---|
| 名称看似合法但命名空间从未经验证 | 准入策略轻信了记录内部的自述文本 | 严格拒绝，直到可信命名空间验证方提供精确前缀 |
| 相同软件包坐标拉取到了全新的二进制内容 | 上游版本被覆盖或分发源遭受投毒篡改 | 立即终止激活，保留两份摘要，调查拉取网络边界 |
| “latest”版本在未经人工审查的情况下发生漂移 | 浮动版本选择绕过了固定指纹机制 | 始终只解析和激活完全精确的已准入版本与摘要 |
| 安全审查通过后线上悄然出现新工具 | 发生了运行时行为漂移，或部署了不同镜像 | 隔离该路由，重新采集最新的实时描述符快照 |
| 已废弃的版本依然在线上持续运行 | 状态同步机制缺失或同步存在严重延迟 | 建立定时状态调和机制，并在每次路由激活前复核 |
| 已删除记录在默认同步中彻底消失 | 客户端只向 Registry 增量请求活跃记录 | 采用增量式或感知删除事件的调和机制，并在本地归档历史 |
| 回滚的目标版本根本从未通过准入审查 | 路由切换与准入审批状态彼此脱节 | 坚决拒绝回滚，强制对该目标走全新的准入流程 |
| 攻击者重写全部账本后本地依然校验通过 | 哈希链缺乏外部信任根的约束锚定 | 定期将带签名的账本头发布到独立的外部信任域 |
| 留存的凭据中泄露了 Bearer Token 或参数 | 日志和证据记录盲目复制了完整请求 | 在采集入口处执行脱敏，仅持久化留存最小必要凭据 |

## 运维守则

发布流程回答的是,该身份是否有权发布这个名称? 进入流程回答的是,我们是否确定要执行这个具体的工件,并向大模型暴露这个具体的行为? 必须严格分开这两个决定,对每个关联点进行指纹固定,让回滚成为基于可验证证证证据的工程动作,而不是依赖于人脑记忆的幸尝试.
