## 概念

### 发现是一个编译器流水线

将文件系统视为源码输入. 不要直接将原始路径发布给模型.

```figure
skill-discovery-pipeline
```

每个阶段都应该产生结构化数据和结构化错误.

- 搜索了哪些根目录?
- 找到了哪些候选人包?
- 拒绝了哪些候选人,原因是什么?
- 在冲突中,哪个包胜出?
- 由于预算限制,哪些目录条目被缩短或省略?

如果没有这些可观证据, 诊断为什么模型没有使用我的技能几乎是不可能的.

### 作用域是运行时策略

可移植规范定义了技能包的结构,但没有定义单一的通用安装路径或优先级顺序.

一通用运行时可能使用以下作用域:

| 作用域 (Scope) | 示例根目录 | 预期所有者 |
|---|---|---|
| Workspace (工作区) | `<repo>/.agents/skills/` | 项目维护者 |
| User (用户) | `<user-data>/skills/` | 单个开发者 |
| Administrator (管理员) | `<system>/skills/` | 机器或组织策略 |
| Plugin (插件) | 已签名的插件包 | 插件发布者与安装者 |
| Built-in (内置) | 运行时自带包 | 运行时提供商 |

截至2026年8月,Codex 文档规定项目级发现会从`$CWD/.agents/skills`开始上升遍历祖先目录直至代码仓库根目录,外加、用户管理员和内置位置. 它支持符号链接的技能 目录.`SKILL.md`规范的强制要求; 在编写适配器时,请查看最新的[Codex skill 文档](https://learn.chatgpt.com/docs/build-skills),我知道.

绝对不要凭空从目录名称推断优先级.应声明为明确的策略并进行测试. 本课程实验为每一个.`Scope`使用显式整数优先级,确保相同的候选集合始终解析出相同的结果.

### 冲突需要超越`name`唯一的标识

两个都叫`release-readiness`包可能是合法的. 一个可能是项目级覆盖,另一个是用户默认配置.

```json
{
  "name": "release-readiness",
  "description": "Inspect a release candidate for this repository.",
  "scope": "workspace",
  "source": "/repo/.agents/skills/release-readiness",
  "selected": true
}
```

常见冲突策略包括:

| 策略 | 优势 | 风险 |
|---|---|---|
| 保留所有候选包 | 不会隐藏任何内容 | 模型会看到歧义的名称 |
| 最高优先级作用域胜出 | 调用简单直接 | 本地包可能会遮蔽（shadow）受信任的包 |
| 拒绝重复项 | 无隐式遮蔽 | 合法的覆盖机制将失效 |
| 按来源限定名称（命名空间化） | 身份明确 | 面向用户的名称变长 |

举办者选择策略.即使某些候选包未出现在模型目录中,也必须保留被拒绝或被遮蔽的候选包信息在诊断日志中.

### 三个披露级别

#### 级别1: 目录元数据 (目录元数据)

模型需要足够的信息来区分该技能与相邻技能.规范估计每个目录条目占约100个代币,但实际序列化和代币化细节由主机决定.

一个有用的描述包含两个句子:

```yaml
description: Validate a release candidate and produce a readiness report. Use when the user asks whether a version, tag, or package is ready to publish.
```

第一个子句说明能力 (能力) ⋅第二个子句说明触发边界 (触发边界) ⋅第25课将使用正向试用例和近邻误触发试用例 (近错提示) 评估这个边界――

#### 激活指令 (活动指令)

激活后正文应扮演路线图与工作流程的角色.`SKILL.md`保持在500 行内. 这是一个设计指导信号,而不是一个要实现的目标.

正文应包含:

- 任务边界
- 默认工作流;
- 分支条件;
- 指向更深层次文件的直接引用;
- 工具和脚本契约
- 障碍与停止行为;
- 预期输出及其验证方法――

为了让进口文件变短,我们必须把核心工作流转移到参考中.

#### 支资源 (支持资源)

引用 提供详细说明或数据. 脚本 提供确定性计算. 资产作为可复制,填充或转换为最终交付的材料,而不是指令本身.

| 目录 | 模型是否读取？ | 模型是否执行？ | 典型内容 |
|---|:---:|:---:|---|
| `references/` | 是，在需要时 | 否 | schemas、策略、领域指南 |
| `scripts/` | 可以视情况检视 | 通过被允许的工具 | 验证器、转换器、数据收集器 |
| `assets/` | 仅在有用时 | 否 | 模板、fixtures、图像、起始文件 |

这些目录名称只是约定,并非固定的魔法能力.

### 面向分支的具体参考优于粗暴的专题倾倒

将入口文件写成决策图:

```markdown
## Choose the path

- For a Python package, read `references/python-release.md`.
- For a container image, read `references/container-release.md`.
- For a documentation-only release, read `references/docs-release.md`.
- If the release combines artifact types, read only the guides for those artifacts.
```

这给每一个参考一个可观察的加载条件.`references/`获取更多信息 没有这样的明确性.

保持引用图(参考图) 平浅显──官方指南建议从 `SKILL.md`直接链接,避免深层调用链链――单跳 (单跳) 使可达性易于测试,并降低所需约束条件从未进入上下文的风险――

### 目前预算和活跃下文是两个独立的预算

设 $c_i$为技能$i$序列化后的目录开销,$B_c$预算表$b_j$为了激活正文开销,$r_k$实际上,

```text
catalog_cost = sum(c_i for every published skill)
active_cost = sum(b_j for every activated skill) + sum(r_k for every disclosed resource)
```

削减一个预算不会自动减少另一个预算――简短的描述可以节省目录空间,但已激活的900 行正文仍然可能会压任务下文――将正文分为参考文献,只有在运行时和命令实际避免加载不相关分支时才能真正减少活跃下文开销――

目前已知下文窗口大小的情况下,将初始技能列表的预算控制在上文窗口的2%──8,000字符的限制仅在下文窗口大小未知时作为回归机制;它不是与2%的规则叠加的第二个上限.当目录超出适用的预算时,描述可能会被缩短或省略.请将这些数字视为本文编辑的具体策略,而不是代理技能标准的普遍属性.

### 资源路径是信任边界

一个技能应该只能读取自己的包内文件.

```text
references/../../../../.ssh/config
references/external-link -> /private/company-secrets
```

使用文件系统语义解析包根目录和候选路径,绝对拒绝输入路径,并验证解析后的候选路径是否仍然位于解析后的根目录下面.

```figure
skill-resource-containment
```

路径限制并不能建立内容信任. 一个有效的包内引用仍然可能包含恶意指令. 第26课将专门处理这一威胁.

### 运载过程必须可观测

记录披露事件,同时避免记录机密信息:

```json
{
  "event": "skill.resource.loaded",
  "skill": "release-readiness",
  "resource": "references/python-release.md",
  "reason": "candidate contains pyproject.toml",
  "bytes": 2840
}
```

`reason`字段将一次上下文选择转化为可供审查证据. 它还有助于识别导致代理 防止所有文件的负载的糟糕指令.

## 构建它

`code/main.py`建立一个确定性发现和披露引擎.

发现模块的接口包括:

- `Scope`:用于来源和优先级的元数据;
- `SkillCandidate`表示未经验的文件系统候选包;
- `discover_scope(scope)`举个直接下层的技能 目录
- `resolve_collisions(candidates, precedence)`应用冲突策略的声明;
- `CatalogEntry`与`build_catalog(...)`:发布有界的元数据;
- `CatalogBudget`核算序列化条目的占用空间,避免假定字符数等于通用代币数.

披露模块的接口包括:

- `load_skill_body(entry, ...)`用于2级的激活加载;
- `validate_reference(skill_dir, reference)`用于路径限制检查;
- `load_reference(...)`读取:用于有界的3级

运行实验:

```bash
cd "$(git rev-parse --show-toplevel)"
cd phases/13-tools-and-protocols/24-skill-discovery-and-progressive-disclosure
python3 code/main.py
python3 -m unittest discover -s code/tests -v
```

该命令块需要本地基特克隆环境,并可以从该克隆内部任意工作目录解析出仓库根路径.

演示会创建临时项目作用域和用户作用域,引入冲突,在故意设置的极小预算下构建目录,激活一个技能,并分别尝试合法参考 阅读和目录遍历逃逸.演示不会安装任何永久文件.

### 为什么发现是浅层的

`discover_scope`仅检查直接子目录下`SKILL.md`,它不会回归每个嵌套的位置.`SKILL.md`视为独立包. 这保护包边界,避免意外发布已安装的技能.

### 为什么实验不解析任意的YAML

实验仅支持其目录所需的标量前材料――生产运行时应使用安全的YAML解析器,配备显式方案、大小限制,并禁用自定义对象构建――仅使用标准库(Stdlib-only) 是一个教学约束,而不是默许随意发明不完整的YAML方言借口――

## 交付它

本课产出炉`skill-catalog-builder`组件包――它按照明确的序列扫描根目录,拒绝符号链接的入口文件和名称目录不匹配项,解决跨作用域冲突,拒绝等级重复项,并声明的条目数量,描述和序列字符预算内装入选的元数据――

## 关键术语

| 术语 | 常见说法 | 实际工程含义 |
|---|---|---|
| Skill 发现 (Skill discovery) | “找到所有 SKILL.md” | 搜索配置的作用域，校验包，附加来源溯源信息，并应用策略 |
| Skill 目录 (Skill catalog) | “已安装 skills 列表” | 面向合格包的、模型可见的紧凑路由元数据 |
| 冲突策略 (Collision policy) | “哪个重复项胜出” | 针对来自不同来源的同名候选包所声明的处理规则 |
| 渐进式披露 (Progressive disclosure) | “懒加载” | 从目录到正文再到特定分支资源的分阶段上下文引入 |
| 引用图 (Reference graph) | “skill 链接的文件” | 可达的资源结构及其加载条件 |
| 路径限制 (Path containment) | “留在文件夹内” | 验证解析后的资源目标路径始终位于解析后的包根目录下 |
