## 学习目标

- 工具描述,注释,客户端信息以及服务端信息均被视为不可信的数据.
- 检测元数据投毒(元数据中毒) 描述器 恶意改(肩拉) 以及跨服务器的名字冲突与遮蔽(遮蔽) 。
- 验证 2026-07-28 版本的请求元数据与流通的HTTP路由头部.
- 保护MRTR`requestState`免受改,并将人工确认与精确调用参数强绑定.
- 将授权和速度限制 (加给认证主体) 而不是已移除的协议会议.

## 问题

模型依赖阅读工具描述来决定调用什么――路由器依赖阅读工具名称来决定将请求发送到哪里――用户依赖阅读界面标签来决定批准什么操作――只需要一个恶意构建的描述符,就能同时对这三者发动攻击――

官方安全指南非常直接:除非描述和注释来自完全信任的服务器,否则一律应视为不可信的数据――即便如此,运行时的信任状态也会发生变化――一次服务器更新,一次受污染的依赖包,一次登记器配置错误,或者一次网关合并,都有可能改模型看到的内容――

当前协议也改变了安全边界. 在2026-07-28核心协议中,没有握手阶段,也没有传输层会议.`Mcp-Session-Id`为了绑定批准凭证,速度限制或审计历史的安全设计,都不再符合当前协议标准.

## 概念

### 值得检查的七大攻击面

为了让我们知道,

1. **元数据投毒（Metadata poisoning）：**描述 嵌入与声明的工具 行为完全无关的指令
2. **Descriptor 恶意篡改（Descriptor rug pull）：**之前已被用户或系统批准的名称,描述,方案或注释发生静默变更.
3. **跨 server 名字遮蔽（Cross-server shadowing）：**两端都显示了相同的未加限工具名称,路由器则根据注册顺序默默选择其中一个.
4. **Header 与 Body 混淆（Header and body confusion）：** HTTP 头部的`Mcp-Method`或`Mcp-Name`与JSON-RPC 请求体中的内容不一致.
5. **Capability 权限提权（Capability escalation）：**端在请求中声明某个扩展或客户端特性,而服务器将错误地将该声明视为已授权的凭证.
6. **MRTR 状态篡改（MRTR state tampering）：**客户端改了`requestState`、回答另一个完全不同的确认问题,或者将旧确认证复用到改动后的论点上.
7. **供应链身份混淆（Supply-chain identity confusion）：**将一个看似熟悉的显示名称 (显示名称) 作为发布者或服务器 真正身份证明.

这些攻击面往往相互交织着──哈希锁定──哈希ping) 帮助发现描述器的后续变化,但无法证明最初的描述器本身是安全的──静态扫描可以捕获明显的危险短语,但无法识别精巧伪装的语义指令──命名空间可以防止同名冲突,但无法阻恶意命名空间内的服务器──因此,必须采用纵深防御──深度防御────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────

### 保护无状态 MRTR 确认

具有重大影响的工具 (后续工具) 可能需要用户确认――当前MCP采用多往回请求 (MRTR),而不是服务器到客户端的反向回调――

第一次回应:

```json
{
  "resultType": "input_required",
  "inputRequests": {
    "confirm": {
      "method": "elicitation/create",
      "params": {
        "mode": "form",
        "message": "Export notes to archive?",
        "requestedSchema": {
          "type": "object",
          "properties": {
            "confirm": {"type": "boolean"}
          },
          "required": ["confirm"]
        }
      }
    }
  },
  "requestState": "opaque-integrity-protected-value"
}
```

客户端获取用户输入后,使用新的JSON-RPC id 重试原始方法:

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {
    "name": "notes.export",
    "arguments": {"query": "private", "destination": "archive"},
    "requestState": "opaque-integrity-protected-value",
    "inputResponses": {
      "confirm": {
        "action": "accept",
        "content": {"confirm": true}
      }
    },
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {
        "elicitation": {"form": {}}
      }
    }
  }
}
```

每个`inputRequests`的值都是一个包含`method`和 `params`完整内嵌请求──其关键名必须与`inputResponses`中的对应条目一致──表单诱导(形式诱导) 用于对象为根节点的`requestedSchema`客户端必须在服务器发出请求之前已声明的形式请求功能.

现行协议有两种法律表达能力:`{"elicitation":{}}`隐式支持表单;而`{"elicitation":{"form":{}}}`为显式声明――若仅声明URL支持`{"elicitation":{"url":{}}}`则不支持表单请求.此时服务器会返回HTTP 400与错误码.`-32021`且`data.requiredCapabilities`为`{"elicitation":{"form":{}}}`,我知道.

必须将`requestState`视为不可信的输入.对其签名或加密,严格验证,并将其与方法,工具,精确的论点,操作目的,过期时间,认证主体以及一次性随机数量进行了测试.

### 高风险调用的两人法则(二的规则)

从三个维度对一次调用进行分类:

- 是否消费不可信输入
- 是否能够访问敏感数据
- 是否会产生不可逆的外部重大影响.

任何单一的自动化步骤都不能同时具有这三个特征. 一旦汇聚,就必须对其分断,降权,或者通过MRTR引入明确的人工确认.

### 在执行前收缩权限 (Reduce Authority)

无状态本身并不等于安全. 虽然它消除了隐藏的会话历史风险,但一个自含的请求仍然可能利用权限过大的处理者泄露数据或造成不可逆转的破坏. 真正的安全来自于每个边界层次的收缩权限:

1. **类型化动词（Typed verb）：**暴露单一受限操作`archive_note`),而不是泛化的`run`或`request`这类可能产生非预期能力的工具.
2. **校验参数（Validated arguments）：**尽可能采用封闭的方案,拒绝未知的字段,对标识符进行单次规范化,限制有效载荷大小,并评估策略前验证目标地址、租户归属与资源所有权──
3. **即时鉴权（Current authorization）：**将已认证的主体与精确的动词、资源、环境及规范化参数绑定――工具注释与客户端能力绝对不赋予此权限――
4. **绑定动作的审批（Action-bound approval）：**对于高影响调用,将人工审批与类化动词及规范化参数的消化 绑定,并附加主体、过期时间和单次有效策略――任何参数变化都必须重新发行审批――
5. **一等拒绝（First-class refusal）：**拒绝,批准过期,用户拒绝和不安全目标视为常规预期结果,不执行任何副作用,绝不能拒绝降级返回权限较弱的备选工具.
6. **脱敏审计证据（Redacted audit evidence）：**记录请求者、采用的准入描述器与策略版本、授权规范目标、允许或拒绝的原因以及是否已经开始执行――

每个环节都在紧紧下一个组件中可执行的权力.最终处理程序应接受经验证的领域命令,而不是原始模型文本附带宽泛的证书.在MRTR重试时,任务更新或网关转发调用时,必须完全重返该链路.前一次单次批准绝不会使后续请求自动变成受理的会话流量.

## 关键术语

| 术语 | 含义 |
|------|------|
| 元数据投毒（Metadata poisoning） | 在 tool descriptor 中嵌入恶意提示词指令或欺骗性声明 |
| 恶意篡改（Rug pull） | 针对先前已获审批的 descriptor 进行未授权的静默修改 |
| 名字遮蔽（Tool shadowing） | 由未加限定的重复 tool name 导致的路由歧义与覆盖 |
| 头部不匹配（Header mismatch） | 路由 header 与 JSON-RPC body 内容冲突，触发错误 `-32020` |
| 哈希锁定（Hash pin） | 对经审核批准的完整规范化 descriptor 计算所得的 SHA-256 digest |
| MRTR | 多往返请求模式（Multi Round-Trip Requests），用于 server 主动请求输入并由 client 无状态重试 |
| `requestState` | 往返传递的不透明状态值，必须作为不可信输入进行完整性保护与校验 |
| Capability 声明 | 仅表示协议特性的兼容性声明，绝不代表授权与访问许可 |
| 隐式表单支持 | 空的 `elicitation` capability 对象 `{}`，等同于显式声明支持表单 |
| 完全限定名（Qualified tool name） | 网关层稳定的命名，如 `notes.search`，防止命名冲突 |
