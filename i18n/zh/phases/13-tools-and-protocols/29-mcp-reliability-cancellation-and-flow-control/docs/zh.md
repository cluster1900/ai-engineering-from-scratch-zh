# 可靠性,消耗和流控

> 要求身份证只能关联消息. 它不能让副作用变得安全,不能让后台工作进程停止,也不能保护数据流免受慢消费者的拖延.

**Type:** Build
**Languages:** Python
**Prerequisites:** Phase 13, Lessons 09 and 13
**Time:** ~120 minutes

## 学习目标

- 为studio 和 Streamable HTTP 分别实现正确的请求取消信号.
- 解决完成 (完成) 和取消 (取消) 之间的竞争态度,避免在取消后发送多余消息.
- 严格区分时时请求取消与持久化`tasks/cancel`的语义差异.
- 根据副作用属性与显式等键 (即无效性) 制定重试策略.
- 在设置进度队列容量上限时,确保最终响应不会被抛弃.
- 通过重新连接,权重拉,以及带动的退避机制实现流的恢复.

## 核心问题

最昂贵的分布式系统缺陷往往潜伏在正常执行的正常路径之外.

客户端调用一个工具――服务端开始执行――进度通知源不断发出――反向代理在中间缓冲了事件流――客户端触发超时并断开连接――服务端恰好在 1 毫秒后完成业务处理――客户端使用新的 JSON-RPC id 发起重试――于是,这项写操作 (转变) 进行了两次执行――

链路上的每个组件都没有任何错误,

 MCP 规范定义了消息格式和传输层行为,但你的应用程序仍然必须负责:

- 时间预算;
- 业务等性
- 有界队列 (有界队列)
- 重试分类(退休类别);
- 持久化任务状态 (持久任务状态);
- 重连与重新拉取策略 (重连与重新拉取策略)

本课程将这些决策构建在一个确定性模拟器中.这里没有引入睡眠,真实网络插座或随机故障.你将直接掌握取消事件的前后序列.

## 要求取消因传输层而异

客户端的意图是一致的:不再需要当前正在执行的结果.

### 工作室

采用单条共享的双向通道.

```json
{
  "jsonrpc": "2.0",
  "method": "notifications/cancelled",
  "params": {
    "requestId": 41,
    "reason": "User closed the operation"
  }
}
```

该通知属于即发即弃(火-and-forget) 服务端不需要且绝不能对其返回任何JSON-RPC响应.

服务端应停止工作,释放资源,不再发送已取消的请求响应. 如果请求未知已完成,或无法安全中断,服务端可以安全忽略取消通知.

形式错误,指向未知请求或针对已完成请求的取消通知都会被服务端默默忽视. 如果这些发出竞争态转化为新的错误报文,只会引发更多竞争态问题.

### 流式 HTTP

现代流通 HTTP 为每一个请求分发独立的 HTTP 响应或 SSE 响应流――客户端通过**直接关闭该请求的响应流**发出消耗信号.

不要为普通的HTTP 请求邮件发送`notifications/cancelled`断开流本身就是取消信号.

一旦服务端检测到连接断开,就应停止工作,并且绝不能再发送任何后续消息.

### 服务端发起的取消范围极其有限

服务端绝不能使用`notifications/cancelled`在工作室传输中,服务端发起的取消仅限于终止.`subscriptions/listen`监听请求.必须将这个极为狭窄的路径与客户端发起的常规请求加以严格区分.

## 取消是一个竞争态

两种事件发生的顺序都是完全合法的.

### 取消获胜

```text
request starts（请求启动）
client sends cancellation signal（客户端发送取消信号）
server marks request cancelled（服务端将请求标记为已取消）
worker reaches completion（工作线程执行完成）
server suppresses the response（服务端抑制并不发送响应）
```

### 完成获胜

```text
request starts（请求启动）
worker commits the result（工作线程提交业务结果）
server sends the response（服务端发送响应）
cancellation arrives late（取消信号迟到）
server ignores the late notification（服务端忽略迟到的通知）
```

客户端也必须积极忽略对已放弃的请求的迟到响应.

```figure
mcp-reliability-race
```

本课的`RequestCoordinator`一旦被取消,`complete()`已完成的记录也绝不能被取消通知.

## 超时机需要两个小时

单一的无活动 (无活动) 计时器是远远不够的.

必须同时引入两套时间限制:

1. **空闲超时（Idle timeout）**要求在多长时间内没有产生任何有用的活动即视为超时.
2. **最大超时（Maximum timeout）**根据"物理时钟预算"的要求,

持续发生的进度事件 (进步) 可以重新置空时钟,但**绝不能**推迟或消除最大截止时间

```text
start: 0 ms
progress: 400 ms
progress: 800 ms
progress: 1200 ms
idle timeout: 500 ms
maximum timeout: 2000 ms
```

在 1500 ms 时,请求仍然处于活跃状态,因为上一次进步事件的距离仅超过 300 ms.

进度通知是可选的.服务端完全可以接受进度令牌 (进度令牌) 的进度令牌 (进度令牌) 预示,但在执行期间不会发送任何更新.

进步通知必须单调递增. 在完成或取消后,所有通知必须立即停止.

## 请取消不等于`tasks/cancel`

这两种机制解决了完全不同的生命周期层面的问题.

| 机制 | 作用目标 | 线路信号 | 成功意味着什么 |
|-----------|--------|--------|--------------------|
| stdio 上的请求取消 | 单次在途 RPC | `notifications/cancelled` | 客户端放弃了该请求；若可行服务端应当停止执行 |
| HTTP 上的请求取消 | 单个在途响应流 | 关闭该流 | 客户端放弃了该请求；若可行服务端应当停止执行 |
| `tasks/cancel` | 单个持久化 Task | 普通 MCP 请求 | 服务端已确认收到取消意图 |

`tasks/cancel`调用成功并没有证明后台工人已经停止运行.`working`状态,直到在某个检查点 (检查点) 工作者感知到取消标志;工作也可能在感知到该标志之前已经成功执行完毕.

当HTTP 连接断开时,**绝不要**清除持久化任务的状态――创建任务的初衷正是让其生命周期能够超越单次请求和单条连接的限制――

## 新的JSON-RPCID绝对不等于等性

它们绝对不代表业务操作本身.

假设客户端提交了账单扣款`41`),中途失去了服务端的响应,随后客户端使用ID`42`发起重试――服务端看到的是两个截然不同的消息――如果没有应用层的唯一标识,服务端根本无法理解它们代表了同一次结账请求――

等键 (等键) 代表了业务意图:

```json
{
  "name": "charge_account",
  "arguments": {
    "account": "acct-7",
    "cents": 1200,
    "idempotencyKey": "checkout-7"
  }
}
```

服务端会持久化记录:

- 等键;
- 操作参数的哈希指纹(论点指纹);
- 已提交的执行结果──

同样的键和相同参数将直接返回之前存储的结果. 如果同样的键带有不同的参数,则将被坚决拒绝.

### 账本边界必须具有原子性和持久性

下列执行过程是极其危险且不安全的:

```text
check key（检查键是否存在）
run mutation（执行写操作）
store result（存储执行结果）
```

两个发发行员可能同时发现该键不存在,同时执行该副作用的写操作. 更糟糕的是,如果程序在执行后的副作用,储存结果发生崩,重试也会导致重复执行.

本课程使用基于文件的SQLite账本.`BEGIN IMMEDIATE`关键的检查,模拟业务副作用,执行计数器以及结果存储全部在同一事务中序列化. 即使两个独立的账本连接使用相同的键,也只会产生一次真正的业务执行并记录已提交的结果.

所有返回值均通过存储的JSON 重新反序列化生成.调用者绝不会直接获取账本内部持有的可变对象引用,从而消除调用方修改返回字典后污染后重放结果的隐患.

模拟器中的业务副作用是包含在同一SQLite 事务内的收据和计量器. 在生产环境中,实际付款,容器部署或外部第三方API调用,绝不是靠本地数据表写一条记录就能自动获得原子性的.

### 重试决策矩阵

在实现重试逻辑之前,必须对重试进行清晰分类.

| 类别 | 示例 | 重试规则 |
|------|---------|------------|
| 安全（Safe） | 无副作用的确定性读操作 | 在明确故障边界后，可使用新的 JSON-RPC id 直接重试 |
| 有条件（Conditional） | 具备持久化幂等键的写操作（Mutation） | 必须使用完全相同的幂等键和完全相同的参数发起重试 |
| 不安全（Unsafe） | 未提供业务去重机制的写操作 | 严禁自动重试；必须先进入人工或系统对账调和流程 |

工具描述符中附带的 `readOnlyHint`和 `idempotentHint`仅仅是不可信的外部提示.真正的重试安全性完全取决于应用层和服务端的底层实现.

## 背压是正确性的一部分

网络生产者生成进步事件的速度可能远远超过客户端,代理或网络链接的消费能力.

必须采用有界队列 (限队列),并确定在过载时可以牺牲什么.

进度通知可替换.对于同一个进度令牌,后来的进度数值自然取代了前来的旧值.

本课程实现缓冲区执行如下流控策略:

1. 合并(Coalesce) 同令牌相邻的进度更新;
2. 当队列达到容量限制时,丢弃最旧的进步数据;
3. 将事件流标记为需要权威数据重拉需要权威重复) ;
4. 始终完整保留最终响应;
5. 如果保留最终响应需要以抛弃另一个最终响应为代价,则拒绝该状态.

 沉默的丢失绝不是合规的策略.

### 代理缓冲问题

服务端可能在完美流式输出中,而中间的反向代理却在私人积事件缓冲.

对于SSE 响应,必须发出以下响应标题:

```http
Content-Type: text/event-stream
Cache-Control: no-cache
X-Accel-Buffering: no
```

2026 年的流媒体HTTP规范强烈建议配置`X-Accel-Buffering: no`为了兼容代理服务器 (如Nginx) 能够立即向客户端推送事件.

对于长期处于静止状态的长连接,需要定期发送 SSE 注释行(保活心跳):

```text
:
```

客户端会自动忽略注释行.中间代理设备则能够看到网络活动,从而避免切断看似空的连接.

传输保生不等于业务进步――绝不能因为收到传输层的保生注释就顺序重新置业务操作的语义空超时计时器――

## 重连意味着重新拉取

现代流通 HTTP 协议**不支持**通过`Last-Event-ID`进行断点续传.

当 当`subscriptions/listen`事件流意外中断后:

1. 使用全新的JSON-RPCID发起新的监听请求;
2. 重新注册所需订阅过器;
3. 调用权力接口全量拉取可能受到影响的工具,资源,提示或任务;
4. 根据稳定的全局唯一标识对应用层状态进行重复;
5. 绝不要仅仅因为前响应丢失就盲目重放未受保护的危险写作操作.

恢复方案显然将`sendLastEventId`设置为错误,并列出需要全量重拉的资源清单.

### 防止重连风暴 (Herd Effect)

如果1万个客户端连接断开后,恰好连接了整整一秒钟,刚刚恢复的服务端将会立即再次被打.

必须采用带有随机动 (Jitter) 和上限保护的指数退避机制――本课程根据客户端ID和重试次数计算确定性动偏移,使单元测试完全可复制:

```text
attempt 0: up to 250 ms
attempt 1: up to 500 ms
attempt 2: up to 1000 ms
...
cap: 8000 ms
```

生产环境可以采用密码学安全随机数或运行随机数. 不变的核心在于时间分布的分离,而不是特定的数学公式本身.

## 手写实现

`code/main.py`构建了五个精炼的可靠核心组件:

### `RequestCoordinator`

- 启动在请求中并维护空与最大双重截止时间;
- 发送单调递增进度通知;
- 为工作和HTTP分别生成规范的取消信号;
- 忽略非法取消通知;
- 显式裁决取消与完成之间的终极竞争态;
- 确保服务端发起的取消仅用于工作室

### `MutationLedger`

- 演示在缺乏业务键的情况下,两次使用不同的JSON-RPC id会导致两次重复执行;
- 使用文件的SQLite 事件串行化键检查,模拟业务效果,执行计数器和结果提交;
- 支持跨多个独立账本连接,对相同的等键和完全一致的参数进行全局重量;
- 拒绝使用相同的键,但改变参数的请求;
- 返回防御性深复,在重新开账文件后仍然完整保留已提交的数据.

### `DurableTaskService`

- 对取消请求进行确认回执 (确认);
- 保持任务处于`working`状态,直到工作线程主动检查到标记;
- 直观展示为什么确认收取取消绝对不等于任务已结束

### `BoundedSseBuffer`

- 在高压背压下合并或淘汰旧进步;
- 明确记录当前流已需要进行权力数据全量重拉;
- 绝不丢弃最终响应.

### 恢复辅助工具

- 输出适用于代理环境的SSE标签与保活心跳注释;
- 完成完整重连与全量重执行方案;
- 采用确定性带动指数退出算法打散重试压力

## 动手实践

为`MutationLedger`扩展一个`reserve_inventory`写操作――

需求规范:

1. 等关键需要绑定 SKU,数量,租户以及操作名称.
2. 使用相同键和完全相同参数重试时,必须直接返回第一次生成的预留结果.
3. 使用相同的键,但修改预留数量发起重试时,必须报错拒绝,并且不得产生第二次预留.
4. 当写操作已提交到服务端,但响应在回传过程中丢失时,支持借贷等关键发起对账核查.
5. 结果绝对无法记录机密证或支付敏感信息.
6. 如果客户端在调用时未提供等键,则直接禁用自动重试机械.
7. 模拟订阅流意外断开的情景,在决定后续动作前,先对该库存记录执行权力全量重拉.
8. 启动两个位于同步屏障 (Barrier) 前的账本连接,并发提交同一个等键――断言全局只有一次预留成功提交――
9. 改首次返回的预留物体.重新传入该键进行重放,证明底层存储的真实结果没有受到任何污染.
10. 关闭并重新开账文件,通过核查预留数据完好无损.

请保持工程诚信:如果库存数据实际上存在于另一个独立微服务中,请明确说明该微服务是否支持同一个等键,或者是否必须引入事务性发件箱 (Transactional Outbox) 来桥接本地提交与远程副作用.

## 生产环境故障模式

| 故障现象 | 观察到的表象 | 正确处理方案 |
|---------|--------------------|------------------|
| HTTP 客户端 POST 发送取消通知 | 服务端与客户端对请求的生命周期产生分歧 | 直接关闭该请求专有的 SSE 响应流 |
| 服务端在接受取消后依然回传响应 | 客户端收到一份已无法使用的陈旧无用结果 | 当取消获胜时停止业务计算并抑制所有后续消息 |
| 进度通知无限重置所有超时时钟 | 挂起卡死的任务永久占用资源无法退出 | 维持一个独立的全局绝对最大超时硬上限 |
| 将新的 RPC id 当成请求去重依据 | 扣款、发布或删除操作被多次重复执行 | 在应用层引入并强制校验持久化幂等键 |
| 键检查与业务副作用彼此分离 | 并发执行的多个 worker 同时判定键不存在 | 将键占位、副作用记录与结果提交放入单次原子事务 |
| 在多副本集群中使用内存级账本 | 节点重启或换到另一台机器后遗忘了先前的提交 | 使用持久化共享存储或依赖上游系统的幂等支持 |
| 直接返回底层存储的可变对象引用 | 调用方的内存修改意外污染了后续重放结果 | 将提交结果序列化存储，返回时构造深拷贝副本 |
| 相同的键被复用于篡改后的参数 | 单个幂等键混淆了两种不同的业务意图 | 持久化记录并校验调用参数的哈希指纹 |
| 进度通知队列无界增长 | 遇到慢消费者时服务内存持续飙升直至 OOM | 在容量限制内对可替代的进度通知进行合并与淘汰 |
| 在高压下误丢弃了最终响应 | 客户端永远无法获知该请求的最终成败 | 预留专用容量或只淘汰进度通知，绝不丢弃最终响应 |
| 反向代理缓冲了 SSE 事件 | 进度事件呈突发性到达，或在全部执行完后才下发 | 禁用代理缓冲（`X-Accel-Buffering: no`）并调整代理超时 |
| 盲目假定支持 `Last-Event-ID` | 客户端尝试从服务端根本不支持的位点续传 | 使用新请求重连并向权威数据源全量拉取 |
| 所有客户端在断开后同一瞬间重连 | 系统恢复的瞬间引发严重的次生雪崩风暴 | 采用带上限保护、结合随机抖动的指数退避重连机制 |
| 将 Task 的确认回执当成已完成取消 | 前端界面显示已停止，而后台 worker 仍在计费运行 | 持续轮询 Task 状态直到其真正进入终态 |

## 石头

工具生态 项目应将系统可靠性视为可执行的代码证据,而不是系统架构中的两行文字.

卡普斯通必须提供以下交付凭证:

- 针对每种传输协议的取消竞争状态执行日志;
- 针对所有暴露的重试决策矩阵;
- 等键持久记录以及参数不匹配时的拦截测试;
- 并发同关键争夺记录,重启后持久核试以及可变物体隔离测试;
- 有界缓冲区过载状态下流控处理日志;
- 反向代理 SSE 标头配置与空保活策略说明;
- 确定权力数据接口的断线重连与全量恢复方案;
- 在引入任务扩展时,完整的持久化任务取消追踪链路.

只有当失去响应,迟到取消,慢消费者以及重连风暴都能产生确定性,可预期的处理结果时,你的石才真正具备生产水平.

## 关键术语

| 术语 | 含义 |
|------|---------|
| 请求取消（Request cancellation） | 放弃单次处于在途状态的 MCP RPC 请求 |
| 取消竞态（Cancellation race） | 终态执行完成与取消信号抵达之间的时序争夺 |
| 空闲超时（Idle timeout） | 距离上一次产生有效请求活动的最大允许时间 |
| 最大超时（Maximum timeout） | 从请求开始时刻算起、不受进度通知影响的全局绝对时间上限 |
| 幂等键（Idempotency key） | 唯一标识单次特定业务意图的应用层去重标识符 |
| 原子账本（Atomic ledger） | 将键校验、副作用记录与结果提交绑定为不可分割单元的持久化存储 |
| 背压（Backpressure） | 在生产者生成速度超过消费者处理能力时施加的流量控制机制 |
| 进度合并（Progress coalescing） | 用更新的权威进度数值替换掉旧的进度更新 |
| 权威重拉（Refetch） | 在数据流中断或出现断层后，向权威接口重新读取当前全量状态 |
| 抖动（Jitter） | 在重试退避间隔中引入的随机偏移，用于在时间轴上打散瞬时并发高峰 |
