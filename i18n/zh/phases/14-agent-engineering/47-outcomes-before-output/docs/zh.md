# 在选择输出之前先定义效果

> 飞速的代码实现能力反过来增加了选错问题所付出的代价――只有先了解到所追求的实质成效,

**Type:** Learn + Build
**Languages:** Python (stdlib)
**Prerequisites:** None
**Time:** ~60 分钟

## 学习目标

- 在未预设具体解决方案的前提下,撰写成效框架 (Each-Out Framework) .
- 明确目标用户,现状及预期改善的标志.
- 显式声明硬性约束 (约束) 限制 (约束) 与非目标 (非目标)
- 识别解决方案泄漏 解决方案泄漏),防止其过早固化为开发范围.

## 交付产品不等于实质成效

构建故障应急助理 仅仅是某种产品的指标.

相比之下,成效框架 () 是这样表达的:

> 当生产环境发生警报时,值班工程师可以在两分钟内定位故障服务并确认下一步安全操作,同时整个排查过程都保持只有阅读和拥有完整的审计追踪.

这句话所定义的成效既可以通过软件实现,也可以通过优化运维手册 (runbook) 修复数据,或者进行更轻量级的界面改造来实现.

## 成效框架的六大要素

| 构成要素 | 核心问题 |
|---|---|
| 用户（User） | 谁在直接面对并承受该问题？ |
| 情境（Situation） | 该问题何时、何地发生？ |
| 当前现状（Current behavior） | 现状如何运作，包括现有的各种临时变通手段（Workarounds）？ |
| 期望成效（Desired outcome） | 哪些可观测的状态应当得到实质改善？ |
| 约束条件（Constraints） | 哪些安全、策略、成本或兼容性底线是固定的？ |
| 非目标（Non-goals） | 哪些极具诱惑但相关的邻近工作被明确排除在外？ |

```mermaid
flowchart LR
  U[用户与情境] --> C[当前现状]
  C --> O[期望成效]
  O --> K[约束条件]
  K --> N[非目标]
  N --> E[证据探究问题]
```

## 识别解决方案泄漏

当成效表述中带来未经证实的产品形式,界面形态,模型选择型,技术框架或底层架构时,就发生了解决方案泄漏:

- 用户每周收到一个AI摘要:泄漏了这个形式和每周的频率.
- 用户在审核前能够准确理解账户变更:表述是真正的成效.
- 部署量数据库:泄漏基础设施选型.
- 审核期间能够便捷获取相关合规政策依据:表述是真正的能力提升

当现有的系统兼容性真正锁定某种技术时,约束条件中可以指定该技术,但必须明确记录其被锁定的客观理由.

## 约束条件守护成效底线

约束条件绝不是单纯的实现细节,它们是真实的目标不可分割的组成部分:

- 在诊断期间严禁执行任何写入操作的生产环境;
- 应对时间必须在事故处置时间预算内控制;
- 现有审计事件记录必须继续保持唯一权威性;
- 不允许引入新的运行依赖库;
- 无障碍访问 访问性 支持必须保持完善

如果一个系统虽然表面上实现了预期目标,但违反了任何强制性约束,那么该系统是完全失败的.

## 根据非目标划清边界

没有目标能够有效防止一个应有的小巧实用功能片段成长为庞大的平台.

- 不做自动化故障修复;
- 不做全新的警报路由系统;
- 不取代现场事故指挥官 (事故指挥官);
- 本片中不涉及历史数据分析功能.
