# 百万语文下载 下的长视频理解

> 一个1小时的4K视频,24FPS,通过补丁和嵌入后,将产生约6000万个代币. 一个转录后的2小时播客单集是30,000个代币. 一部长篇蓝光电影,即使使用激进的聚合压缩,也会有数亿个代币.Google的双胞胎1.5月 (三月2024年) 启动了这个时代,能够在小时级视频中可靠地完成针头在堆中召回.LWM (Liu et al.,2024年2月) 展示了环球关注的扩展路径.

**Type:** Build
**Languages:** Python (stdlib, needle-in-haystack simulator + agentic-retrieval router)
**Prerequisites:** Phase 12 · 17 (video temporal tokens)
**Time:** ~180 minutes

## 学习目标
- 计算不同FPS和聚合下长视频的总视觉标志数量──
- 解释三条扩展路径:粗略的背景(双子 1.5) ‧环注重(LWM) ‧标记压缩(LongVILA / Video-XL) ‧
- 在准确率和延迟上比较原始文本视频VLM与代理检索视频VLMs (VideoAgent) 
- 为 30 分钟视频设计一个针子在一堆草 测试,并测量特定分钟处的召回率――

## 问题
在384原生分辨率下,单约为729个代币. 后,每使用3×3聚合81个代币. 一个30分钟片段按1FPS计算 = 1800  = 145,800 个代币. 到2025年开放的VLM可以做到,但很紧.

一部 2 小时电影按 1 FPS 是 583k 代币――超出多数 2026 年开放模型能力;需要双子 2.5 个Pro,或更激进地集成――

出现了三条扩展路径.

## 概念
### 路径1:粗的背景:

用硬件解决问题.把文本扩展到数百万代币,在一次前进传输中处理所有内容.

双子球1.5 Pro 发布时支持1M代币;双子球1.5Ultra 达到10M;2026年双子球2.5 Pro 能可靠处理数小时视频――论文(arXiv:2403.05530) 在最高约9.5M代币下,针头在一堆草 召回率达到99.7%──

工程上:一种带内存层级的自定义关注实现,加上用于长文本效率的MoE专家路由.

### 路径 2:环球注意力 (LWM,LongVILA)

环节注意 把长序列分布在多个设备上,形成一个环,每个设备都持有一个块――对完整序列的注意力通过环节模式完成:每个设备把自己的块 发送给下一个设备,计算部分注意力,并进行聚合――

通过这种方式训练了一个1M-Token 模型――训练计算量随着本文线性扩展而不是平方扩展,因为注意的平方成本被分摊到环中设备上――

长VILA(arXiv:2408.10188) 把该模式适配到VLMs──1400 视频,每 192 个代币 = 268k文本,并使用8个方向平行的环节注意力训练──

### 路径3:电话压缩 (视频-XL,长VA)

比原始背景更便宜:在LLM 看到序列之前进行激进压缩.

视频-XL(arXiv:2409.14485) 使用视觉总结代币:每个包含N 的片段 产生一个单独的总结代币,该代币会到N ──在推断时,LLM 每个片段只看到一个总结代币,从而大幅缩小了文本──

长时间使用长文本转移技术将LLM文本从200k扩展到2M.

标志压缩使用特定时间的召回能力来换取可扩展性.模型通常知道发生了什么,但有时会错过精确性.

### 路径 4: 代理检索 (视频代理)

不要把完整的视频输入LLM.相反,把视频视频作为数据库,并使用LLM查询它.

视频代理:

1. 学生学习问题
2. 请请我带着猫的段子来看看.
3. 工具 返回匹配的剪辑时间标签──
4. 通过VLM读取这些视频.
5. 组织答案或提出后续查询.

简单的说法,更便宜的,更难的.

### 子子中的针标

标准长文本测试:在视频中的随机位置插入一个唯一的视觉或文本标记,然后提出一个需要记忆的标记查询.

标记位置的回忆@k。

双子球2.5 Pro 在最长90分钟视频上分 >99% 召回率──开放 72B 模型(Qwen2.5-VL-72B、InternVL3-78B) 在30分钟处分约85-90%,超过60分钟后下降──

如果工具足够好,视频代理在 2+ 小时场景下可以匹配或超过原始文本模型,因为检索可以命中针.

### 选择哪个路径

对于边界精度的15分钟剪辑:开放 72B + 原生文本通常可行──选择 Qwen2.5-VL-72B──

对于30分钟到1小时内容:开放模型选择 LongVILA 或 Video-XL;闭源选择 Gemini 2.5 Pro──质量门很重要,边界走闭源──

对于2+ 小时内容:视频代理或类似的检索模式──或,摘要成更小的部分,并输入等级摘要──

### 2026年生产模式

实际上,生产级长视频管道是混合式的:

1. 对于整个视频运行动态-FPS采样+积极的集成 (图片显示100k-Token的全局)
2. 传给72BVLM 生成全局摘要
3. 如果用户提出细节问题,请使用该摘要作为指数运行代理检索.

这结合了原始文本的全局理解和检索的局部细节能力.

## 使用它
`code/main.py`其他:

- 计算 1 分钟到 3 小时视频在不同的FPS + 聚合下的代币 预算。
- 模拟一次针头在一堆草 运行:在随机时刻注入标记,提出问题,并评估召回
- 包含一个代理检索路由器模拟器,用于选择输入下游VLM的特定剪辑.

运行预算表,感受尺度差距

## 交付它
本课产出发 `outputs/skill-long-video-strategy-planner.md`△给定视频时间长度和查询复杂性,它会在粗文背景的压缩和代理检索之间选择,并计算延迟 +质量预期.

4. 环球注意的内存成本随着序列长度线性扩张,也随着设备数量线性扩展.

5. 阅读双子座 1.5 第5节关于子中的针的内容.

## 关键术语
| Term | What people say | What it actually means |
|------|-----------------|------------------------|
| Brute context | “只是更多 Token” | 将 LLM context 扩展到数百万 Token；一次性处理所有内容 |
| Ring attention | “LWM-style parallel” | 分布式 attention 模式：每个设备持有一个 chunk 并轮转 |
| Token compression | “Summary tokens” | 在进入 LLM 前，通过 learned compressor 减少每个 clip 的 Token |
| Needle-in-haystack | “NIH test” | 在随机位置插入唯一 marker，在测试时要求模型回忆它 |
| Agentic retrieval | “LLM as query planner” | LLM 向 retrieval tool 请求相关 clips，通过 VLM 读取它们，并组织答案 |
| VideoAgent | “Retrieval pattern for video” | 规范的 agentic-retrieval 设计：question -> tool -> clip -> answer |
