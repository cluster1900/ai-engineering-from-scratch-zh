## 概念

### RFC 8414  OAuth 授权服务器元数据

位于 `/.well-known/oauth-authorization-server`ووصف الملفات كل المعلومات التي يحتاجها المستخدم:

```json
{
  "issuer": "https://auth.example.com",
  "authorization_endpoint": "https://auth.example.com/authorize",
  "token_endpoint": "https://auth.example.com/token",
  "jwks_uri": "https://auth.example.com/.well-known/jwks.json",
  "client_id_metadata_document_supported": true,
  "registration_endpoint": "https://auth.example.com/register",
  "authorization_response_iss_parameter_supported": true,
  "response_types_supported": ["code"],
  "grant_types_supported": ["authorization_code", "refresh_token"],
  "code_challenge_methods_supported": ["S256"],
  "scopes_supported": ["mcp:tools.read", "mcp:tools.invoke"],
  "token_endpoint_auth_methods_supported": ["none", "private_key_jwt"]
}
```

客户端在获取MCP 资源URL 后进行链式发现:先通过RFC 9728 `oauth-protected-resource`(资源服务器文档) للحصول على معرفة من المؤمنين المصدرين، ثم من خلال RFC 8414 ((本规范文档) للحصول على كل نقطة خدمة من المصدرين.

بالنسبة للكلمة المحتوية على المعلومات، يرجى إدخال المعلومات المعروفة في هذه المعلومات.`https://mcp.example.com/team/server`على ضوابط الموارد المحمية`https://mcp.example.com/.well-known/oauth-protected-resource/team/server`‬ ‫لا يجب أن تكون`/.well-known/...`خطأ إضافة في طريق الموارد بعد ذلك.

في اعتماد某身份提供商 (IDP) تستخدم مؤسسة MCP قبل الاختبار:

- `code_challenge_methods_supported`يجب أن تتضمن`S256`(توافق مع RFC 7636 要求 PKCE)**缺失**, إذا أشار إلى أن هذا الجهاز لا يدعم PKCE,**必须**رفضوا مواصلة التنفيذ
- `grant_types_supported`包含 `authorization_code`، قاطع رفض`password`和 `implicit`.
- على الأقل دعم نموذج للتسجيل:`client_id_metadata_document_supported: true`(CIMD,首选) 、 إحصاءات العملاء المخصصة مسبقاً، أو `registration_endpoint`(لقد تم إلغاء RFC 7591 兼容模式)
- إذا`authorization_response_iss_parameter_supported`للحق، والعملاء التزامية الامتحانات القانونية للرد على RFC 9207 `iss`,并严格将其与重定向之前记录发发发人比对.
- في OAuth 2.1 规范下،`response_types_supported`يجب أن يكون واضحاً`["code"]`.

若缺少`S256`دعم، خادم MCP قاطع رفض الوصول إلى IDPPKCE  لا يوجد نظام تخفيض `client_id`, لا يمكن أيضاً إكمال التواصل; في الوقت الحالي يجب تعديل تعيين التصفيقات ، بدلاً من تعديل الكود.

### 客户端 ID 元数据文档(推默认方案)

سيتم تسجيل المستخدم من التقليدي 推(Push) 模式反转为拉(Pull) 模式── المستخدم لم يعد يتجه إلى طلب الخادم المفوض للحصول على سلطة`client_id`بدلاً من ذلك ، سوف تتحكم مباشرة في عنوان HTTPS**作为**`client_id` URL هذا يشير إلى مستند JSON 元数据; المُسلّط الخادم في عملية OAuth لتحقيق الحاجة إلى الوصول إلى هذا الملف.`app.example.com`اسم المجال، ثمّة ثقة في الوصول`https://app.example.com/client.json`هذا الجهاز قام بإزالة التسجيلات الحركية والعودة إلى التواصل، وتجنب`client_id`命名空间耗尽风险,也省去了跨服务器同步状态的复杂性──

客户端所托管的元数据文档结构如下:

```json
{
  "client_id": "https://app.example.com/oauth/client.json",
  "client_name": "Example MCP Client",
  "client_uri": "https://app.example.com",
  "application_type": "native",
  "redirect_uris": ["http://127.0.0.1:7333/callback", "http://localhost:7333/callback"],
  "grant_types": ["authorization_code", "refresh_token"],
  "response_types": ["code"],
  "token_endpoint_auth_method": "none"
}
```

文档内部的 `client_id`字段值**必须**مع توطيب هذه الملفات URL  تماما مطابقة  المُسلّط الخادم سوف تقاسِم على نحو صارم، إذا لم يُسلّط مباشرة رفض)  المُسلّط الخادم في نفسها RFC 8414 元数据中通过 `client_id_metadata_document_supported: true`声明支持此特征──

في قواعد المجلس الوطني للطاقة البدنية`client_id`.`client_name`مع غير فارغ`redirect_uris`عدد المستخدمين لتحقيق المعلومات. يجب أن يكون العلامات التعرفية للعملاء هو URL HTTPS المطلقة التي تحمل مسارات.`application_type`لكنّه ليس جزءاً مُجبرّاً من CIMD`application_type`المعدات المستخدمة حتى الانتخابات الأولية على طريق CIMD

规范明确指出的两个核心安全事实:

- **防范 SSRF：**授权服务器拉取是攻击者提供的URL,必须严密防范服务端请求伪造(严禁访问内部私有网络及管理端点)
- **防范 localhost 冒充：**وحدها على CIMD لا يمكن منع المهاجمين المحليين من استخدام عنوان البيانات المستخدمة من المستخدمين الشرعيين و لا يرتبطون بأي طريقة`localhost`重定向端口── لذلك، عندما يعرض الخادم الموافقة على المستخدم صفحة الموافقة على الموافقة،**必须**清晰展示重定向 URI 的主机名,并**应当**لـ "الصافية "`localhost`تُصدر تحذيرات أمنية

وبما أن CIMD لا تحتاج إلى حالة التسجيل الدائمة في الخدمة، فإنه لم يعد بحاجة إلى مركز تسجيل معقد مثل DCR ذلك الحفاظ على مركز خدمات التسجيل المعقد.

إذا كان مدير الخدمة المفروضة قد تمت توزيع علامات المستخدم مسبقاً، يجب أن تستخدم أولاً شهادة التسجيل المسبقة المخصصة للمصدر المحدد، ثم تحاول التسجيل تلقائياً. وإلا فإن المصدر الأول لم يدعم التسجيل المسبق أو يدعم CIMD، إلا إذا عاد إلى برنامج DCR المُهجر.

### RFC 7591: مسار التسجيل المشترك المرفوض

تم إلغاء DCR في 2026-07-28 规范修订中已正式废弃―― فقط لمعالجة عدم القدرة على استخدام CIMD 且无法进行预注的旧版授权服务器保留――兼容客户端发送如下注册请求:

```json
POST /register
Content-Type: application/json

{
  "application_type": "native",
  "redirect_uris": ["http://127.0.0.1:7333/callback"],
  "grant_types": ["authorization_code", "refresh_token"],
  "response_types": ["code"],
  "token_endpoint_auth_method": "none",
  "scope": "mcp:tools.invoke",
  "client_name": "Cursor",
  "software_id": "com.cursor.cursor",
  "software_version": "0.42.0"
}
```

 خدمة الاستجابة `client_id`وبالإضافة إلى إعادة استخدام التخصيصات`registration_access_token`:

```json
{
  "client_id": "c_3e7f1a",
  "client_id_issued_at": 1769472000,
  "redirect_uris": ["http://127.0.0.1:7333/callback"],
  "grant_types": ["authorization_code", "refresh_token"],
  "registration_access_token": "regt_b2...",
  "registration_client_uri": "https://auth.example.com/register/c_3e7f1a"
}
```

`application_type`具有严格约束力: استخدام عنوان الحلقة المكتبية يجب أن يعلن عن`native`؛ على أساس خدمة توظيف الويب  تطبيقات العملاء يجب أن يعلن`web`و لا تستخدم HTTPS 重定向 URI.`token_endpoint_auth_method: none`هو صحيح التشغيل الافتراضي، في الوقت الحالي المستخدم فقط تم توزيعها`client_id`، إثبات الملكية يعتمد تماما على PKCE 保障

الثلاثة فخات دفاعية للقطاع:

- يجب أن تكون النقاط المرجعية على أساس IP المصدرة محددة بشكل صارم. وإلا يمكن للمهاجم كتابة كتابة كتابة تسجيل ملايين العملاء المزيفين، ويتم استهلاكهم.`client_id`命名空间── يجب أن يكون في محركات التسجيل
- بعض المؤسسات تدريجية IDP  ضابط`software_statement`(من أجل المستخدمين خلف الكتاب الموقع JWT) ―― هذا مثال سوف ينقصه؛ ولكن في الإنتاج ينبغي زيادة منطق تجربة، رفض إدخال غير الموقع خارج محيط التوجيهات المباشرة للعودة إلى المنطقة.
- `registration_access_token`في التخزين يجب أن يكون محفوفاً، لا يمكن أبداً حفظها بوضوح.

### RFC 8707 ((回顾) 资源指示符 ((مؤشرات الموارد)

### 常见故障模式(أوضاع الفشل)

- **陈旧过期的 JWKS：**بعد تغيير المفتاح AS ، سيتم إعطاء الاختيار القانوني للتوقيت. الحل هو المهام المذكورة أعلاه في الوقت الحالي.
- **回退机制误搞成密钥轮换：**لتحقيق خطأ في طريق العودة غير المقصود لإنتاج مفتاح جديد محليا بدلاً من إعادة إعادة إعادة إرسالها إلى الخارج ، هذا خطأ منطقي خطير للغاية: إنه ليس فقط لا يمكن إعادة إرساله إلى الداخل.`kid`، وسوف يسمح للمهاجمين باستخدام المزيف`kid`تنفيذ المفتاح المتفجّر الهجوم على الدول العربية.
- **缺失 `aud` Claim：**بعض النسخة القديمة من الـ IdP 默认会省略 `aud`، إلا إذا كان العميل قد قدم عرضاً واضحاً في طلبات الوهم`resource` يجب أن يكون الاختبار قاطعاً لرفض غياب`aud`لا يمكن أن تُضيف إضفاء نظرة على إضافة إضافة إضافة إلى إضافة.
- **遗漏 `iss` 校验导致的 Mix-Up 攻击：**客户端若未校验 RFC 9207 授权响应中 `iss`参数,可能会被诱惑将诚实AS的授权码提交给黑客控制的代码端点――这是典型的客户端缺陷,资源服务器无法弥补――
- **Scope 提升并发竞争：**مع واحد المستخدم اثنين من المشاركات في إصدار الاختيارات ارتفاعات الدورية) قد يكون عملية النجاح في وقت سابق، وتوليد اثنين من الوصول اليدوية التي لها أهمية مختلفة. يجب أن يقوم المختبر بإصدار الحكم بشكل كامل على أساس اليدوية المحددة المرفقة بالطلب الحالي، لا يمكن أن تذهب إلى قاعدة البيانات بشكل مختلف للتحقيق في ما يطلق عليه أحدث نطاق لهذا المستخدم الحالي.
- **注册 Token 泄露：**التفريغ`registration_access_token`سيتم إضافة الرقم المستخدم إلى مخزن الاحتياطي؛ يجب أن يضطر العميل إلى إظهار بيانات واضحة في كل تحديث؛ وعندما يتم إفراز شكوك في التداول على الفور.
- **未固定 `iss` 白名单：**验签器若盲目接受任何 `iss`، يمكن للمهاجم أن يُنشئ خادمًا مصدرًا للشيء السيئ ، وذلك استهدافًا للمستهدف من خلال إصدار رموز للشيء السيئ.`authorization_servers`قائمة هي قائمة بيضاء يجب أن تكون محكمة
- **凭据或 Token 缓存键混淆：**客户端 إذا كان فقط على أساس الموارد على بطاقة التسجيل إنشاء مؤشر، قد يعرض مؤشر المرسل المفوض على خدمة أخرى. 客户端 إذا كان فقط على أساس المصدِّر على بطاقة الوصول إنشاء مؤشر، فإنه قد يضع الـ Token خطأ إلى مصادر الجمهور الخطأ.`(issuer, resource)`الوصول إلى رمز، وعندما يصدر المرسل يتعين إعادة التسجيل.

## 关键术语

| 术语 | 通俗说法 | 精确工程含义 |
|------|---------|-------------|
| ASM | "OAuth 元数据文档" | RFC 8414 规范的 `/.well-known/oauth-authorization-server` JSON 文档 |
| CIMD | "客户端元数据 URL" | 客户端 ID 元数据文档（Client ID Metadata Document）：将 HTTPS URL 直接作为 `client_id`，由 AS 主动拉取 JSON。MCP 2026-07-28 首选注册方式 |
| DCR | "自助客户端动态注册" | RFC 7591 规定的 `POST /register`；在当前 MCP 规范中已废弃，仅作兼容兜底 |
| JWKS | "用于 JWT 验签的公钥集合" | JSON Web Key Set，从 `jwks_uri` 拉取，内部按 `kid` 进行哈希索引 |
| Rotate vs Refresh | "更新公钥" | **Rotate（轮换）** = 授权服务器签发/作废签名密钥；**Refresh（刷新）** = 资源服务器重新拉取发布的公钥。资源服务器仅能执行 Refresh |
| 资源指示符（Resource indicator） | "受众参数" | RFC 8707 规定的 `resource` 参数，用于将 Token 强绑定到特定 server |
| `aud` Claim | "受众标识" | JWT 中的 Claim 字段，验签器将其与自身的规范化资源 URL 进行严格字符串比对 |
| 受众重放（Audience replay） | "Token 重放攻击" | 将为 Server A 签发的 Token 拿到 Server B 去尝试调用；由受众校验防御（规范术语：访问令牌特权限制） |
| 混淆代理（Confused deputy） | "代理 Token 滥用" | 拥有静态客户端 ID 的 MCP 代理服务在未获取逐客户端同意授权的情况下盲目转发 Token；与受众重放本质不同 |
| Mix-up 混淆攻击 | "Token 端点走错门" | 客户端被恶意诱导将诚实 AS 派发的授权码拿到攻击者控制的端点去兑换；由客户端依照 RFC 9207 `iss` 校验进行防御 |
| `iss` 白名单 | "受信任的授权服务器集合" | 在受保护资源元数据的 `authorization_servers` 字段中显式声明的受信任列表 |
| `resource_metadata` | "去哪里查找 PRM 文档" | 401/403 质询头 `WWW-Authenticate` 中的标准参数，指向 RFC 9728 元数据文档的获取 URL |
| 公共客户端（Public client） | "Native 或浏览器端客户端" | 无法安全保管 `client_secret` 的客户端类型；依赖 PKCE 机制实现所有权证明 |
| `WWW-Authenticate` | "401/403 响应头" | 携带 `Bearer error=...` 等指令指导客户端如何进行凭据补全与错误恢复的标准 HTTP 响应头 |
