# vLLM خدمة الداخلية: الاهتمام المخصص

> يعتمد الهيمنة في vLLM في عام 2026 على ثلاثة إعدادات افتراضية متداخلة ، وليس على بعض الممارسات الفردية.`code/main.py`في منتصف اللعبة مستمرة البطشة  انتهى، فإنه سيكون مثل vLLM

**Type:** Learn
**Languages:** Python (stdlib, toy continuous batching scheduler)
**前置要求：**المرحلة 17 · 01 (خدمة النموذج) ، المرحلة 11 (هندسة الجامعة)
**Time:** ~75 minutes

## 學习目标
- 将 PagedAttention  شرح للمخصص الاحتياطي KV:البلوكات  جداول الاحتياطي، وكذلك لماذا يبقى التجزئة تحت الحمل الإنتاج في 4% أعلاه.
- في التكرار 层面 رسم سلسلة مستمرة:完成的序列 如何离开批量,新序列 如何加入,而不需要排泄──
- استخدام كلمة تصف الملفات المضادة المقطوعة،并 يقول أنه يحمي أي متريض التأخير
- ويقولون إن 2026 عام vLLM v0.18.0 سيؤثر على تلك المرات التي يتم فيها إضافة جميع المجموعات المثلى

## 问题
حلقة خدمة PyTorch بسيطة تنفيذ طلب واحد: توكيينز ، قبل إكمال ، فك التشفير حتى EOS ، عودة إلى الوراء.

vLLM 同时解决三个问题──PagedAttention 阻止KV cache 碎片化像经典连续分配那样吃掉 60-80% من ذاكرة GPU──Continuous batching 允许请求在每次解码代谢中 加入和离开批次,因此批次 始终充满真实工作──Chunked prefill 32 将k-token prompt 拆成约512-token 的片片,并与解码交错执行,因此长速不结 GPU 上的每个解码代码代码符号──

إنتاج عام 2026 هو المبدأ المطلق. تحتاج إلى فهم دور كل آلية، لأن النموذج الفاشل هو على الجدول المخطط، وليس على النموذج.

### التكرار 层面的 تسلسل مستمر

旧式 dynamic batching 会等窗口(على سبيل المثال 10 ms) لتملأ اللفة ، ثم تنطلق prefill + decode + decode + decode ، حتى كل تسلسل 完成──快 تسلسل 会提前离开并置 ، بينما GPU 继续处理慢序列──

التسلسل المستمر في كل خطوة لتفكيك 之间运行──把正在运行的序列 集合称为 `RUNNING`القائمة:

1. `RUNNING`أي تسلسل يصل إلى EOS أو max_tokens سيتم نقله.
2. المخطط 查看 انتظار الصف. إذا كان هناك كاوش كيو، فإنه سوف يتقبل تسلسلات جديدة.
3. المضي قدما في حال حاضر `RUNNING`على المحتوى المحتوى، لكل تسلسل إصدار رمز جديد

حجم اللحظة 永远不会被填充到固定数字──输出位置不同序列 共享一次融合前面──在2026年VLLM中,这叫做`V1 scheduler` المجدول: كل إعادة تشكيل 运行 مرة واحدة، بدلا من كل طلب 运行 مرة واحدة‬

### الاحتمالات المسبقة للفئة المقطوعة  حفاظت الذيل TTFT

إعداد مسبق هو الحساب مقيدة للـ: ∙ إلاما 3.3 70B 上的 32k-token prompt 在单张 H100 上需要大约800 ms 的纯预填── قبل إعداد 运行时,batch 中所有其他序列的解码代码都在等待── 在服务循环中,长快速的第一代码延迟(TTFT) 将变成几十其他用户的互联代码延迟(ITL) 动──

سيقوم المخطط بتشغيل المخططات المحددة إلى قطع كبيرة جداً (مفتوحة 512 رمز) ، ويقوم بتشغيل المخططات المحددة لتتبعها.

### ثلاث إعدادات متضمنة تتفاعل

هذه الوظائف الثلاثة تفترض وجود بعضها البعض. الصفحة الاهتمام للمخطط. توفر جزيئات صغيرة من الموارد الكهربائية لتوزيعها.`RUNNING`القرارات التي يتم اتخاذها من القائمة، إنها مجرد سياسة أخرى من المجدول، وليس نظام مستقل.

أنت لا تحتاج إلى معرفة كل علم. أنت تحتاج إلى معرفة المخططات.

### 2026 سنة v0.18.0 的 gotcha

في vLLM v0.18.0، أنت لا يمكن أن `--enable-chunked-prefill`مع تشفير المضاربة النموذج مشروع`--speculative-model`(ج) 结合使用──文档说明的例外是 V1 جداول المواعيد في N-gram GPU تخمينات فكيفية. those do not read release notes 就打开所有旗的团队,会遇到运行时间错误,而不是软性回归.

### نمط المخطط

```
while True:
    finished = [s for s in RUNNING if s.is_done()]
    for s in finished: release_blocks(s); RUNNING.remove(s)

    while WAITING and have_free_blocks_for(WAITING[0]):
        s = WAITING.pop(0)
        allocate_initial_blocks(s)
        RUNNING.append(s)

    # schedule prefill chunks + decode in one batch
    batch = []
    for s in RUNNING:
        if s.in_prefill:
            batch.append(next_prefill_chunk(s))   # e.g. 512 tokens
        else:
            batch.append(decode_one_token(s))     # 1 token

    run_forward(batch)                            # one fused GPU call
```

`code/main.py`正是这个循环的 stdlib Python 版本,使用假的代币数 和假的前延迟――运行它会显示碎片的预填 如何在长期预填 期间让解码序列保持活跃――

## 关键术语
| Term | What people say | What it actually means |
|------|----------------|------------------------|
| PagedAttention | “KV trick” | 用于 KV cache 的固定大小 block allocator；碎片化 <4% |
| Block table | “page table” | 每个 sequence 从 logical token position 到 physical KV block 的映射 |
| Continuous batching | “dynamic batching, but right” | 每个 decode iteration 都做 admit/release 决策 |
| Chunked prefill | “prefill splitting” | 将长 prefill 拆成 512-token 切片并与 decode 交错 |
| TTFT | “first token time” | Prefill + queue + network；在长 prompts 下由 prefill 主导 |
| ITL | “inter-token latency” | 连续 decode tokens 之间的时间；由 batch size 主导 |
| Goodput | “满足 SLO 的 throughput” | 每个 request 仍命中 TTFT 和 ITL targets 时的 tokens/sec |
| V1 scheduler | “new scheduler” | vLLM 的 2026 scheduler；N-gram spec decode 是与 chunked-prefill 兼容的路径 |
| `--gpu-memory-utilization` | “memory knob” | 在 weights 和 activations 之后为 KV blocks 预留的 HBM 比例 |
